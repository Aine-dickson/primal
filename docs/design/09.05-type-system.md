The type system is particularly important for this DSL because we aren't just dealing with ordinary programming values. We're dealing with **mathematical objects, physical quantities, spatial objects, symbolic expressions, simulations, observations, and representations**.

The goal is therefore not:

> "Make a Rust-like type system."

The goal is:

> **Make invalid scientific/mathematical constructions difficult or impossible to express, while keeping valid authoring natural.**

---

# 1. What is a type doing here?

A type answers:

> **What kind of value is this, and what operations make semantic sense for it?**

For ordinary programming:

```text
42 : Integer
3.14 : Real
true : Boolean
```

But our DSL needs considerably more:

```text
9.81 m/s²
(3, 4) m
velocity
electric_field
probability_distribution
particle
graph
equation
dataset
```

So our type system needs to capture **meaning**, not just memory representation.

---

# 2. The type-system layers

I think we should separate the type system into several layers:

```text
TYPE SYSTEM
│
├── PRIMITIVE TYPES
│   ├── Boolean
│   ├── Integer
│   ├── Real
│   ├── Complex
│   └── String
│
├── MATHEMATICAL TYPES
│   ├── Vector
│   ├── Matrix
│   ├── Tensor
│   ├── Point
│   ├── Set
│   ├── Sequence
│   ├── Function
│   ├── Distribution
│   └── Expression
│
├── SCIENTIFIC TYPES
│   ├── Quantity
│   ├── Unit
│   ├── Dimension
│   ├── Uncertainty
│   └── Domain
│
├── MODEL TYPES
│   ├── Object
│   ├── Property
│   ├── Relation
│   ├── Collection
│   ├── Field
│   └── State
│
├── OBSERVATION TYPES
│   ├── Observation
│   ├── Measurement
│   └── Data
│
└── PRESENTATION TYPES
    ├── Projection
    ├── Representation
    ├── View
    └── Interaction
```

But again, this doesn't mean every line gets a special primitive type.

Some will be parameterized or derived.

---

# 3. Primitive scalar types

We start with:

```text
Boolean
Integer
Real
Complex
String
```

Potentially later:

```text
Natural
Rational
Decimal
```

But we shouldn't add types just because they're mathematically interesting.

The key question is whether they have distinct semantics useful to authors.

---

# 4. Exact vs approximate numbers

This is important for mathematics.

Consider:

```text
1 / 3
```

versus:

```text
0.3333333333
```

They are not semantically equivalent.

Likewise:

```text
sqrt(2)
```

may be exact while:

```text
1.41421356
```

is approximate.

So we should not make `Real` mean:

> IEEE floating-point number.

Instead, `Real` should be a **semantic numeric type**.

Its execution representation could be:

```text
exact rational
symbolic expression
arbitrary precision
f64
f32
GPU representation
```

depending on context.

This maintains:

```text
SEMANTIC NUMBER
        ≠
MACHINE REPRESENTATION
```

---

# 5. Numeric hierarchy

A possible conceptual hierarchy:

```text
Number
├── Integer
├── Rational
├── Real
└── Complex
```

But there is a complication.

Should:

```text
Integer → Real
```

be implicit?

Probably yes in many mathematical contexts.

But:

```text
Real → Integer
```

should not silently happen.

Likewise:

```text
Real → Complex
```

can generally be promoted.

We therefore need **coercion rules**.

---

# 6. Numeric promotion

Conceptually:

```text
Integer
   ↓
Rational
   ↓
Real
   ↓
Complex
```

where permitted.

But we should be careful not to let automatic conversion destroy exactness.

For example:

```text
1 / 3
```

shouldn't silently become a floating-point approximation merely because a `Real` appears somewhere.

This is a future semantic rule we should preserve.

---

# 7. Quantity

This is probably one of the most important types in the entire DSL.

Instead of:

```text
gravity = 9.81
```

we want:

```text
gravity = 9.81 m/s²
```

A quantity consists conceptually of:

```text
Quantity
├── magnitude
├── unit
└── dimension
```

---

# 8. Unit vs Dimension

These are different.

For example:

```text
1 m
100 cm
0.001 km
```

have different units but the same dimension:

```text
Length
```

Likewise:

```text
1 s
1000 ms
```

are both:

```text
Time
```

Therefore:

```text
Dimension(Length)
```

and:

```text
Unit(meter)
```

must be separate concepts.

---

# 9. Dimensional arithmetic

This lets the type system catch errors.

For example:

```text
velocity = distance / time
```

gives:

```text
Length / Time
```

Therefore:

```text
velocity : Length / Time
```

And:

```text
energy = mass * velocity²
```

produces:

```text
Mass × Length² / Time²
```

which is energy.

But:

```text
distance + time
```

should fail semantically.

This is a huge benefit of the DSL.

---

# 10. Units shouldn't be the whole type

We should be careful here.

If:

```text
x : 5 m
```

and:

```text
y : 7 cm
```

then both are quantities of dimension Length.

The magnitude and unit are values.

The **dimension** participates in type checking.

So conceptually:

```text
Quantity<Length>
Quantity<Time>
Quantity<Velocity>
Quantity<Energy>
```

rather than making every possible unit a completely separate type.

---

# 11. Vectors

We need vectors as mathematical objects.

For example:

```text
velocity = (10, 20)
```

But vector dimensionality matters.

```text
Vector<2>
Vector<3>
Vector<N>
```

And so does the component type:

```text
Vector<2, Real>
Vector<3, Quantity<Velocity>>
```

Potentially:

```text
Vector<3, m>
```

as shorthand for a vector whose components carry Length dimension.

---

# 12. Point vs Vector

This distinction is crucial.

A point represents a location.

A vector represents displacement/direction.

So:

```text
Point<2, Length>
Vector<2, Length>
```

are not interchangeable.

Mathematically:

```text
Point + Vector → Point
Point - Point → Vector
Vector + Vector → Vector
```

But:

```text
Point + Point
```

should normally not be a valid ordinary operation.

This is exactly the sort of semantic safety the type system should provide.

---

# 13. Geometry

Geometry is broader than points/vectors.

Potential semantic types:

```text
Geometry
├── Point
├── Line
├── Segment
├── Circle
├── Ellipse
├── Polygon
├── Curve
├── Region
└── Mesh
```

But these are likely **parameterized types or library types**, rather than all being kernel primitives.

The core type system needs to support them.

The geometry library can define the actual shapes.

---

# 14. Matrix

Matrices need dimensional information:

```text
Matrix<Rows, Columns, ElementType>
```

For example:

```text
Matrix<3,3,Real>
```

Operations then become type-aware:

```text
Matrix<3,3> × Vector<3>
    → Vector<3>
```

while:

```text
Matrix<3,3> × Vector<2>
```

is invalid.

---

# 15. Tensor

We should not hard-code only vectors and matrices.

A tensor is a natural generalization.

Conceptually:

```text
Tensor<Shape, ElementType>
```

A matrix is effectively a rank-2 tensor.

A vector is rank-1.

This lets scientific domains introduce:

- stress tensors
- electromagnetic tensors
- multidimensional datasets

without modifying the core type system.

---

# 16. Functions

Function types need both input and output types.

For example:

```text
f : Real → Real
```

or:

```text
f : Vector<2> → Real
```

or:

```text
E : Point<2, Length> → Vector<2, ElectricField>
```

For multiple arguments:

```text
f : (Real, Real) → Real
```

This becomes particularly important for fields and projections.

---

# 17. Generic functions

We will likely need genericity.

For example:

```text
magnitude : Vector<N,T> → T
```

rather than defining:

```text
magnitude2
magnitude3
magnitude4
...
```

This doesn't necessarily mean exposing Rust-style generics to the author.

The semantic type system can support them underneath.

---

# 18. Collections

Collections need element types.

For example:

```text
Collection<Particle>
Collection<Real>
Collection<Point<2>>
Collection<Node>
```

We may distinguish:

```text
Set<T>
Sequence<T>
Map<K,V>
```

Potentially also:

```text
Multiset<T>
```

if scientific/statistical use requires it.

---

# 19. Dynamic collections

A key requirement from our catalogue is that collections can change.

For example:

```text
particles
```

may go:

```text
1000
 ↓
997
 ↓
1003
```

through creation/destruction.

The type:

```text
Collection<Particle>
```

doesn't change.

Its **state** changes.

This is another useful separation:

```text
TYPE
≠
CURRENT CARDINALITY
```

---

# 20. Object types

We need object identity plus structure.

For example:

```text
Particle
```

could be a user-defined type:

```text
Particle {
    position : Point<2, Length>
    velocity : Vector<2, Velocity>
    mass     : Quantity<Mass>
}
```

The core language doesn't need to know what "Particle" means.

It only needs to understand:

```text
ObjectType
```

with properties and relationships.

This is how domain libraries become possible.

---

# 21. Relations as types

Relations can also have types.

For example:

```text
ConnectedTo<A,B>
Orbits<Planet,Star>
Bond<Atom,Atom>
```

But we should be cautious about encoding too much domain semantics into the type system.

The core needs to know:

```text
Relation<A,B>
```

and libraries can specialize it.

---

# 22. References

Since objects have identity, the language needs references.

Conceptually:

```text
Reference<T>
```

For example:

```text
Reference<Particle>
```

This lets us distinguish:

```text
particle
```

from:

```text
particle.position
```

and:

```text
copy of particle state
```

This becomes important for relations, events, interactions and collections.

---

# 23. Expressions as values

A particularly interesting capability is symbolic mathematics.

Consider:

```text
x² + 2x + 1
```

At one point this may be an expression.

Later we might evaluate it at:

```text
x = 3
```

So we may need:

```text
Expression<T>
```

where:

```text
Expression<Real>
Expression<Vector<3>>
Expression<Quantity<Energy>>
Expression<Boolean>
```

are possible.

This allows symbolic and numerical worlds to coexist.

---

# 24. Symbolic vs evaluated value

This is a major design decision.

We may have:

```text
Expression<Real>
       ↓ evaluate
Real
```

For example:

```text
x² + 1
```

is an expression.

After:

```text
x = 3
```

it can evaluate to:

```text
10
```

The two shouldn't be confused.

This will be crucial for:

- displaying equations
- symbolic transformations
- numerical evaluation
- graphing
- differentiation
- solving

---

# 25. Equations as typed objects

An equation can be thought of as:

```text
Equation<LHS, RHS>
```

but semantically it is more useful to think:

```text
Equation<T>
```

where both sides are compatible expressions of type `T`.

For example:

```text
mass * acceleration = force
```

requires compatible dimensions.

Likewise:

```text
x = y
```

requires compatible types.

---

# 26. Constraints

A constraint operates on a predicate.

Conceptually:

```text
Constraint<State>
```

or more generally:

```text
Constraint<Context>
```

For example:

```text
mass > 0
```

becomes a Boolean condition over state.

The constraint adds semantics:

> This condition must hold for a valid state.

---

# 27. Fields

Now revisit the field question.

A field:

```text
F(x,y)
```

can be represented as:

```text
Function<Domain, Value>
```

For example:

```text
Field<Point<2>, Real>
```

or:

```text
Field<Point<3>, Vector<3, Velocity>>
```

This strongly suggests:

> **Field does not need to be a fundamentally separate type.**

It can be a semantic specialization of a function over a domain.

However, the field abstraction can still exist in the domain library and runtime because it may have special computational behavior.

---

# 28. Probability distributions

We should distinguish:

```text
Distribution<T>
```

from:

```text
RandomSource
```

A distribution says:

> What probability model exists?

A random source says:

> How do we generate samples?

For example:

```text
Normal<Real>
Uniform<Real>
Poisson<Integer>
```

could be library types.

---

# 29. Random source

Conceptually:

```text
RandomSource
├── algorithm
├── seed
└── state
```

This is runtime state rather than simply a mathematical value.

Therefore:

```text
Distribution<T>
```

belongs to mathematical semantics.

Whereas:

```text
RandomSource
```

belongs to computation/runtime semantics.

---

# 30. Data types

Observed data is more structured than a normal collection.

A dataset might have:

```text
Dataset
├── values
├── axes
├── dimensions
├── units
├── timestamps
├── metadata
├── uncertainty
└── provenance
```

Potential type:

```text
Dataset<T>
```

or multidimensional:

```text
Dataset<Shape, T>
```

This will support:

- plotting
- tables
- statistics
- exporting
- scientific analysis.

---

# 31. Uncertainty

Scientific measurements may need:

```text
Measurement<T>
├── value
├── uncertainty
├── unit
├── timestamp
└── metadata
```

But uncertainty should probably not contaminate every `Quantity`.

A theoretical value:

```text
9.81 m/s²
```

doesn't necessarily have measurement uncertainty.

A measurement:

```text
9.81 ± 0.02 m/s²
```

does.

So:

```text
Quantity<T>
     ↓
Measurement<Quantity<T>>
```

is more sensible.

---

# 32. Time types

We need to distinguish:

```text
Instant
Duration
Time
```

For example:

```text
t = 5 s
```

could represent a duration or simulation-time coordinate depending on context.

The type system should prevent nonsensical operations.

For example:

```text
instant + duration → instant
instant - instant → duration
duration + duration → duration
```

This is similar to Point/Vector semantics.

---

# 33. Space types

Similarly:

```text
Space<N, CoordinateSystem>
```

can describe model space.

For example:

```text
Space<2, Cartesian>
Space<3, Cartesian>
Space<2, Polar>
```

Then:

```text
Point<Space>
Vector<Space>
```

can carry appropriate dimensional information.

---

# 34. Model state types

Now we move above mathematical values.

A system has state:

```text
State<S>
```

where `S` describes its schema.

For example:

```text
ProjectileState
```

might contain:

```text
ball.position
ball.velocity
```

The state type should encode **structure**, not current values.

---

# 35. Property types

Properties can have roles.

For example:

```text
Stored<T>
Derived<T>
Parameter<T>
Computed<T>
```

This is interesting because we don't necessarily need separate runtime types.

We might instead have:

```text
Property<T, Role>
```

Conceptually:

```text
Property<Real, Stored>
Property<Velocity, Derived>
Property<Acceleration, Computed>
Property<Gravity, Parameter>
```

This would be powerful for semantic checking.

---

# 36. Mutability

Mutability is not exactly a type.

It's a semantic capability.

For example:

```text
Stored<T>
```

may be writable.

Whereas:

```text
Derived<T>
```

may be read-only.

And:

```text
Parameter<T>
```

may be writable by authorized interactions but not by arbitrary model processes.

So we should distinguish:

```text
TYPE
+
ROLE
+
CAPABILITIES
```

rather than stuffing everything into the base type.

---

# 37. Presentation types

We also need types for:

```text
Representation
Projection
View
```

For example:

```text
Projection<ModelValue, Representation>
```

Conceptually:

```text
Point<2>
      ↓
Projection
      ↓
Circle
```

or:

```text
Dataset<Real>
      ↓
Projection
      ↓
Plot
```

The representation type can remain separate from the model type.

---

# 38. Interaction types

An interaction may have:

```text
InputType
IntentType
TargetType
OperationType
```

For example:

```text
Drag<PointRepresentation>
```

may map to:

```text
Set<Point.position>
```

This gives the compiler enough information to check that an interaction is meaningful.

---

# 39. Type compatibility

We now need to distinguish several relationships.

### Exact type match

```text
Real ↔ Real
```

### Numeric promotion

```text
Integer → Real
```

### Unit conversion

```text
cm → m
```

### Dimensional compatibility

```text
m ↔ cm
```

### Structural compatibility

```text
Vector<2> ↔ Vector<2>
```

### Semantic incompatibility

```text
Time ✕ Length
```

### Reference compatibility

```text
Particle reference → Particle
```

These should not all be handled by one generic "conversion" mechanism.

---

# 40. Operator semantics

Operators must be type-aware.

For example:

```text
+:
    Real + Real → Real
    Vector + Vector → Vector
    Point + Vector → Point
    Duration + Duration → Duration
```

But:

```text
Point + Point
```

may be invalid.

Multiplication:

```text
mass * acceleration → force
```

must also propagate dimensions.

Division:

```text
distance / time → velocity
```

Again, semantic typing becomes useful.

---

# 41. Function composition

If:

```text
f : A → B
g : B → C
```

then:

```text
g ∘ f : A → C
```

This seems obvious mathematically, but it becomes extremely useful for projections.

For example:

```text
temperature
   ↓
normalize
   ↓
color
```

is:

```text
Quantity<Temperature>
    → Real
    → Color
```

The type system can verify the chain.

---

# 42. Collection transformations

Similarly:

```text
map : Collection<A> × (A → B) → Collection<B>
```

and:

```text
filter : Collection<A> × (A → Boolean) → Collection<A>
```

and:

```text
reduce : Collection<A> × ... → B
```

This is enough to express huge numbers of data/model transformations.

---

# 43. Generic domain types

We should support parameterized concepts rather than creating endless types.

For example:

```text
Vector<N,T>
Matrix<R,C,T>
Collection<T>
Function<A,B>
Reference<T>
Dataset<T>
Expression<T>
```

This gives us a compact type vocabulary.

---

# 44. User-defined types

This is absolutely necessary.

An author should be able to define:

```text
type Particle {
    position : Point<2, m>
    velocity : Vector<2, m/s>
    mass     : kg
}
```

Then:

```text
particles : Collection<Particle>
```

The core doesn't need to know what a particle is.

This is what lets the domain libraries and eventually users extend the system.

---

# 45. Structural vs nominal types

We now encounter an important design decision.

Suppose:

```text
type Particle { ... }
```

and:

```text
type Ball { ... }
```

have identical properties.

Should they be considered the same type?

### Structural typing

If the structure is identical:

```text
Particle ≈ Ball
```

### Nominal typing

They remain distinct because their declared identity differs.

For a scientific DSL, I suspect we will need **both concepts** in different situations.

For example:

```text
Vector<2, m/s>
```

can be structural.

But:

```text
Particle
Electron
Node
```

may be nominal semantic types.

We'll defer the final decision to later type-system refinement.

---

# 46. Subtyping

We may eventually need relationships such as:

```text
Object
  ↑
PhysicalObject
  ↑
Particle
```

or:

```text
Number
  ↑
Real
```

But unrestricted inheritance could make the language unnecessarily object-oriented.

So we should prefer **semantic type relationships** over automatically adopting class inheritance.

---

# 47. Capability types

There is another interesting possibility.

Instead of saying:

```text
Point
```

is inherently draggable, we could say:

```text
Draggable<Point>
```

or conceptually:

```text
Point + writable(position)
```

Likewise:

```text
Observable<T>
Projectable<T>
Measurable<T>
```

This could become useful later.

But we should not introduce capability types until we know we need them.

---

# 48. Static vs dynamic typing

I strongly think the DSL should be **predominantly statically typed**.

Why?

Because we want the compiler to catch:

```text
distance + time
```

and:

```text
Vector<2> + Vector<3>
```

and:

```text
Point + Point
```

and:

```text
Function<Real,Real>(Vector)
```

before runtime.

But static typing doesn't mean everything must be known at compile time.

Simulation values are obviously dynamic:

```text
position(t)
```

The **type** is static.

The **value** changes.

---

# 49. Runtime-dependent types

For example:

```text
particles : Collection<Particle>
```

The compiler knows:

```text
Particle
```

but doesn't know:

```text
count(particles)
```

until runtime.

That's fine.

We don't need dependent types for ordinary dynamic model state.

---

# 50. Symbolic typing

A symbolic expression should retain its semantic type.

For example:

```text
x : Length
```

then:

```text
x² : Length²
```

and:

```text
x / t : Velocity
```

even if `x` hasn't been assigned a numerical value yet.

This is a powerful feature.

The compiler can perform dimensional/type analysis on symbolic mathematics.

---

# 51. Type inference

We shouldn't force authors to annotate everything.

For example:

```text
x = 5 m
```

can infer:

```text
x : Quantity<Length>
```

And:

```text
v = x / t
```

can infer:

```text
v : Quantity<Velocity>
```

Likewise:

```text
f(x) = x²
```

can infer the structure of the expression where possible.

So:

```text
AUTHOR WRITES
    ↓
compiler infers
    ↓
semantic type
```

---

# 52. But don't infer what is ambiguous

For example:

```text
x = 5
```

Should that mean:

```text
Integer
Real
Quantity
```

We can infer numeric type from context where possible.

But if the context is genuinely ambiguous, the compiler should require clarification.

This aligns with our earlier principle:

> **Infer when safe; require explicit information when ambiguous.**

---

# 53. Type errors should be semantic

Examples:

```text
distance + time
```

→ incompatible dimensions.

```text
Point<2> + Point<2>
```

→ invalid operation.

```text
Vector<2> + Vector<3>
```

→ incompatible dimensions.

```text
f : Real → Real
f((1,2))
```

→ argument type mismatch.

```text
temperature → position
```

→ invalid projection mapping unless an explicit conversion exists.

These are much better errors than generic runtime failures.

---

# 54. Proposed Type Model

Our current candidate looks like:

```text
TYPE
│
├── Scalar
│   ├── Boolean
│   ├── Integer
│   ├── Rational
│   ├── Real
│   └── Complex
│
├── Scientific
│   ├── Quantity<Dimension>
│   ├── Unit
│   ├── Dimension
│   └── Measurement<T>
│
├── Mathematical
│   ├── Vector<N,T>
│   ├── Matrix<R,C,T>
│   ├── Tensor<Shape,T>
│   ├── Point<Space>
│   ├── Set<T>
│   ├── Sequence<T>
│   ├── Function<A,B>
│   ├── Distribution<T>
│   ├── Expression<T>
│   └── Equation<T>
│
├── Structural
│   ├── Object
│   ├── Property
│   ├── Collection<T>
│   ├── Relation<A,B>
│   ├── Reference<T>
│   └── State<S>
│
├── Observation
│   ├── Observation<T>
│   └── Dataset<T>
│
└── Presentation
    ├── Projection<A,B>
    ├── Representation
    ├── View
    └── Interaction
```

# 55. What is *not* a type?

This distinction is important.

These should generally **not** be treated simply as types:

```text
Process
Event
Constraint
Operation
Parameter
Animation
Experiment
```

They have **semantic roles**.

For example:

```text
Parameter<Real>
```

might be a perfectly valid way to represent a parameter, but "parameter" is more than a type: it defines how that value participates in the model.

Likewise:

```text
Process
```

is behavior, not merely a value.

So our semantic model and type model remain separate.

---

# 56. Type + Role + Capability

This gives us a useful three-layer view:

```text
WHAT IS IT?
    ↓
TYPE

WHAT DOES IT MEAN IN THE MODEL?
    ↓
ROLE

WHAT MAY BE DONE WITH IT?
    ↓
CAPABILITY
```

Example:

```text
gravity
```

might be:

```text
TYPE:
    Quantity<Acceleration>

ROLE:
    Parameter

CAPABILITIES:
    read
    modify
    observe
```

Whereas:

```text
speed
```

might be:

```text
TYPE:
    Quantity<Velocity>

ROLE:
    Derived Property

CAPABILITIES:
    read
    observe
```

And:

```text
ball.position
```

might be:

```text
TYPE:
    Point<2, Length>

ROLE:
    Stored Property

CAPABILITIES:
    read
    modify
    observe
```

This is significantly more expressive than trying to make one type system encode everything.

---

# 57. The type system's job

We can now define its boundary:

```text
TYPE SYSTEM SHOULD ANSWER:

What kind of value is this?
What operations are valid?
Are dimensions compatible?
Are units compatible?
Are function inputs/outputs compatible?
Are collection elements compatible?
Are references compatible?
Are expressions well-typed?
Are equations dimensionally/type consistent?
Can a projection connect these values?
Can an interaction target this value?
```

It should **not** answer:

```text
Which solver should run?
How should Vello render this?
When should an event execute?
How should the camera move?
```

Those belong elsewhere.

# 58. Type-system architecture

For the eventual Rust implementation, conceptually:

```text
SOURCE
  ↓
AST
  ↓
NAME RESOLUTION
  ↓
TYPE INFERENCE
  ↓
TYPE CHECKING
  ↓
DIMENSION / UNIT CHECKING
  ↓
SEMANTIC ANALYSIS
  ↓
SEMANTIC IR
```

The type checker should operate before runtime construction.

# 60. The emerging type philosophy

The type system should be:

> **Strong enough to understand mathematics and scientific meaning, but not so strong that every simulation becomes a theorem-proving exercise.**

That means:

```text
STATIC WHERE SEMANTICALLY USEFUL
DYNAMIC WHERE VALUES NATURALLY CHANGE
INFERRED WHERE UNAMBIGUOUS
EXPLICIT WHERE AMBIGUOUS
DOMAIN-AWARE WITHOUT HARD-CODING DOMAINS
```

# 61. Where this leaves us

Our current candidate is:

```text
                    TYPE
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
     SCALAR      MATHEMATICAL    STRUCTURAL
        │             │             │
   Integer         Vector         Object
   Real            Matrix         Property
   Complex         Function       Collection
   Boolean         Expression     Relation
                  Equation         Reference
                  Point             State
                  Tensor
        │
        ↓
   SCIENTIFIC
        │
   Quantity
   Dimension
   Unit
   Measurement
        │
        ↓
   OBSERVATION / PRESENTATION
```

And we have deliberately avoided making every domain concept a built-in type.

# 62. One issue we must carry forward

There is a subtle issue that will matter enormously in **09.6 Scoping / Binding**:

Suppose we write:

```text
ball.position
```

What exactly is `position`?

Is it:

```text
a property?
a variable?
a binding?
a reference?
a computed expression?
a state slot?
```

And when we write:

```text
x
```

how does the compiler know whether `x` refers to:

```text
a local value
a system variable
an object property
a parameter
a function
a collection
a type
a field
a module symbol
```

That is no longer primarily a type problem.

It is a **name-resolution and binding problem**.

Which is exactly why **Scoping / Binding** must come next rather than prematurely trying to solve everything inside the type system.
