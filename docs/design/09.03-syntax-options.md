# Part I: Construct Minimization

## 1. The question

For every candidate construct, ask:

> If we remove this as a fundamental language construct, can its semantics still be expressed naturally and unambiguously using the remaining core?

There are three possible outcomes:

```text
FUNDAMENTAL
    ↓
Cannot reasonably remove it.

DERIVED
    ↓
Can be expressed from more fundamental constructs.

CONVENIENCE
    ↓
Could be built into syntax/library for authoring ergonomics,
but isn't fundamental to the semantic kernel.
```

---

# 2. Start with the mathematical layer

Our current candidates are:

```text
VALUE
TYPE
EXPRESSION
FUNCTION
PREDICATE
EQUATION
```

### Value

Obviously fundamental.

Without values, there is no model.

**→ KEEP**

---

### Type

We could theoretically have dynamically typed values, but our system needs:

- dimensional checking
- vector/matrix distinction
- function domains
- geometry
- collections
- references
- model validation

So some type system is fundamental.

**→ KEEP**

---

### Expression

Could expressions be represented as functions?

For example:

```text
x + y
```

could technically become:

```text
fn(x, y) => x + y
```

But that would be unnecessarily awkward and would obscure ordinary mathematical authoring.

More importantly, expressions occur everywhere:

```text
mass * acceleration
x^2
temperature > 300 K
position + velocity * dt
```

**→ KEEP as a semantic construct.**

Whether it gets special syntax is another matter.

---

### Predicate

A predicate is essentially:

```text
Expression → Boolean
```

Therefore we don't need a completely separate semantic primitive.

**→ DERIVED FROM EXPRESSION + BOOLEAN TYPE**

It may still have convenient syntax.

---

### Function

A function has a stable semantic identity:

```text
Domain → Codomain
```

and can be passed around, composed, sampled, visualized, etc.

For example:

```text
f(x) = sin(x)
```

**→ KEEP**

---

### Equation

An equation is more interesting.

Could:

```text
a = b
```

just be a Boolean expression?

Mathematically, yes:

```text
equal(a,b)
```

But our system needs equations to have semantic roles such as:

```text
constraint
definition
governing relationship
differential equation
displayed mathematical object
```

An equation may also be passed to a solver.

So treating it merely as Boolean equality loses useful semantics.

**→ KEEP as a semantic construct.**

---

# 3. Object layer

Candidates:

```text
OBJECT
PROPERTY
COLLECTION
RELATION
```

### Object

Identity is fundamental.

Two objects can have identical values but still be distinct.

```text
particle₁ ≠ particle₂
```

**→ KEEP**

---

### Property

Could properties simply be relations?

Technically:

```text
particle --has_position--> point
```

But then ordinary authoring becomes unnecessarily relational.

Properties are such a pervasive part of the model that they deserve first-class treatment.

**→ KEEP**

---

### Collection

Could a collection simply be an object whose property contains other objects?

Technically yes.

But collections are fundamental to the case catalogue:

```text
particles
students
nodes
data
cells
molecules
```

And operations such as filtering, mapping and aggregation are ubiquitous.

**→ KEEP**

---

### Relation

Could relations be represented as properties?

No, not cleanly.

Relations can:

- connect multiple objects
- have their own properties
- appear/disappear
- change topology
- be queried independently

For example:

```text
A connected_to B
```

is not naturally just a property of A or B.

**→ KEEP**

---

# 4. Context layer

Candidates:

```text
DOMAIN
SPACE
TIME
PARAMETER
FIELD
```

### Domain

Fundamental.

A function needs a domain.

A field needs a domain.

A variable may be constrained to a domain.

**→ KEEP**

---

### Space

Could space be a specialized domain?

Yes.

That suggests:

```text
Domain
  └── SpatialDomain
```

rather than two unrelated primitives.

**→ DOMAIN SPECIALIZATION**

We probably don't need a completely separate semantic foundation.

---

### Time

Same situation.

Time is a special domain/context with temporal semantics.

So:

```text
Domain
  ├── SpatialDomain
  ├── TemporalDomain
  └── ...
```

may eventually be more elegant.

But time has additional runtime semantics, so we should retain it as a **first-class language concept**, even if internally it specializes `Domain`.

**→ FIRST-CLASS CONCEPT, DOMAIN-BASED SEMANTICS**

---

### Parameter

A parameter could technically be:

```text
variable + metadata
```

But its semantic role is sufficiently important:

> "This value is intended to configure/control the model."

For an authoring language, that distinction is useful.

**→ KEEP AS A DECLARATIVE CONSTRUCT**

---

### Field

Could a field simply be a function?

Mathematically:

```text
F(x,y,t)
```

is indeed a function.

But fields have important semantics:

- sampling
- interpolation
- spatial visualization
- potentially cached numerical representation
- field-specific operations

Still, that doesn't necessarily mean `field` must be a primitive.

We could have:

```text
function : Domain → Value
```

and specialize it as a field when its domain is spatial.

This is an important potential simplification.

**→ PROVISIONALLY DERIVED FROM FUNCTION + DOMAIN**

We should test this later against field-heavy cases.

---

# 5. Behavior layer

Candidates:

```text
RULE
PROCESS
EVENT
CONSTRAINT
```

### Constraint

Could be:

```text
predicate + validation semantics
```

Yes.

But constraints have a semantic role beyond ordinary predicates.

For example:

```text
position lies inside region
```

isn't merely something we ask `true/false`; it restricts permitted states.

**→ KEEP AS SEMANTIC CONCEPT**

---

### Rule

A rule is essentially:

```text
condition → operation
```

That could be constructed from:

```text
predicate
+
operation
```

So it may not need to be fundamental.

**→ DERIVED**

---

### Event

An event is:

```text
condition/time/input
→ occurrence
→ operations
```

Again, it may be built from more primitive scheduling/operation machinery.

However, events are important enough that a DSL probably wants first-class event declarations.

**→ SEMANTIC CONSTRUCT, POSSIBLY SURFACE CONVENIENCE**

---

### Process

A process describes evolution.

Could it simply be:

```text
behavior + time
```

Possibly.

For example:

```text
dx/dt = v
```

already describes continuous evolution.

But discrete processes and algorithmic processes need a clear identity.

**→ SEMANTIC CONSTRUCT**

---

# 6. Observation layer

```text
OBSERVATION
DATA
```

### Observation

Could observation simply be a function:

```text
State → Value
```

For example:

```text
measure_speed(state)
```

Mathematically yes.

But observation has semantics that a normal function does not:

- sampling time
- measurement uncertainty
- instrument characteristics
- recording
- observation provenance

**→ KEEP**

---

### Data

Could data simply be collections?

Often, yes.

But observed datasets have:

- dimensions
- axes
- timestamps
- units
- metadata
- provenance
- uncertainty

So `Data` deserves a semantic category.

**→ KEEP**

---

# 7. Presentation layer

Candidates:

```text
PROJECTION
REPRESENTATION
VIEW
```

This is where the architecture we developed really pays off.

### Projection

Definitely keep.

```text
Model → Projection → Representation
```

It expresses the semantic mapping.

**→ KEEP**

---

### Representation

Keep.

The thing being rendered is not necessarily the model itself.

**→ KEEP**

---

### View

Keep as a presentation context.

Multiple views can observe the same representation/model.

**→ KEEP**

---

# 8. Interaction layer

Candidates:

```text
INTERACTION
OPERATION
```

### Operation

Fundamental because it describes an effect:

```text
set
modify
create
destroy
connect
disconnect
...
```

**→ KEEP**

---

### Interaction

Could an interaction simply be:

```text
input → operation
```

Yes, but targeting, intent, modes, transactions and interpretation make it a useful semantic construct.

For example:

```text
drag(point)
```

is very different from a raw mouse event.

**→ KEEP**

---

# 9. Experiment

Could an experiment be:

```text
system
+
snapshot
+
parameters
+
operations
+
observations
```

Yes.

So it is **composable**.

However, experiments are a major intended use case.

That makes this a candidate for a **high-level language construct** rather than a kernel primitive.

**→ HIGH-LEVEL LANGUAGE CONSTRUCT**

---

# 10. System

Everything needs a semantic boundary.

**→ KEEP**

# 11. The minimized semantic kernel

After this analysis, our candidate **deep kernel** becomes considerably smaller:

```text
CORE SEMANTIC KERNEL
│
├── TYPE
├── VALUE
│
├── OBJECT
├── PROPERTY
├── COLLECTION
├── RELATION
│
├── DOMAIN
│
├── EXPRESSION
├── FUNCTION
├── EQUATION
├── CONSTRAINT
│
├── PROCESS
├── EVENT
│
├── STATE
│
├── OPERATION
│
├── OBSERVATION
├── DATA
│
├── PROJECTION
├── REPRESENTATION
├── VIEW
│
├── INTERACTION
│
└── SYSTEM
```

And these become derived/specialized:

```text
PREDICATE     ← Expression returning Boolean

RULE          ← Predicate + Operation

FIELD         ← Function over a spatial/domain context

SPACE         ← Domain specialization

TIME          ← Domain + temporal/runtime semantics

PARAMETER     ← Value/Variable + configuration semantics

EXPERIMENT    ← System + execution + observations + interventions

ANIMATION     ← Time + presentation-state transformations
```

This is a much healthier direction.

---

# 12. But there's an even deeper question

We have:

```text
PROPERTY
VARIABLE
VALUE
PARAMETER
STATE
```

Do we really need all of these?

Consider:

```text
particle.position = (3,4)
```

We could view that as:

```text
Object
 └── named binding
       └── Value
```

Then a variable is simply a binding whose value may change.

A parameter is a binding with configuration semantics.

A property is a binding associated with an object.

This suggests a deeper construct:

# **Binding**

Conceptually:

```text
NAME → VALUE
```

with metadata describing:

```text
ownership
mutability
derivation
constraints
role
```

Then:

```text
property = object-owned binding
variable = mutable binding
parameter = configuration binding
constant = immutable binding
derived property = computed binding
```

This is promising, but **we should not adopt it yet**.

Why?

Because this is precisely the kind of abstraction that looks elegant on paper but can become awkward when authoring real physics and mathematics.

We will test it in the type/scoping stages.

# Part II: What should the syntax actually feel like?

Now we can finally start discussing syntax.

But we shouldn't pick one syntax immediately.

Let's identify the major syntax families.

---

# 13. Option A: Declarative block DSL

Something like:

```text
system Projectile {

    parameter gravity = 9.81 m/s^2

    object ball {
        position = (0, 0)
        velocity = (10, 15)
        mass = 1 kg
    }

    process motion {
        ...
    }

    view scene {
        ...
    }
}
```

### Strengths

Very readable.

Good for educational authoring.

Naturally represents hierarchical systems.

### Weakness

Can become extremely nested.

---

# 14. Option B: Entity/component style

Something closer to:

```text
system Projectile

object ball
    position = (0, 0)
    velocity = (10, 15)
    mass = 1 kg

parameter gravity = 9.81 m/s^2

process motion
    ...
```

### Strengths

Flat and easy to edit.

Potentially excellent for tooling.

### Weakness

Relationships between constructs may become less visually obvious.

---

# 15. Option C: Mathematical/declarative style

Something closer to mathematics:

```text
system Projectile

g := 9.81 m/s²
m := 1 kg

position(t) := ...
velocity(t) := ...

velocity' = (0, -g)

trajectory := observe position(t)
```

### Strengths

Extremely natural for scientific/mathematical users.

### Weakness

Less obvious how to express complex interactive systems.

---

# 16. Option D: Hybrid

This is currently the most interesting direction to investigate.

Mathematical things look mathematical:

```text
g := 9.81 m/s²

f(x) := x²

F = m * a
```

Structural things look declarative:

```text
system Projectile {
    ...
}
```

Presentation looks declarative:

```text
view Scene {
    ...
}
```

Interaction looks event-oriented:

```text
on drag(ball) {
    ...
}
```

This could give us:

```text
MATHEMATICS → mathematical syntax
MODEL      → declarative syntax
BEHAVIOR   → rule/process syntax
VIEW       → declarative presentation syntax
INTERACTION→ event/operation syntax
```

Rather than forcing everything into one syntactic shape.

---

# 17. We should not choose based on aesthetics

We need a harder test.

Take one concept and express it using each syntax family.

Let's use the simplest meaningful case:

> A ball is launched upward. Gravity acts on it. Its position is displayed. The user can drag the ball to change its initial position.

A hypothetical hybrid language might look like:

```text
system Projectile {

    parameter g = 9.81 m/s²

    object ball {
        position = (0 m, 0 m)
        velocity = (8 m/s, 12 m/s)
        mass = 1 kg
    }

    process motion {
        velocity' = (0, -g)
        position' = velocity
    }

    view scene {
        show ball as circle
        show ball.position
        show trajectory
    }

    interaction drag(ball.position)
}
```

Notice what this already tells us.

We have:

```text
system
parameter
object
property
process
equation
view
projection
interaction
```

But the author doesn't need to mention:

```text
renderer
frame
matrix
hit test
inverse transform
solver
scheduler
```

That's exactly what we want.

---

# 18. Now test a pure mathematical case

We must make sure the language isn't secretly a simulation DSL.

For:

```text
f(x) = x²
```

we should not need:

```text
system
process
simulation
runtime
```

A plausible program could simply be:

```text
f(x) = x²

view graph {
    plot f(x)
}
```

This is extremely important.

The DSL must support:

```text
mathematical visualization
```

without pretending there is a simulation.

---

# 19. Test a purely visual animation

Suppose we want:

> Draw a circle, move it across the screen, then fade it out.

There may be no model whatsoever.

Conceptually:

```text
circle = ...
animate circle.position from A to B
animate circle.opacity from 1 to 0
```

Therefore the language must permit a **presentation-only program**.

This reinforces:

```text
MODEL
≠
REQUIRED FOR EVERY PROGRAM
```

---

# 20. Test stochastic radioactivity

Suppose:

> 1000 unstable atoms decay according to a decay probability.

We need something conceptually like:

```text
atoms = create 1000 atoms

process decay {
    each atom:
        if random() < probability(λ, dt):
            atom.alive = false
}
```

But our eventual language shouldn't force the author to manually implement stochastic mathematics if a chemistry/physics library can provide it.

This reveals another important design principle:

> **The core language needs to express stochastic behavior; domain libraries can make common stochastic models concise.**

---

# 21. Test graph algorithms

Suppose:

> Visualize BFS traversing a graph.

The model might be:

```text
graph
nodes
edges
queue
visited
```

The representation might be:

```text
nodes → circles
edges → lines
queue → table
current node → highlight
```

And the algorithm:

```text
process bfs {
    ...
}
```

This is very different from projectile motion.

Yet the same semantic structure works.

That is a strong indication that we're not accidentally designing a physics language.

---

# 22. Test multi-view representation

Consider radioactive decay again.

One model:

```text
atoms
decay process
```

could simultaneously produce:

```text
View microscopic {
    show atoms
}

View graph {
    plot remaining_atoms over time
}

View equation {
    show dN/dt = -λN
}

View statistics {
    show histogram of decay times
}
```

The critical property is:

```text
             MODEL
          /    |    \
         ↓     ↓     ↓
      View A View B View C
```

rather than:

```text
Model A
Model B
Model C
```

So our syntax needs a way to make this relationship explicit.

---

# 23. Preliminary syntax principle

At this stage, I would **not choose exact keywords yet**.

But the evidence is increasingly pointing toward a **hybrid declarative DSL**:

```text
MATHEMATICAL EXPRESSIONS
        ↓
   look mathematical

MODEL DECLARATIONS
        ↓
   look declarative

BEHAVIOR
        ↓
   looks rule/process oriented

PROJECTION / VIEW
        ↓
   looks declarative

INTERACTION
        ↓
   looks event/operation oriented
```

This is much more natural than forcing the entire language into either:

```text
everything = function calls
```

or:

```text
everything = nested JSON-like blocks
```

# 25. What we have learned from 09.3

The construct minimization gives us an important result:

### We should NOT build a language with one primitive for every concept.

Instead:

```text
             USER DSL
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
  CORE LANGUAGE       DOMAIN LIBRARIES
       │                   │
       ↓                   ↓
 semantic kernel       Physics/Chemistry/
                       Math/CS/etc.
```

And the DSL should provide **convenient surface constructs** that may compile down to the smaller kernel.

# 27. One more thing before 09.4

We have intentionally exposed a question that is too important to bury:

### What is a declaration versus an expression versus an operation?

For example:

```text
mass = 2 kg
```

Could mean:

1. declare a property,
2. assign a value,
3. define a computed relationship,
4. constrain mass,
5. initialize state.

Those are **semantically different** even though they look identical.

Similarly:

```text
position = velocity * t
```

could mean:

- a definition,
- an assignment,
- an equation,
- an initial condition.

Therefore the next artifact must establish exactly how syntax maps onto the semantic model.

That is precisely:

# **09.4 Semantic Mapping**

There we will take constructs such as:

```text
object
property
function
equation
process
event
view
projection
interaction
```

and define:

> **What does each construct actually mean in the generalized model?**

We'll also tackle the very important distinction between:

```text
DECLARATION
DEFINITION
ASSIGNMENT
INITIALIZATION
DERIVATION
CONSTRAINT
EVOLUTION
```

because getting that wrong would make the DSL ambiguous at its foundation.
