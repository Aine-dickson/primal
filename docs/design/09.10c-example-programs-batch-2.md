# 09.10 Example Programs, Batch 1 Refinement + Batch 2

The first batch gives us enough evidence to tighten the semantics before throwing harder cases at them.

One useful external check is that hybrid-systems literature independently makes essentially the same distinction we encountered: continuous evolution and discrete/event-triggered behavior need explicit semantics rather than being treated as one undifferentiated mechanism.

---

# Part A: Resolve the Batch 1 findings

## 1. `Process` should remain, but become an umbrella

We discovered three fundamentally different computational behaviors:

```text
BEHAVIOR
│
├── FUNCTION
│   └── input → output
│
├── PROCESS
│   ├── CONTINUOUS
│   │   └── differential/algebraic evolution
│   │
│   ├── DISCRETE
│   │   └── state transitions
│   │
│   ├── ALGORITHMIC
│   │   └── ordered computation / iteration
│   │
│   └── STOCHASTIC
│       └── probabilistic evolution
│
├── EVENT
│   └── occurrence / trigger
│
├── RULE
│   └── condition → operation
│
└── CONSTRAINT
    └── restrict valid states
```

So this:

```text
process motion {
    d(x)/dt = v
}
```

and this:

```text
process bfs {
    while queue not empty {
        ...
    }
}
```

are both processes, but **not the same execution kind**.

Therefore the semantic IR should carry an execution classification:

```text
Process
├── continuous
├── discrete
├── algorithmic
└── stochastic
```

The DSL does not necessarily need four different top-level keywords.

---

# 2. Multiple processes should not "write" the same derivative

This was one of the most important findings.

Bad model:

```text
process gravity {
    d(v)/dt = gravity
}

process wind {
    d(v)/dt = wind
}
```

If assignments are interpreted literally, we get an ownership conflict.

Instead, evolution should distinguish **definition** from **contribution**.

For example:

```text
process gravity {
    contribute acceleration to ball.velocity:
        (0, -g)
}

process wind {
    contribute acceleration to ball.velocity:
        wind_acceleration
}
```

Semantically:

```text
ball.velocity
      ↑
      │
 ┌────┴─────┐
 │          │
gravity    wind
 │          │
 └────┬─────┘
      ↓
combined evolution
```

The generalized form becomes:

```text
EvolutionTarget
    +
Contributions
    +
Combination semantics
```

For simple additive dynamics:

\[
\frac{dv}{dt}
=
a_\text{gravity}
+
a_\text{wind}
\]

But **addition is not universal**.

Another system might require:

```text
replace
minimum
maximum
priority
sequential transformation
constraint intersection
solver coupling
```

So we shouldn't bake "sum all contributions" into the core.

### Refined semantic rule

> Multiple behaviors may contribute to the same evolution target only through an explicitly defined combination semantics.

This is much safer.

---

# 3. State variables, properties and parameters

We found:

```text
ball.position
```

and:

```text
θ
```

look similar but aren't quite the same.

Let's separate the concepts.

### Binding

At the deepest level:

```text
Binding
├── name
├── type
├── value
├── role
├── ownership
├── mutability
└── metadata
```

Then:

```text
parameter
variable
constant
property
derived value
```

can be roles.

But **object property** still has special semantics because it belongs to an identifiable object.

So:

```text
ball.position
```

means:

```text
object = ball
property = position
```

while:

```text
θ
```

means:

```text
system state binding = θ
```

Therefore we should **not** collapse properties and state variables into one syntax yet.

The deeper common abstraction is binding.

---

# 4. Relations vs derived geometry

Consider:

```text
AB = segment(A.position, B.position)
```

This is not necessarily a semantic relation.

We should distinguish:

```text
Relation
    connects semantic objects

Geometry
    describes geometric structure

Projection
    converts semantic information into representation
```

Therefore:

```text
relation connected(A, B)
```

could exist independently of:

```text
segment(A.position, B.position)
```

And a geometry projection might turn the relation into a visible segment.

This is cleaner:

```text
A ───── semantic relation ───── B
             │
             ↓
         projection
             │
             ↓
       visual segment
```

That means **a line on screen does not automatically mean a semantic relation**.

Good.

---

# 5. Continuous events

The bouncing-ball example exposed something important.

The model says:

```text
when position.y <= 0
```

but a numerical solver might jump from:

```text
y = +0.03
```

to:

```text
y = -0.07
```

without evaluating exactly at zero.

Therefore we should distinguish:

```text
MODEL SEMANTICS
    "event occurs when guard becomes true"

EXECUTION STRATEGY
    "how the runtime locates that event"
```

This distinction is well established in hybrid-system work; event detection/root localization is an execution concern layered over continuous dynamics.

So the DSL does **not** need:

```text
root_find(...)
```

inside the model.

The runtime does.

---

# 6. Stochastic behavior

We should refine:

```text
Distribution
RandomSource
StochasticProcess
```

into distinct concepts.

```text
Distribution
    mathematical probability object

RandomSource
    reproducible source of random values

StochasticProcess
    behavior whose evolution depends on randomness

RandomEvent
    stochastic occurrence
```

Thus:

```text
λ
```

doesn't itself mean "random."

Instead:

```text
ExponentialDecay(λ)
```

could be a library-defined stochastic process.

The core only needs to understand the general machinery.

---

# 7. Refined behavior model

After these corrections:

```text
BEHAVIOR
│
├── FUNCTION
│
├── EQUATION
│
├── CONSTRAINT
│
├── RULE
│
├── EVENT
│
└── PROCESS
    │
    ├── CONTINUOUS
    ├── DISCRETE
    ├── ALGORITHMIC
    └── STOCHASTIC
```

And processes operate through:

```text
Evolution
├── target
├── contribution
├── condition
├── execution mode
└── combination semantics
```

This is a meaningful refinement of the core model rather than a syntax patch.

# Part B: Batch 2: Hard Cases

Now let's deliberately attack the refined model.

---

# 19 Collision of many objects

Consider particles moving in 2D.

```text
system Gas {

    collection particles : Particle

    process motion {

        for p in particles {

            contribute velocity to p.position
        }
    }

    event collision(a, b) {

        when touching(a, b)

        operation {
            resolve_collision(a, b)
        }
    }

    view scene {
        for p in particles {
            show p
        }
    }
}
```

This exposes something new.

`resolve_collision` may change:

```text
a.velocity
b.velocity
```

while the motion process continuously evolves positions.

That's fine.

But what if three particles collide simultaneously?

```text
A ↔ B
B ↔ C
A ↔ C
```

Now event ordering matters.

We cannot simply say:

```text
event 1
event 2
event 3
```

because different orders could produce different states.

### New runtime requirement

We need an explicit concept of:

```text
simultaneous event set
```

or a deterministic conflict-resolution policy.

This is not a physics primitive.

It belongs to runtime semantics.

### Result

```text
RUN-05:
Simultaneous events and conflicting state operations need defined semantics.
```

---

# 20 2D model → 3D representation

Suppose the model is:

```text
object particle {
    position : Point<3>
}
```

but the renderer is 2D.

```text
view screen {

    project particle.position
        using camera
}
```

This validates:

```text
Model Space ≠ Render Space
```

But it exposes a deeper requirement.

A projection may require:

```text
camera
projection transform
clipping
depth ordering
scale
```

Those belong to the representation/view system, not the model.

So:

```text
Point<3>
```

must never implicitly become:

```text
Point<2>
```

through ordinary type coercion.

Instead:

```text
Point<3>
    ↓
Projection
    ↓
Point<2>
```

### Verdict

**PASS**

# 21 Heat diffusion

Now a real field.

\[
\frac{\partial T}{\partial t}
=
\alpha\nabla^2T
\]

### DSL

```text
system Heat {

    domain space : Space<2>

    field temperature(x : Point<2>) : Temperature

    parameter α : Diffusivity

    process diffusion {

        equation:
            partial(temperature, t)
                =
            α * laplacian(temperature)
    }

    view field {
        color = temperature
    }

    view graph {
        plot temperature(probe.position)
    }
}
```

This is a very strong test.

The field is:

```text
Point<2> → Temperature
```

while its evolution involves a differential operator over the field.

### Important conclusion

The core doesn't need to understand:

```text
Laplacian
Heat
Temperature
Diffusion
```

Those can be mathematical/domain libraries.

The core needs:

```text
Field
Domain
Function
Derivative/evolution
```

### But runtime now needs spatial discretization.

For example:

```text
finite difference
finite element
spectral
...
```

Again:

```text
MODEL
    ∂T/∂t = α∇²T

COMPUTATION
    discretization + solver
```

must remain separate.

---

# 22 Wave propagation

\[
\frac{\partial^2u}{\partial t^2}
=
c^2\nabla^2u
\]

This introduces a second derivative.

```text
process wave {

    equation:
        partial²(u, t)
            =
        c² * laplacian(u)
}
```

The core needs no new "wave" primitive.

But it does need sufficiently general differential-expression semantics.

### Result

**PASS**

The mathematical layer is general enough.

---

# 23 Cellular automaton

Now something radically different.

```text
system Life {

    domain grid : Grid<2>

    state cells : Collection<Cell>

    process generation {

        for cell in cells {

            next[cell] =
                rule(cell, neighbors(cell))
        }

        commit next
    }

    view grid {
        show cells
    }
}
```

The important thing is that this isn't continuous mathematics.

It's:

```text
state
→ discrete transformation
→ new state
```

This validates the distinction between:

```text
continuous process
```

and:

```text
discrete process
```

### But a subtle issue appears

We used:

```text
next
```

rather than immediately mutating:

```text
cells
```

because the entire generation should usually be computed from the old state.

That means the language/runtime needs a notion of:

```text
snapshot
→ evaluate
→ commit
```

for certain processes.

This connects directly to the transactional ideas already present in interaction.

### New runtime requirement

```text
RUN-06:
Processes may require read-from-old-state / write-to-new-state semantics.
```

---

# 24 Dynamic graph topology

Consider a network whose edges appear and disappear.

```text
event connect(a, b) {

    when compatible(a, b)

    operation {
        connect(a, b)
    }
}

event disconnect(edge) {

    when failure(edge)

    operation {
        disconnect(edge)
    }
}
```

This validates dynamic topology.

But now a dependency might disappear while another process is evaluating it.

So the dependency graph itself is dynamic.

That confirms our previous model:

```text
dependency graph
```

cannot be assumed static.

It must be capable of invalidation/reconstruction.

### Verdict

**PASS**

---

# 25 Particle spawning/destruction

A particle simulation may do:

```text
event split(particle) {

    when energy(particle) > threshold

    operation {

        destroy particle

        create child1
        create child2
    }
}
```

This exposes identity semantics.

`child1` and `child2` aren't merely new values.

They are new **entities with new identities**.

Thus:

```text
TYPE
≠
IDENTITY
≠
STATE
```

continues to hold.

# 26 Microscopic + macroscopic coupling

This is more interesting.

Suppose:

```text
MicroscopicModel
    molecules
```

produces:

```text
temperature
pressure
concentration
```

which feeds:

```text
MacroscopicModel
```

Conceptually:

```text
Molecules
   ↓
Observation/Aggregation
   ↓
Temperature
```

```text
    interface
```

**PASS**

# 27 Stochastic particle simulation

Now combine:

- particles,
- continuous movement,
- random events,
- creation/destruction.

```text
process movement {
    equation:
        d(p.position)/dt = p.velocity
}

event collision(p, wall) {

    when touches(p, wall)

    operation {
        reflect(p.velocity)
    }
}

event emission {

    according_to emission_distribution

    operation {
        create Particle
    }
}
```

This is now:

```text
continuous
+
discrete
+
stochastic
+
dynamic topology
```

The architecture still holds.

But runtime semantics are getting serious.

The runtime now needs an execution model capable of coordinating:

```text
continuous flows
discrete events
random events
state changes
entity lifecycle
```

This is exactly why hybrid systems are treated as a distinct semantic challenge in the literature.

# 28 External sensor input

Now leave simulation.

Imagine a temperature sensor:

```text
input temperature_sensor
    : Temperature
```

and:

```text
process control {

    output heater_power =
        controller(
            target_temperature,
            temperature_sensor
        )
}
```

The sensor isn't a model variable in the ordinary sense.

It's an **external input source**.

So the runtime pipeline is:

```text
external world
      ↓
input adapter
      ↓
typed value
      ↓
model
```

This validates our previous distinction:

```text
External Input
≠
Interaction
```

A sensor can affect the model without being a human interaction.

# 29 Missing sensor

What happens if the sensor disconnects?

We previously identified:

```text
absent
unknown
unavailable
pending
invalid
```

as distinct states.

Here:

```text
temperature_sensor = unavailable
```

is clearly different from:

```text
temperature = invalid
```

and different from:

```text
temperature = 0°C
```

So the type/status model survives.

### Result

# 30 Invalid state

Suppose:

```text
constraint mass > 0
```

and interaction tries:

```text
mass = -2 kg
```

The correct result is not:

```text
runtime crash
```

It is:

```text
operation rejected
reason:
    constraint violation
```

So:

```text
Operation
    ↓
Validation
    ↓
reject
```

without corrupting the state.

This validates transactional interaction semantics.

# 31 Numerical failure

Now suppose:

```text
equation:
    dx/dt = x²
```

and the numerical solution diverges.

The equation itself is not necessarily invalid.

The runtime may report:

```text
computation status:
    unstable
```

or:

```text
solver status:
    failed
```

while the semantic model remains valid.

This confirms:

```text
Equation invalidity
≠
solver failure
≠
runtime failure
```

# 32 Non-invertible projection

Suppose:

```text
temperature → color
```

The projection is:

```text
Temperature
     ↓
Color
```

Many temperatures could map to similar colors.

So this is not invertible.

If the user clicks the color:

```text
color → temperature
```

the system must **not infer a temperature automatically**.

Instead, an explicit interaction mapping might say:

```text
on drag temperature_slider {
    set temperature = slider.value
}
```

This validates:

```text
Projection
≠
Interaction mapping
```

and:

```text
non-invertible projection
≠
non-interactive representation
```

# 33 Many-to-one projection

```text
Particles

   ↓
```

# 34 One-to-many projection

One semantic object can produce multiple representations.

For example:

```text

 ↓
├── visual circle
├── label
├── velocity arrow
├── trajectory
└── measurement readout
```

Therefore:

```text
one model object
→
many representation elements
```

is equally legitimate.

This is already consistent with our projection model.

# 35 Constrained direct manipulation

Suppose a point is constrained to a circle.

```text
constraint:
    distance(A, origin) = radius
```

The user drags A.

Naively:

```text
mouse position → A.position
```

would violate the constraint.

Instead:

```text
mouse
 ↓
proposed position
 ↓
constraint projection
 ↓
valid position
 ↓
commit
```

This is an important refinement.

The interaction system should distinguish:

```text
raw proposed value
```

from:

```text
validated committed value
```

We already had proposed/committed state.

Now we know it is not merely convenient: it is essential for constrained manipulation.

Each subsystem can have its own:


```text

```

```text

```


```text

                      │
             ┌────────┼────────┐
```
