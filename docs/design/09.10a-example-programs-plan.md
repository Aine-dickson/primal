# 09.10 Example Programs

## 1. Purpose

We now have:

```text
09.1 Language Requirements
09.2 Construct Inventory
09.3 Syntax Options
09.4 Semantic Mapping
09.5 Type System
09.5b Type-System Revalidation
09.6 Scoping / Binding
09.7 Composition
09.8 Error Model
09.9 Extension Model
```

So 09.10 asks:

> **Can a programmer actually express the cases from the original test catalogue using the proposed language?**

And more importantly:

> **Where does the language become awkward, ambiguous, excessively verbose, or impossible?**

We should *not* modify the core just because a syntax looks ugly. First determine whether the problem is:

1. syntax,
2. semantic mapping,
3. type system,
4. scoping/binding,
5. composition,
6. runtime semantics,
7. projection,
8. interaction,
9. or a genuinely missing primitive.

# 2. Example-program test strategy

Rather than writing 30 unrelated examples, let's create **families of progressively harder programs**.

```text
LEVEL 1 Pure mathematics
LEVEL 2 Static structures
LEVEL 3 Simple dynamics
LEVEL 4 Continuous simulation
LEVEL 5 Discrete/event systems
LEVEL 6 Stochastic systems
LEVEL 7 Fields
LEVEL 8 Collections / dynamic topology
LEVEL 9 Coupled systems
LEVEL 10 Multiple representations
LEVEL 11 Interaction
LEVEL 12 Experiments
LEVEL 13 Education
LEVEL 14 Composition
LEVEL 15 Domain extensions
LEVEL 16 Hybrid / pathological cases
```

The important thing is that **we don't optimize the examples for the DSL**.

If a case is naturally ugly, we let it be ugly.

That's how we'll discover what the language actually needs.

# 3. Level 1 Pure mathematics

Start with the simplest possible case.

## Example 1: Function plot

Concept:

\[
f(x)=x^2
\]

Desired output:

- define function
- evaluate it
- plot it
- perhaps allow the user to change the domain

Conceptual DSL:

```text
system Quadratic {

    function f(x : Real) : Real =
        x²

    domain x = [-5, 5]

    view graph {
        plot f(x)
        x_axis
        y_axis
    }
}
```

### What this tests

```text
Function
Domain
Expression
Numeric types
Projection
View
```

No simulation is involved.

That is important.

The system must not require:

```text
process
time
state evolution
```

just to draw a mathematical function.

# 4. Example 2 Parametric curve

\[
x(t)=\cos(t)
\]

\[
y(t)=\sin(t)
\]

```text
system Circle {

    function position(t : Real) : Point<2> =
        (cos(t), sin(t))

    domain t = [0, 2π]

    view graph {
        plot position(t)
    }
}
```

This immediately tests something interesting:

### Is `Point<2>` just a vector?

Our previous type-system work said **no**.

We need:

```text
Point + Vector → Point
Point - Point  → Vector
Vector + Vector → Vector
```

So this example becomes an early type-system test.

# 5. Example 3 Equation visualization

Suppose we want:

\[
x^2+y^2=1
\]

This isn't naturally a function `y=f(x)`.

```text
system UnitCircle {

    equation:
        x² + y² = 1

    domain:
        x = [-2, 2]
        y = [-2, 2]

    view graph {
        plot equation
    }
}
```

Now we discover a distinction:

```text
Function
Equation
```

cannot simply be collapsed syntactically.

The equation describes a **relationship**, while the function describes a **mapping**.

Good validation case.

# 6. Level 2 Static geometric model

## Example 4 Triangle

```text
system Triangle {

    object A : Point<2> = (0, 0)
    object B : Point<2> = (4, 0)
    object C : Point<2> = (2, 3)

    relation AB = segment(A, B)
    relation BC = segment(B, C)
    relation CA = segment(C, A)

    view geometry {
        show AB
        show BC
        show CA
        show A
        show B
        show C
    }
}
```

But this raises an important question.

Are `A`, `B`, and `C`:

```text
values
```

or:

```text
objects containing properties?
```

If they are simply points, perhaps:

```text
A = (0,0)
```

is enough.

If they need identity, interaction, annotations, constraints, etc., they may need object identity.

This is exactly the kind of distinction 09.10 should expose.

interaction construct_triangle {

# 8. Level 3 Simple dynamics

## Example 6 Projectile

Now we introduce actual state evolution.

```text
system Projectile {

    parameter g : Acceleration = 9.81 m/s²

    object ball {

        position : Point<2> = (0 m, 0 m)

        velocity : Vector<2> =
            (10 m/s, 15 m/s)

        mass : Mass = 1 kg
    }

    process motion {

        acceleration = (0, -g)

        evolve ball.velocity
            by acceleration

        evolve ball.position
            by ball.velocity
    }

    view scene {

        show ball
        show trajectory(ball.position)
    }
}
```

This example is deliberately problematic.

Because:

```text
evolve velocity by acceleration
evolve position by velocity
```

is not yet precise enough.

We need to know:

- continuous or discrete?
- what timestep?
- what integration method?
- when are values sampled?
- are the two updates simultaneous?
- does position use old or new velocity?

That means 09.10 is already feeding back into **06 Runtime Semantics**.

That's exactly what we want.

---

# 9. Example 7 Explicit differential equation

Alternative formulation:

\[
\frac{d\mathbf{x}}{dt}=\mathbf{v}
\]

\[
\frac{d\mathbf{v}}{dt}=\mathbf{a}
\]

```text
process motion {

    equation:
        d(ball.position) / dt = ball.velocity

    equation:
        d(ball.velocity) / dt = (0, -g)
}
```

This is much closer to the scientific model.

Then the runtime chooses:

```text
Euler
RK4
adaptive solver
...
```

without changing the model.

This tests one of our major invariants:

> **Equation ≠ Solver**

---

# 10. Example 8 Pendulum

A more difficult continuous system:

\[
\frac{d\theta}{dt}=\omega
\]

\[
\frac{d\omega}{dt}
=-\frac{g}{L}\sin\theta
\]

```text
system Pendulum {

    parameter g = 9.81 m/s²
    parameter L = 1 m

    state {
        θ : Angle = 30°
        ω : AngularVelocity = 0 rad/s
    }

    process motion {

        equation:
            d(θ) / dt = ω

        equation:
            d(ω) / dt =
                -(g / L) * sin(θ)
    }
}
```

This exposes:

- units,
- dimensions,
- derivatives,
- state variables,
- parameters,
- continuous evolution.

---

# 11. Level 4 Events

## Example 9 Bouncing ball

Now continuous dynamics meet discrete events.

```text
process motion {
    equation:
        d(position) / dt = velocity

    equation:
        d(velocity) / dt = gravity
}

event ground_collision
    when ball.position.y <= 0
{
    ball.position.y = 0
    ball.velocity.y = -restitution * ball.velocity.y
}
```

Now we have a hybrid system:

```text
continuous evolution
        +
discrete event
```

This is one of the most important validation cases.

---

# 12. Level 5 Stochastic systems

## Example 10 Radioactive decay

We don't want to fake stochasticity by merely adding a random number to a deterministic equation.

A nucleus has a probabilistic decay process.

```text
system RadioactiveSample {

    parameter λ : Rate = 0.1 / s

    collection nuclei : Nucleus = create 1000

    process decay {

        for nucleus in nuclei {

            event decay
                probability = λ * dt
                when decay
                {
                    destroy nucleus
                }
        }
    }

    observation remaining =
        count(nuclei)

    view graph {
        plot remaining over time
    }
}
```

This immediately tests several abstractions:

```text
Collection
Dynamic destruction
Probability
Random source
Events
Observation
Data
```

And it forces us to define how:

```text
probability
```

interacts with:

```text
time step
```

which belongs partly to runtime semantics.

---

# 13. Example 11 Decay chain

Now:

```text
A → B → C
```

where B itself decays.

```text
type Nucleus {
    species : Species
}

event decay(nucleus : Nucleus) {

    match nucleus.species {

        A →
            nucleus.species = B

        B →
            nucleus.species = C

        C →
            destroy nucleus
    }
}
```

This tests:

- nominal domain types,
- variant/sum types,
- mutation,
- event payloads,
- dynamic state,
- pattern matching.

It also tests whether the language needs a general `match` construct.

---

# 14. Level 6 Chemistry

## Example 12 Chemical reaction

Consider:

\[
A+B\rightarrow C
\]

A simple stochastic molecular simulation:

```text
system Reaction {

    collection molecules : Molecule

    event reaction(a, b)
        when near(a, b)
        and a.species == A
        and b.species == B
    {
        destroy a
        destroy b

        create Molecule {
            species = C
        }
    }
}
```

Now we have:

```text
dynamic topology
spatial relation
conditions
creation
destruction
domain extension types
```

Again, no `Reaction` primitive is required in the core.

Chemistry can provide it.

---

# 15. Example 13 Reaction kinetics

But chemistry also needs the **macroscopic** formulation:

\[
\frac{d[A]}{dt}=-k[A][B]
\]

```text
process kinetics {

    equation:
        d(A) / dt = -k * A * B

    equation:
        d(B) / dt = -k * A * B

    equation:
        d(C) / dt = k * A * B
}
```

Notice something important.

The same domain concept can have two models:

```text
microscopic molecular model
        ↓
individual molecules

macroscopic kinetic model
        ↓
concentrations
```

Our architecture already supports this.

# 16. Level 7 Fields

## Example 14 Electric field

For point charges:

\[
\mathbf E(\mathbf x)
=
\sum_i
kq_i
\frac{\mathbf x-\mathbf x_i}
{|\mathbf x-\mathbf x_i|^3}
\]

Conceptually:

```text
system ElectrostaticField {

    collection charges : Charge

    field E(position : Point<2>) : Vector<2> {

        sum over charges:
            coulomb_field(charge, position)
    }

    view field {
        arrows = E
    }

    view scalar {
        magnitude = |E|
        color = magnitude
    }
}
```

This tests:

```text
Field
Collection
Function
Aggregation
Vector math
Multiple projections
```

It also demonstrates why:

> **Field is naturally a function over a domain.**

So the earlier decision to treat fields as a specialization/composition of functions + domains looks justified.

# 17. Level 8 Graph algorithms

## Example 15 BFS

Now leave physics completely.

```text
type Node {
    value : Text
}

relation Edge {
    from : Node
    to   : Node
}

collection graph.nodes : Node
collection graph.edges : Edge

process bfs(start : Node) {

    collection frontier = [start]

    while frontier not empty {

        node = pop(frontier)

        node.visited = true

        for edge in outgoing(node) {

            if not edge.to.visited {
                push(frontier, edge.to)
            }
        }
    }
}
```

This is useful because it asks:

> Does our supposedly scientific DSL actually support computer-science models?

It needs:

- collections,
- mutable state,
- relations,
- iteration,
- predicates,
- control flow,
- algorithms.

# 18. Example 16 Sorting visualization

```text
collection values : Sequence<Real> =
    [7, 2, 9, 1, 5, 3]

process insertion_sort {

    for i in 1 .. length(values) {

        key = values[i]

        j = i - 1

        while j >= 0 and values[j] > key {

            values[j + 1] = values[j]
            j = j - 1
        }

        values[j + 1] = key
    }
}
```

Then:

```text
view bars {
    for value in values {
        show value as bar
    }
}
```

Now we discover whether the DSL can express **algorithmic state evolution** without pretending everything is a physical simulation.

# 19. Level 9 Hybrid systems

## Example 17 Predator/prey

\[
\frac{dx}{dt} = ax-bxy
\]

\[
\frac{dy}{dt} = -cy+dxy
\]

```text
system PredatorPrey {

    state {
        prey : Real = 100
        predators : Real = 10
    }

    parameters {
        birth_rate = 1.0
        predation_rate = 0.01
        death_rate = 0.5
        reproduction_rate = 0.005
    }

    process ecology {

        equation:
            d(prey)/dt =
                birth_rate * prey
                - predation_rate * prey * predators

        equation:
            d(predators)/dt =
                -death_rate * predators
                + reproduction_rate * prey * predators
    }

    view graph {
        plot prey
        plot predators
    }
}
```

This validates that a model does not need physical geometry at all.

# 20. Level 10 Multiple synchronized representations

This is where the architecture becomes more interesting.

Take the projectile again.

We might simultaneously show:

```text
             ┌── scene
             │
Projectile ──┼── velocity graph
             │
             ├── energy graph
             │
             ├── equation
             │
             └── data table
```

DSL concept:

```text
view scene {
    show ball
    show trajectory
}

view velocity_graph {
    plot ball.velocity
}

view energy_graph {
    plot kinetic_energy(ball)
    plot potential_energy(ball)
}

view equations {
    show motion_equations
}

view data {
    show observations
}
```

The critical property:

**These views do not own separate copies of the projectile.**

They all observe the same model.

```text
                 MODEL
                   │
        ┌──────────┼───────────┐
        ↓          ↓           ↓
     Scene      Graph       Equation
        ↓          ↓           ↓
       View       View        View
```

This is a major test of the projection model.

# 21. Level 11 Direct manipulation

Now:

> Drag the projectile's initial velocity vector.

```text
interaction adjust_velocity {

    on drag(ball.velocity_handle) {

        proposed ball.velocity =
            inverse_project(mouse.position)

        preview
    }

    on release {

        commit
    }
}
```

The semantic chain becomes:

```text
mouse
 ↓
screen position
 ↓
representation
 ↓
inverse projection
 ↓
ball.velocity
 ↓
model operation
 ↓
new simulation
```

This tests one of our most important conclusions:

> A projection does not have to be invertible globally for interaction to work.

The interaction explicitly defines the mapping.

# 22. Level 12 Experiment

Now we don't merely run a simulation.

We want:

> "Try different gravitational accelerations and compare the trajectories."

```text
experiment gravity_test {

    model Projectile

    parameters {
        g = [3, 9.81, 15] m/s²
    }

    run for 10 s

    observe {
        trajectory
        maximum_height
        range
    }

    view comparison {
        plot trajectory
        plot maximum_height
        plot range
    }
}
```

This tests:

```text
Experiment
Parameter binding
Repeated execution
Observation
Dataset
Comparison
```

And it demonstrates why an experiment is **not simply another simulation**.

# 23. Level 13 Branching

Suppose the user pauses the projectile at `t = 2s`.

Then:

```text
branch A → g = 9.81
branch B → g = 3.0
branch C → g = 20
```

The runtime should conceptually have:

```text
Snapshot S
   │
   ├── Experiment A
   ├── Experiment B
   └── Experiment C
```

No model-level inheritance is required.

# 24. Level 14 Educational layer

Now put an activity around the simulation.

```text
activity projectile_lesson {

    simulation Projectile

    instruction:
        "Predict which trajectory reaches the highest point."

    prediction {
        options = [
            "g = 3 m/s²",
            "g = 9.81 m/s²",
            "g = 20 m/s²"
        ]
    }

    experiment {
        allow parameter g
    }

    observation {
        measure maximum_height
    }

    assessment {
        compare prediction with result
    }

```

This is important architecturally.

Education does **not** become part of the scientific model.

Instead:

```text
Scientific Model
      ↓
Experiment
      ↓
Observation
      ↓
Educational Activity
```

# 25. Level 15 Composition

Now something more serious.

Suppose we model a vehicle:

```text
Vehicle
├── Battery
├── Motor
├── Controller
├── Wheels
└── Environment
```

But none of these need to be special core constructs.

```text
component Battery {
    state {
        charge : Energy
    }

    process discharge {
        ...
    }
}

component Motor {
    input voltage : Voltage
    output torque : Torque
}

component Controller {
    input speed : AngularVelocity
    output voltage : Voltage
}
```

Then:

```text
system ElectricVehicle {

    battery : Battery
    controller : Controller
    motor : Motor

    connect
        controller.voltage
        → motor.voltage

    connect
        motor.power
        → battery.power
}
```

This tests whether our composition model is actually usable.

# 26. Level 16 Domain extension

Finally, we test the most important extension requirement.

Suppose the physics library defines:

```text
type Projectile {
    position : Point<2>
    velocity : Vector<2>
    mass : Mass
}

capability Positioned {
    position : Point<2>
}
```

and:

```text
Projectile provides Positioned
```

Then generic geometry can say:

```text
function distance<A : Positioned, B : Positioned>(
    a : A,
    b : B
) : Length =
    magnitude(a.position - b.position)
```

Now chemistry could define:

```text
type Atom {
    position : Point<3>
    element : Element
}

Atom provides Positioned
```

and the same:

```text
distance(atom1, atom2)
```

works.

The geometry library does not know what an atom is.

That is precisely what our **nominal type + capability** model was intended to achieve.

# 27. The really important stress cases

The examples above are still relatively friendly.

We should deliberately include cases that try to break the model.

### A. No spatial representation

```text
f(x) = x²
```

Must work.

### B. Spatial model with no simulation

Static geometry must work.

### C. Simulation with no visual representation

A computation/data experiment must work.

### D. Representation with no underlying simulation

Explanatory animation must work.

### E. Continuous + discrete

Bouncing ball.

### F. Deterministic + stochastic

Chemical reaction / radioactive decay.

### G. Dynamic topology

Particles being created/destroyed.

### H. Multiple solvers

Two coupled subsystems using different numerical methods.

### I. Multiple time scales

Fast microscopic process coupled to slow macroscopic process.

### J. Non-invertible projection

Temperature → color.

Then attempting:

```text
drag color → temperature
```

must **not** magically invent an inverse.

### K. Many-to-one projection

Thousands of particles → one histogram bar.

### L. One-to-many projection

One semantic object → several visual elements.

### M. External input

Sensor/network/file/microcontroller updates model state.

### N. Missing input

Sensor unavailable.

Should become:

```text
unavailable
```

not:

```text
0
```

and not necessarily:

```text runtime crash
```

### O. Invalid state

Negative mass.

Should be distinguishable from an engine crash.

### P. Numerical failure

Equation valid, solver fails to converge.

### Q. User cancellation

A partially constructed triangle should disappear without corrupting the model.

### R. Branching

Same state → multiple experiments.

### S. Replay

Same initial state + parameters + RNG + interactions → reproducible run.

### T. Nested systems

A vehicle containing a motor containing electromagnetic submodels.

# 28. What we should record for every example

I suggest we don't merely write programs.

For each program, create a small validation record:

| Field | Purpose |
|---|---|
| Case | What are we expressing? |
| DSL | Actual program |
| Constructs used | What language features are required? |
| Semantic lowering | What generalized-model elements result? |
| Runtime requirements | What execution semantics are needed? |
| Projection requirements | What must be visualized? |
| Interaction requirements | What can the user do? |
| Type-system pressure | What types/capabilities are tested? |
| Composition pressure | Does it compose with other models? |
| Failure cases | What can go wrong? |
| Awkwardness | What feels unnatural? |
| Missing capability | Genuine gap, if any |

This prevents us from saying:

> "The syntax looks nice, therefore the model works."

# 29. First milestone

I recommend we **don't attempt all 30+ examples at once**.

Let's establish the first validation batch:

```text
01  f(x) = x²
02  Parametric circle
03  Implicit equation
04  Static triangle
05  Projectile
06  Pendulum
07  Bouncing ball
08  Radioactive decay
09  Chemical reaction
10  Electric field
11  BFS
12  Sorting visualization
13  Predator-prey
14  Multi-view projectile
15  Interactive projectile
16  Experiment / branching
17  Composed electric vehicle
18  User-defined domain extension
```

That gives us coverage across almost every major abstraction we've developed.

And I think we should make the next step particularly strict:

> **For each example, write the DSL first without adding any new language construct. Then attempt the semantic lowering. If something fails, determine whether the failure is syntax, semantics, type system, runtime, projection, interaction, or a genuinely missing core capability.**

That gives us a clean transition from **09.10 Example Programs → 09.11 DSL Validation**, rather than letting the examples quietly redesign the language as we go.
