# 09.11 DSL Validation

## Purpose

The purpose of this stage is to determine whether the proposed DSL is:

1. **Expressive enough** for the complete test-case space.
2. **Semantically coherent**, constructs mean one thing rather than changing meaning unpredictably by context.
3. **Type-safe enough** to prevent meaningless operations while remaining extensible.
4. **Composable** across models, subsystems, domains and libraries.
5. **Executable** without forcing runtime implementation details into the language.
6. **Extensible** without requiring compiler modifications for every scientific domain.
7. **Small enough** that the core language is not unnecessarily large.

This is therefore a **validation stage, not a feature-adding stage**.

The key question is:

> Can the language express the required cases naturally while preserving the distinctions established by the generalized model?

---

# 09.11.1 Syntax Validation

## 1. Syntax must expose semantic intent

The DSL should not force the author to express every internal runtime mechanism.

For example, an author should be able to write something conceptually like:

```text
object ball {
    position = (0, 0)
    velocity = (10, 15)
}
```

without specifying:

- memory layout,
- dependency graph nodes,
- invalidation strategy,
- scheduler queues,
- renderer objects,
- GPU buffers,
- numerical integrator internals.

Those belong below the DSL.

---

## 2. Different relationships need distinguishable syntax

One major danger is allowing `=` to represent everything.

These are semantically different:

```text
position = (0, 0)
speed := magnitude(velocity)
F = m * a
temperature' = diffusion(temperature)
```

Conceptually:

| Form | Meaning |
|---|---|
| `=` | initialization/assignment depending on context |
| `:=` | definition/derivation |
| equation syntax | mathematical relationship |
| evolution syntax | state evolution |
| constraint syntax | admissible-state restriction |

The exact symbols are still open, but the semantic distinction must remain.

### Validation result

**PASS**, provided the parser/semantic analyzer does not collapse these into generic assignments.

---

## 3. Mathematical expressions must remain natural

A scientific DSL becomes unusable if ordinary mathematics requires excessive ceremony.

This should remain possible:

```text
f(x) := x² + 2x + 1
```

rather than requiring:

```text
function f(input x : Real) returns Real {
    expression ...
}
```

The latter may exist as an expanded form, but the former should be legal surface syntax.

### Validation result

**PASS.**

---

## 4. Structural declarations should remain declarative

Models should read approximately like models:

```text
object ball {
    position = (0, 0)
    velocity = (10, 15)
    mass = 1 kg
}
```

rather than resembling imperative object construction code.

### Validation result

**PASS.**

---

## 5. Behavior needs more than one syntax form

The examples have already demonstrated three fundamentally different process styles.

### Mathematical evolution

```text
process motion {
    acceleration = (0, -g)
}
```

### Reactive behavior

```text
when ball.position.y <= 0 {
    ball.velocity.y := -ball.velocity.y
}
```

### Algorithmic behavior

```text
process bfs(graph, start) {
    queue := [start]

    while queue is not empty {
        ...
    }
}
```

Trying to force all three into a single syntax would make at least one of them unnatural.

Therefore:

> `process` is a semantic category, but its body may contain different execution forms.

### Validation result

**PASS**, with a runtime requirement that process execution mode be explicit or inferable.

---

## 6. Presentation syntax should remain separate

The model should not need to know how it is rendered.

For example:

```text
view scene {
    show ball as circle
    show ball.position
    show trajectory
}
```

does not redefine the ball.

It creates projections and representations of the ball.

This preserves:

```text
MODEL ≠ REPRESENTATION
```

### Validation result

**PASS.**

---

## 7. Interaction syntax should identify semantic targets

For example:

```text
interaction drag(ball.position)
```

should mean:

```text
input
→ intent = drag
→ target = ball.position
→ operation = modify
```

It should not mean "drag whatever graphical object happens to be underneath the mouse."

### Validation result

**PASS**, provided visual hit-testing resolves to a semantic binding.

---

## 8. Syntax should support explicitness when inference becomes ambiguous

The DSL should allow:

```text
show temperature as color
```

but also allow an explicit projection:

```text
project temperature
    to color
    using palette(...)
```

Likewise:

```text
distance(a, b)
```

may infer a spatial capability, while explicit typing remains possible where necessary.

### Validation result

**PASS.**

---

## 9. Syntax validation conclusion

The proposed hybrid syntax survives.

The strongest direction remains:

```text
MATHEMATICS
    → mathematical syntax

MODEL
    → declarative syntax

BEHAVIOR
    → process/rule/event syntax

PRESENTATION
    → declarative projection/view syntax

INTERACTION
    → event/operation syntax
```

The syntax should therefore **not attempt to make the entire language uniformly declarative or uniformly imperative**.

---

# 09.11.2 Semantic Validation

The next question is much more important:

> Does every meaningful DSL construct map cleanly into the generalized semantic model?

---

## 1. Object declaration

```text
object ball {
    position = (0, 0)
    mass = 1 kg
}
```

Maps to:

```text
Object
├── identity
├── property: position
└── property: mass
```

### PASS

---

## 2. Standalone variable

```text
time = 0 s
```

Maps to:

```text
State
└── variable time
```

No object is required.

### PASS

This confirms that not everything should be forced into an object.

---

## 3. Derived value

```text
speed := magnitude(ball.velocity)
```

Maps to:

```text
Expression
    ↓
Dependency
    ↓
Derived value
```

No mutable state is created.

### PASS

---

## 4. Function

```text
f(x) := x²
```

Maps to:

```text
Function
Domain: Real
Codomain: Real
Mapping: x²
```

### PASS

---

## 5. Equation

```text
F = m * a
```

Maps to a mathematical relationship.

It does **not automatically mean**:

```text
a := F / m
```

unless the author explicitly asks for such a derivation.

This distinction is important because equations may be:

- displayed,
- solved,
- used as constraints,
- used as evolution laws,
- used as mathematical relationships.

### PASS

---

## 6. Constraint

```text
mass > 0 kg
```

maps to:

```text
Constraint
    ↓
valid-state predicate
```

It does not necessarily create an evolution rule.

### PASS

---

## 7. Rule

```text
when temperature > 100 °C {
    state := "boiling"
}
```

maps to:

```text
Predicate
    ↓
Event/trigger
    ↓
Operation
```

### PASS

---

## 8. Process

A process such as:

```text
dx/dt = v
```

maps to continuous evolution.

A cellular automaton process maps to discrete evolution.

A sorting algorithm maps to algorithmic execution.

A Monte Carlo process maps to stochastic execution.

Therefore `Process` is intentionally broad.

### PASS

But this produces an important requirement:

> Process semantics must explicitly distinguish execution mode.

---

## 9. Observation

```text
measure ball.velocity
```

maps to:

```text
State
 ↓
Observation
 ↓
Data
```

It does not mutate the model.

### PASS

---

## 10. Projection

```text
show ball.position
```

maps to:

```text
Model value
 ↓
Projection
 ↓
Representation
 ↓
View
```

### PASS

---

## 11. Interaction

```text
drag(ball.position)
```

maps to:

```text
Input
 ↓
Intent
 ↓
Target
 ↓
Operation
 ↓
State change
```

### PASS

---

## 12. Animation

```text
animate label.opacity from 0 to 1 over 1 s
```

belongs to presentation state.

It does not necessarily modify semantic model state.

### PASS

---

## Semantic validation conclusion

The semantic mapping remains coherent.

The most important invariant is:

```text
DSL construct
    ↓
semantic meaning
    ↓
generalized model
```

rather than:

```text
DSL construct
    ↓
special runtime feature
```

That distinction keeps the language extensible.

# 09.11.3 Type Validation

The type system now faces its hardest test:

> Can it reject meaningless scientific operations without knowing every scientific domain?

---

## 1. Ordinary mathematical typing

```text
x : Real
y : Real

x + y
```

valid.

```text
x : Real
flag : Boolean

x + flag
```

invalid.

### PASS

---

## 2. Dimensional typing

```text
distance = 10 m
time = 2 s

velocity = distance / time
```

produces:

```text
Quantity<Length / Time>
```

while:

```text
distance + time
```

is invalid.

### PASS

This is essential for scientific software.

---

## 3. Point/vector semantics

The system must distinguish:

```text
Point
Vector
```

so:

```text
point + vector → point
point - point → vector
vector + vector → vector
```

while:

```text
point + point
```

is not automatically valid.

### PASS

---

## 4. Generic mathematical structures

The type system can express:

```text
Vector<2, Real>
Vector<3, Real>
Matrix<3, 3, Real>
```

without creating:

```text
Vector2
Vector3
Matrix3x3
```

as unrelated core types.

### PASS

---

## 5. Domain types

A physics library can define:

```text
type Projectile
```

A chemistry library can define:

```text
type Molecule
```

A graph library can define:

```text
type GraphNode
```

The core compiler does not need special knowledge of these.

### PASS

---

## 6. Capability typing

Suppose:

```text
interface Positioned {
    position : Point<2>
}
```

Then:

```text
function distance<A : Positioned, B : Positioned>(a, b)
```

can operate on:

```text
Projectile
Particle
Atom
Vehicle
GraphNode
```

provided each supplies the capability.

This is a major extension-model validation.

### PASS

---

## 7. Constraint typing

Instead of creating:

```text
PositiveReal
PositiveMass
NonZeroReal
ValidProbability
```

the system can express constraints:

```text
mass : Quantity<Mass>
constraint mass > 0 kg
```

### PASS

---

## 8. Sum types

Events and other alternatives can use variants:

```text
Event =
    Collision
  | Decay
  | Birth
  | Death
  | UserInput
```

This is useful for algorithms and event-driven models.

### PASS

---

## 9. Optional/unknown values

Scientific systems need to distinguish:

```text
absent
unknown
unavailable
pending
invalid
```

These must not all become `null`.

For example:

```text
sensor.temperature
```

may be unavailable because the sensor disconnected.

That is not the same as:

```text
temperature = NaN
```

### PASS

---

## 10. Type validation conclusion

The type model survives the test.

The strongest formulation remains:

```text
NOMINAL TYPES
        +
STRUCTURED TYPES
        +
CAPABILITIES
        +
GENERICS
        +
CONSTRAINTS
```

This gives domain extensibility without requiring domain-specific compiler primitives.

---

# 09.11.4 Composition Validation

Now test whether independently authored models can actually become larger systems.

---

## 1. Simple composition

```text
motor
battery
controller
wheel
```

can each be independently defined and composed.

The system should expose only required interfaces.

### PASS

---

## 2. Functional composition

```text
position
    ↓
velocity
    ↓
acceleration
```

is straightforward dependency composition.

### PASS

---

## 3. Shared-state composition

Two subsystems may intentionally access the same state.

But the language must not silently merge their state.

Ownership/exposure must remain explicit.

### PASS

---

## 4. Event composition

```text
Collision
    ↓
damage handler
    ↓
sound effect
    ↓
statistics recorder
```

One event can feed multiple consumers.

### PASS

---

## 5. Feedback composition

```text
sensor
 ↓
controller
 ↓
motor
 ↓
physical system
 ↓
sensor
```

creates a cycle.

Cycles are therefore not automatically errors.

The runtime determines whether the cycle is:

- algebraic,
- discrete,
- continuous,
- delayed,
- unstable,
- impossible to solve.

### PASS

---

## 6. Dynamic composition

The system must allow:

```text
create particle
destroy particle
connect node
disconnect node
merge objects
split objects
```

This is necessary for:

- particle systems,
- chemical reactions,
- biological populations,
- dynamic graphs,
- simulations with births/deaths.

### PASS

---

## 7. Multiple behavioral contributions

This is the first major composition boundary.

Suppose:

```text
gravity → ball.velocity
wind → ball.velocity
collision → ball.velocity
controller → ball.velocity
```

The runtime cannot simply choose:

```text
last writer wins
```

Nor can it universally assume:

```text
add everything
```

Instead:

```text
Evolution Target
        ↓
Contributions
        ↓
Combination semantics
        ↓
Proposed state
```

For example:

```text
velocity
    ← gravity contribution
    ← wind contribution
    ← collision operation
```

The combination mechanism depends on the target's semantics.

### Required rule

> Multiple contributions to an evolution target must have explicit combination semantics.

### PASS WITH RUNTIME REQUIREMENT

---

## 8. Composition conclusion

Composition remains viable, but it confirms that **evolution semantics cannot be reduced to ordinary assignment**.

This is one of the most important findings of DSL validation.

---

# 09.11.5 Runtime Boundary Validation

The DSL should define *what the model means* while allowing different execution strategies.

---

## 1. Continuous systems

Example:

```text
dx/dt = v
dv/dt = -g
```

The DSL defines the model.

The runtime may choose:

```text
Euler
RK4
adaptive integration
GPU integration
symbolic solution
```

without changing the model.

### PASS

---

## 2. Event boundaries

Suppose:

```text
when x = 0 {
    velocity := -velocity
}
```

The runtime must determine when the condition becomes true.

A naive fixed timestep may jump from:

```text
x = 0.02
```

to:

```text
x = -0.04
```

without landing exactly on the boundary.

Therefore event semantics require:

```text
continuous evolution
        ↓
guard detection
        ↓
event boundary
        ↓
event execution
        ↓
continued evolution
```

Possible runtime strategies include:

- substepping,
- interpolation,
- root finding,
- event localization.

These are runtime strategies, not new DSL concepts.

### PASS WITH RUNTIME REQUIREMENT

---

## 3. Stochastic systems

The model must distinguish:

```text
Distribution
RandomSource
StochasticProcess
RandomEvent
```

For example:

```text
P(decay during dt) = λN dt
```

is not itself a random-number generator.

A random source provides controlled randomness.

Reproducibility requires:

```text
model
+
initial state
+
parameters
+
random seed/source state
+
execution configuration
```

### PASS WITH RUNTIME REQUIREMENT

---

## 4. Algorithmic processes

Sorting and graph traversal expose a different execution model.

Example:

```text
while queue not empty {
    node := pop(queue)
    ...
}
```

This requires ordered execution rather than differential evolution.

Therefore the runtime needs an algorithmic process mode.

### PASS

---

## 5. Old-state/new-state semantics

Cellular automata expose another requirement.

A rule may mean:

```text
new_cell_state
    =
function(neighbor states from old state)
```

It must not accidentally read partially updated cells.

Therefore the runtime needs a notion of:

```text
read state
    ↓
compute transitions
    ↓
commit new state
```

This is not a new domain concept.

It is an execution semantic.

### PASS WITH RUNTIME REQUIREMENT

---

## 6. Simultaneous events

Suppose two events happen at the same simulation instant.

The runtime needs defined semantics for:

- event ordering,
- priority,
- simultaneous execution,
- conflict resolution,
- cancellation,
- transactional commit.

Again, these are runtime semantics rather than additional domain primitives.

### PASS WITH RUNTIME REQUIREMENT

---

## 7. Numerical failure

The model may be valid while the numerical method fails.

For example:

```text
valid equation
        ↓
unstable numerical method
        ↓
numerical failure
```

Therefore:

```text
equation invalid
```

must not be inferred from:

```text
solver failed
```

### PASS

---

## 8. Runtime validation conclusion

The semantic DSL remains independent of execution strategy.

The runtime, however, must eventually define:

```text
PROCESS EXECUTION
EVOLUTION CONTRIBUTIONS
EVENT BOUNDARIES
EVENT ORDERING
CONFLICT RESOLUTION
RANDOMNESS
SNAPSHOTS
NUMERICAL APPROXIMATION
ALGORITHMIC EXECUTION
```

These are runtime obligations, not reasons to enlarge the semantic kernel.

---

# 09.11.7 Minimal-Kernel Revalidation

This is the most important test.

We now ask:

> After all the validation, which concepts are genuinely fundamental, and which are conveniences that could be built from others?

The purpose is to prevent the language from becoming a giant catalogue of scientific concepts.

---

# A. Candidate Core Concepts

Current candidate:

```text
SYSTEM
TYPE
VALUE
OBJECT
PROPERTY
COLLECTION
RELATION
DOMAIN
EXPRESSION
FUNCTION
EQUATION
CONSTRAINT
STATE
PROCESS
EVENT
OPERATION
OBSERVATION
DATA
PROJECTION
REPRESENTATION
VIEW
INTERACTION
```

This is already much smaller than the original inventory.

But we can reduce it further.

---

# B. Can PROPERTY be removed?

Consider:

```text
ball.position
```

A property is essentially a named binding associated with an object.

We already identified:

```text
Binding = name + meaning + value/definition + metadata
```

Therefore property may not need to be a separate semantic primitive.

It can become:

```text
Binding
    owner = ball
    name = position
    role = property
```

### Result

**PROPERTY can probably be removed as an independent kernel primitive.**

The surface language may still use `property`.

---

# C. Can PARAMETER be removed?

A parameter is essentially a binding with a particular role:

```text
g : Quantity<Acceleration>
role = parameter
```

Therefore:

```text
PARAMETER
```

does not need to be a distinct value type.

### Result

**Parameter should be a binding role/metadata, not a fundamental type.**

---

# D. Can VARIABLE be removed?

Similarly:

```text
velocity
```

is a binding whose value changes over time.

Therefore:

```text
variable
```

is a state/binding role.

### Result

**Variable does not need to be a fundamental type.**

---

# E. Can PREDICATE be removed?

A predicate is simply:

```text
Expression<Boolean>
```

Therefore:

```text
PREDICATE
```

does not need independent core status.

The DSL may still use the word `when`, but semantically it is an expression returning Boolean.

### Result

**Remove Predicate from the semantic kernel.**

---

# F. Can RULE be removed?

A rule:

```text
condition → operation
```

can be represented as:

```text
Expression<Boolean>
+
Event/trigger
+
Operation
```

Therefore Rule does not necessarily need to be fundamental.

The surface syntax can still provide:

```text
when condition {
    ...
}
```

### Result

**Rule can be syntactic sugar over existing semantics.**

---

# G. Can FIELD be removed?

A field is:

```text
F : Domain → Value
```

which is a function over a domain.

Therefore the core does not strictly require a separate Field type.

However, fields often have specialized computational semantics:

- sampling,
- interpolation,
- discretization,
- caching,
- spatial storage,
- derivatives.

The question is whether those are semantic identity or runtime optimization.

For the core semantic model:

```text
Field ≈ Function<Domain, Value>
```

is sufficient.

A domain/geometry library may provide a specialized `Field` abstraction.

### Result

**Field can be a library-level specialization of Function.**

This is a useful reduction.

---

# H. Can EVENT be removed?

An event is more difficult.

Events represent discrete occurrences and have:

- occurrence time,
- trigger condition,
- payload,
- ordering,
- scheduling,
- simultaneous-event semantics.

They are not simply ordinary functions.

They could theoretically be encoded using processes and predicates, but doing so would obscure a fundamental runtime semantic distinction.

### Result

**Keep Event.**

---

# I. Can PROCESS be removed?

A process represents state evolution.

It is fundamentally different from a function:

```text
Function:
input → output
```

versus:

```text
Process:
state → state'
```

It also has continuous, discrete, algorithmic and stochastic forms.

### Result

**Keep Process.**

---

# J. Can OPERATION be removed?

An operation represents an intended state-changing action:

```text
SET
MODIFY
CREATE
DESTROY
CONNECT
DISCONNECT
...
```

It is central to:

- interaction,
- events,
- processes,
- transactions,
- replay,
- undo,
- branching.

### Result

**Keep Operation.**

---

# K. Can OBSERVATION be removed?

Observation could technically be represented as a function:

```text
State → Data
```

But the system needs to distinguish:

```text
computation
```

from:

```text
measurement/observation
```

because observation has temporal, sampling, uncertainty, provenance and instrumentation semantics.

### Result

**Keep Observation.**

---

# L. Can PROJECTION be removed?

Projection is distinct from representation because:

```text
model meaning
        ↓
mapping
        ↓
representation
```

A projection may aggregate, filter, transform, encode or map coordinates.

Without it, model and representation become unnecessarily coupled.

### Result

**Keep Projection.**

---

# M. Can REPRESENTATION be removed?

Representation is the semantic/presentation result of a projection.

It may be:

- curve,
- diagram,
- color field,
- histogram,
- particle rendering,
- symbolic equation,
- table.

It is distinct from the actual View.

### Result

**Keep Representation.**

---

# N. Can VIEW be removed?

A representation could theoretically render directly.

But the system needs presentation state:

```text
camera
zoom
pan
layout
visibility
selection
viewport
```

This is not the model and not the representation itself.

### Result

**Keep View**, although the runtime may implement it differently for different output targets.

---

# O. Can INTERACTION be removed?

Interaction is:

```text
Input
→ interpretation
→ intent
→ target
→ operation
```

It is distinct from raw input and from operation.

Without this abstraction, the language would have difficulty expressing:

- drag,
- measurement,
- construction,
- selection,
- parameter control,
- direct manipulation,
- experiment interaction.

### Result

**Keep Interaction.**

---

# P. Can DATA be removed?

Data is the result of observations and analysis.

It could potentially be represented as collections of values.

However, datasets have additional semantics:

- axes,
- timestamps,
- units,
- dimensions,
- provenance,
- uncertainty,
- sampling.

Therefore it is useful as a semantic abstraction.

### Result

**Keep Data**, though simple data may be represented by ordinary collections.

---

# Q. Can EQUATION be removed?

An equation is mathematically representable as an expression involving equality:

```text
lhs = rhs
```

So at the deepest level:

```text
Equation
≈ Boolean relationship / equality constraint
```

But equations have special roles:

- mathematical relationship,
- solver input,
- displayed mathematics,
- continuous evolution law,
- constraint.

The semantic model must distinguish these roles.

The question is whether `Equation` needs to be a kernel object or can simply be:

```text
Expression
+
Equality relation
+
Role
```

This is plausible.

### Result

**Equation may be reducible at the deepest kernel level.**

However, keeping `Equation` as a semantic construct may make the scientific DSL dramatically clearer.

Therefore:

> Equation should remain a **first-class language construct**, while its lowest-level semantic representation may be reducible to expressions and relations.

This distinction avoids unnecessary runtime primitives without making the source language awkward.

---

# R. Can SYSTEM be removed?

Everything exists inside some system/context.

A system provides:

- scope,
- composition,
- state,
- behavior,
- context,
- interfaces.

It is therefore fundamental.

### Result

**Keep System.**

---

# S. Can TYPE be removed?

No.

The language needs:

- type checking,
- domain extension,
- generic constraints,
- capability satisfaction,
- dimensional structure,
- semantic identity.

### Result

**Keep Type.**

---

# T. Can OBJECT be removed?

Possibly an object is:

```text
identity + bindings
```

But stable identity is fundamental to:

- particles,
- nodes,
- entities,
- dynamic creation/destruction,
- relations,
- references,
- interaction targets.

Therefore the identity abstraction must remain.

### Result

**Keep Object/Entity identity**, although the surface keyword may eventually be `entity` or another name.

---

# U. Can COLLECTION be removed?

Collections are more than ordinary values because dynamic membership matters:

```text
create
destroy
filter
map
reduce
group
sort
sample
```

They are required for:

- particles,
- populations,
- graph nodes,
- molecules,
- data structures,
- algorithmic models.

### Result

**Keep Collection**, although some collection forms may be ordinary values.

---

# V. Can RELATION be removed?

No.

Relations are semantically distinct from geometry.

Examples:

```text
A bonded_to B
node_a connected_to node_b
prey hunted_by predator
vehicle connected_to battery
```

A visible line does not necessarily mean a semantic relation.

### Result

**Keep Relation.**

---

# W. Can DOMAIN be removed?

Domain is needed to express:

```text
x ∈ R
position ∈ Space2D
time ∈ [0,∞)
node ∈ Graph
```

Functions and fields depend on domains.

### Result

**Keep Domain.**

---

# X. Can STATE be removed?

This is perhaps the deepest abstraction.

Everything dynamic ultimately depends on:

```text
state
```

State distinguishes:

```text
what currently exists
```

from:

```text
what could happen
```

and:

```text
what is computed from it
```

### Result

**Keep State.**

# 09.11.10 Validation Verdict

The current DSL design survives the complete validation suite.

More importantly, validation changed the design in a useful direction:

### Before

The language appeared to require many semantic constructs:

```text
property
parameter
variable
field
predicate
rule
equation
experiment
animation
...
```

### After

Many of these can be understood as **surface-level abstractions over a smaller semantic kernel**.

The emerging architecture is:

```text
                  DOMAIN LIBRARIES
                         │
                  STANDARD LIBRARIES
                         │
                  SURFACE LANGUAGE
                         │
                  SEMANTIC LOWERING
                         │
                ┌────────▼────────┐
                │ SEMANTIC KERNEL │
                └────────┬────────┘
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
     RUNTIME        PRESENTATION      INTERACTION
        │                │                │
        └────────────────┼────────────────┘
                         ▼
                       OUTPUT
```

The fundamental design principle can now be stated more precisely:

> **The DSL should provide a small semantic kernel for describing typed values, identities, state, relationships, domains, computation, evolution, observation, projection and interaction; higher-level mathematical, scientific, educational and presentation concepts should be expressible through composition and lowering rather than being built into the core.**

This is a substantially stronger result than simply showing that the examples "work."

The next stage should therefore **not yet be Rust implementation**.

The next design task is to formalize the remaining semantic boundaries, especially:

```text
09.12 Formal Semantic Core
```

with particular attention to:

```text
Binding
State
Evolution Target
Contribution
Operation
Event
Process
Dependency
Commit
Time
```

because these are now the concepts on which the runtime, type system, DSL syntax and compiler IR will all depend.
