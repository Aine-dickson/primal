---

## 1. What makes a language requirement?

A requirement is something the author must be able to **express, control, observe, or compose** through the language.

We therefore derive requirements from the semantic model rather than simply turning every internal runtime concept into a keyword.

For example:

> The runtime has an event scheduler.

does **not** automatically mean:

```text
schedule_event(...)
```

must exist in the DSL.

Instead we ask:

> What authoring capability does the scheduler make possible?

Perhaps:

```text
"when the particle reaches the wall, reverse its velocity"
```

The language needs to express **condition-triggered behavior**. The scheduler may remain an implementation detail.

That distinction will be important throughout this artifact.

---

# 2. The fundamental requirement

The DSL must allow an author to describe:

> **A system, its meaning, how it changes, what can be observed, how it is represented, and how an external actor can interact with it.**

In conceptual form:

```text
AUTHOR
  │
  ├── defines MODEL
  │
  ├── defines BEHAVIOR
  │
  ├── defines OBSERVATIONS
  │
  ├── defines PROJECTIONS
  │
  ├── defines INTERACTIONS
  │
  └── optionally defines PRESENTATION / ANIMATION
```

The author should **not** have to manually implement the underlying runtime architecture.

---

# 3. Requirement Group A: Model Definition

The DSL must allow authors to define semantic systems.

### A1: Define a system

An author must be able to create a self-contained model/system.

It must be possible for a system to contain:

- state
- objects
- values
- variables
- relations
- collections
- fields
- behavior
- parameters
- constraints
- observations
- projections
- interactions

---

### A2: Define objects

The language must allow identifiable objects to exist.

Objects may represent:

- physical things
- mathematical things
- conceptual things
- algorithmic structures
- agents
- particles
- nodes
- molecules
- geometric entities
- educational objects

But the DSL should **not** need:

```text
particle
molecule
pendulum
projectile
atom
```

as fundamental language constructs.

Those can be library-defined concepts.

---

### A3: Define properties

An object must be able to have properties.

For example:

```text
position
velocity
mass
charge
temperature
name
radius
```

Properties may be:

```text
constant
variable
derived
computed
stochastic
user-controlled
```

---

### A4: Define collections

The language must support groups of objects.

This is essential for cases such as:

- thousands of particles
- populations
- graph nodes
- molecules
- cells
- data points
- particles created during a simulation
- algorithm inputs

The language must support operations conceptually equivalent to:

```text
create
destroy
filter
map
reduce
count
group
sort
sample
aggregate
```

---

### A5: Define relationships

The DSL must express relationships between objects.

Examples:

```text
particle belongs_to system
node connected_to node
planet orbits star
molecule contains atom
prey interacts_with predator
```

Relations may themselves have properties.

The language must also support **dynamic topology**:

```text
connect
disconnect
create relation
destroy relation
```

---

# 4. Requirement Group B: Mathematical Expression

This is particularly important because the system isn't merely an animation language.

### B1: Values

The DSL must express values such as:

```text
Boolean
Integer
Real
Complex
Quantity
Vector
Matrix
Tensor
Point
Geometry
Set
Sequence
Distribution
Function
Expression
Equation
Reference
Data
```

---

### B2: Expressions

Authors must be able to derive values from other values.

Conceptually:

```text
speed = sqrt(vx^2 + vy^2)
```

or:

```text
kinetic_energy = 0.5 * mass * speed^2
```

Expressions must be able to depend on:

- constants
- parameters
- object properties
- other expressions
- state
- time
- fields
- functions
- randomness where explicitly requested

---

### B3: Functions

The DSL must allow mathematical mappings to be defined.

For example:

```text
f(x) = x^2
```

But functions must also support more general mappings:

```text
Vector → Vector
Point → Real
State → Data
Data → Data
```

This is necessary for both mathematics and computation.

---

### B4: Equations

Equations must be expressible independently of their eventual solution method.

For example:

```text
F = m * a
```

or:

```text
dN/dt = -λN
```

The language must **not equate an equation with a solver**.

The author expresses the mathematical relationship.

The runtime/library determines how it is evaluated or solved.

---

### B5: Predicates and conditions

The DSL must express propositions:

```text
x > 0
distance(a, b) < r
temperature > boiling_point
node.visited == false
```

These become important for:

- rules
- events
- constraints
- interactions
- branching
- experiments

---

### B6: Units and dimensions

The language must be capable of representing quantities with units/dimensions.

For example:

```text
5 m
10 s
9.81 m/s²
300 K
```

It should distinguish:

```text
unit
```

from:

```text
dimension
```

so that dimensional correctness can be checked.

---

# 5. Requirement Group C: Behavior

The language must describe **how things behave**, without forcing everything into one mechanism.

It must distinguish:

```text
Function
Expression
Equation
Rule
Process
Event
Constraint
```

These are semantically different.

---

### C1: Rules

Example concept:

```text
if temperature > threshold:
    activate_fan()
```

Rules should support conditions and effects.

---

### C2: Processes

The DSL must express ongoing evolution.

For example:

```text
velocity changes continuously
population evolves
heat diffuses
wave propagates
```

This must support both continuous and discrete processes.

---

### C3: Events

The language must express discrete occurrences.

Events may be:

- scheduled
- condition-triggered
- random
- externally triggered
- user-triggered

---

### C4: Constraints

Authors must be able to specify what states are valid.

Examples:

```text
distance >= 0
energy >= 0
point lies inside region
sum(probabilities) == 1
object cannot overlap another object
```

Constraints must remain semantic rather than being hidden inside rendering or interaction code.

---

# 6. Requirement Group D: Time

The language must be able to express temporal concepts without assuming one universal notion of time.

It must support:

- time
- duration
- instants
- timestep
- scheduled events
- temporal conditions
- playback
- time scaling

And importantly:

```text
SIMULATION TIME
≠
PRESENTATION TIME
≠
WALL-CLOCK TIME
```

An author should therefore be able to describe a simulation that runs:

- slower than real time
- faster than real time
- paused
- stepped
- offline
- interactively

without changing the model itself.

---

# 7. Requirement Group E: Space

The DSL must not assume that every model is simply a 2D scene.

It must support:

```text
non-spatial
1D
2D
3D
N-dimensional
abstract/topological
```

It must allow concepts such as:

- position
- direction
- distance
- angle
- coordinate systems
- regions
- geometry
- transformations
- spatial relationships

A 3D model must therefore remain expressible even if the initial renderer is 2D.

---

# 8. Requirement Group F: Fields

Fields must be first-class enough to express cases such as:

```text
electric field
temperature field
pressure field
velocity field
probability density
height field
```

Conceptually:

```text
F : Domain → Value
```

The DSL must support fields that are:

- analytically defined
- numerically computed
- sampled
- interpolated
- dynamically changing
- visualized

---

# 9. Requirement Group G: Computation

The language must allow authors to describe computation without forcing them to implement numerical infrastructure.

It needs conceptual support for:

- evaluation
- iteration
- numerical integration
- numerical solving
- root finding
- linear algebra
- sampling
- aggregation
- statistics
- optimization
- constraint solving

But this does **not** mean every algorithm becomes a core DSL primitive.

For example, the author might specify:

> evolve this differential equation

while selecting or inheriting an integration strategy separately.

This preserves:

```text
SCIENTIFIC MODEL
        ≠
EXECUTION STRATEGY
```

---

# 10. Requirement Group H: Randomness

Stochastic systems require more than `random()`.

The language/runtime combination must support:

```text
distribution
random source
seed
random state
sampling
```

This allows:

```text
same model
+
same initial state
+
same parameters
+
same seed
+
same execution configuration
```

to produce reproducible experiments where the execution model permits it.

This is essential for:

- radioactive decay
- Monte Carlo
- random walks
- stochastic chemistry
- populations
- probabilistic algorithms

---

# 11. Requirement Group I: Observation

The language must allow the author to specify **what is observed**, separately from what exists.

For example:

```text
measure(position)
measure(speed)
measure(temperature)
count(particles)
sample(field, point)
record(energy)
```

Observation must support:

```text
State
 ↓
Observation
 ↓
Data
```

The resulting data must be usable for:

- graphs
- tables
- statistics
- measurements
- analysis
- educational feedback
- exported datasets

---

# 12. Requirement Group J: Projection

This is one of the most important DSL requirements.

The author must be able to say:

> **Show this semantic information in this representation.**

Without forcing the model itself to become a scene.

Conceptually:

```text
MODEL/DATA
     ↓
 PROJECTION
     ↓
REPRESENTATION
     ↓
    VIEW
```

The DSL therefore needs a way to express mappings such as:

```text
particle.position → circle.position
particle.mass     → circle.radius
particle.charge   → circle.label
temperature       → color
velocity          → arrow
population        → graph
data              → histogram
equation          → mathematical display
```

---

# 13. Requirement Group K: Multiple Representations

The DSL must support multiple views of the same underlying model.

For example:

```text
             ┌→ particle view
MODEL ───────┼→ graph view
             ├→ equation view
             └→ data table
```

These representations may update simultaneously.

The language must therefore avoid requiring:

```text
model_for_scene_1
model_for_scene_2
model_for_graph
```

when they are actually observing the same semantic model.

---

# 14. Requirement Group L: Writable Representations

Some representations are merely displays.

Others allow manipulation.

The DSL must distinguish these.

For example:

```text
temperature → color
```

may be read-only.

Whereas:

```text
point.position ↔ draggable point
```

may be writable.

Therefore the language must somehow support:

```text
read binding
write binding
read/write binding
explicit interaction mapping
```

without assuming every projection is invertible.

---

# 15. Requirement Group M: Interaction

The author must be able to define interaction.

Conceptually:

```text
INPUT
 ↓
INTERPRETATION
 ↓
INTENT
 ↓
TARGET
 ↓
OPERATION
 ↓
EFFECT
```

Interactions must be able to target:

- model objects
- properties
- relations
- collections
- fields
- parameters
- runtime
- views
- observations
- datasets

---

# 16. Requirement Group N: Direct Manipulation

The DSL must support interactions such as:

```text
drag point
move particle
resize object
rotate object
connect nodes
draw region
construct triangle
place charge
```

But the language must not require the author to manually perform:

```text
screen coordinate
→ inverse camera transform
→ inverse projection
→ model coordinate
→ constraint solving
```

for every interaction.

Those are semantic/runtime responsibilities.

The author expresses the intended relationship.

---

# 17. Requirement Group O: Interaction Transactions

Some interactions are temporary.

For example:

```text
drag point
```

may produce:

```text
begin
  ↓
preview
  ↓
move
  ↓
release
  ↓
validate
  ↓
commit
```

The DSL must therefore be capable of expressing interactions that are:

- immediate
- transactional
- previewable
- cancellable
- multi-step

---

# 18. Requirement Group P: Runtime Control

The language must provide access to execution controls where appropriate:

```text
play
pause
step
reset
seek
speed
branch
checkpoint
```

But these are not model properties.

For example:

```text
pause
```

does not mean:

```text
simulation_state.paused = true
```

in the scientific model.

It modifies **runtime state**.

---

# 19. Requirement Group Q: Experiments

The DSL must support the concept of an experiment.

An experiment may consist of:

```text
MODEL
+
INITIAL STATE
+
PARAMETERS
+
INTERVENTIONS
+
EXECUTION
+
OBSERVATIONS
+
RESULTS
```

This enables educational and scientific workflows such as:

```text
change gravity
run experiment
measure range
repeat with different gravity
compare results
```

---

# 20. Requirement Group R: Snapshots and Branching

The language/runtime must support preservation of model execution state.

Conceptually:

```text
        initial
           │
       checkpoint
        /       \
       /         \
 experiment A   experiment B
```

This enables:

- undo
- redo
- experimentation
- what-if scenarios
- replay
- branching simulations

---

# 21. Requirement Group S: Animation

The DSL must support animation even when there is no simulation.

For example:

```text
show equation
transform equation
draw circle
move arrow
fade label
```

Therefore:

```text
ANIMATION
```

cannot simply be a side effect of:

```text
SIMULATION
```

The language must support:

```text
MODEL-DRIVEN ANIMATION
```

and:

```text
AUTHOR-DIRECTED ANIMATION
```

and combinations of both.

---

# 22. Requirement Group T: Educational Authoring

Because the target system includes educational content, the DSL should be capable of expressing higher-level activities.

Examples:

```text
prediction
question
measurement task
guided exploration
experiment
feedback
assessment
narration
```

But again, these should likely be **library-level constructs**, not necessarily fundamental language syntax.

The core language only needs to be sufficiently expressive to build them.

---

# 23. Requirement Group U: Composition

The language must allow complex systems to be constructed from smaller systems/components.

For example:

```text
projectile
+
gravity field
+
air resistance
+
measurement system
+
graph view
```

becomes a composed system.

Composition must support:

- shared state
- dependencies
- data flow
- events
- interfaces
- coupling
- nested systems

This is necessary for genuinely complex simulations.

---

# 24. Requirement Group V: Separation of Concerns

The DSL must preserve the distinctions we've established throughout the project.

The language must not accidentally collapse:

```text
MODEL
SIMULATION
REPRESENTATION
VIEW
INTERACTION
ANIMATION
OBSERVATION
DATA
```

For example:

> Drawing a circle should not create a particle.

> Showing an equation should not automatically make it a governing equation.

> Selecting an object should not automatically modify its semantic state.

> Moving a camera should not move the model.

These distinctions are **language requirements**, not merely implementation preferences.

---

# 25. Requirement Group W: Inference

The language should avoid making authors repeatedly specify information that can be safely inferred.

For example, if:

```text
point.position
```

is bound to a point representation and the author declares that the point is draggable, the system may be able to infer the required inverse coordinate transformation.

Likewise:

```text
particles → circles
```

might allow representation lifecycle to follow collection membership automatically.

But inference must be:

> **deterministic, explainable, and semantically unambiguous.**

Where inference becomes ambiguous, the DSL must permit explicit specification.

This gives us an important future design principle:

```text
EXPLICIT WHEN NECESSARY
INFERRED WHEN SAFE
```

We should revisit this carefully during **09.3-09.4**.

---

# 26. Requirement Group X: Extensibility

The language must allow domain libraries to introduce higher-level concepts.

For example:

```text
physics
chemistry
biology
mathematics
computer_science
electronics
```

can build on the core.

A physics library could define:

```text
Particle
Force
Mass
Momentum
Gravity
```

A chemistry library could define:

```text
Atom
Molecule
Bond
Reaction
Concentration
```

without changing the fundamental language.

This is critical if the system is expected to eventually cover the enormous case catalogue we created.

---

# 27. Requirement Group Y: Execution Independence

The DSL must not unnecessarily bind an author's model to:

```text
Rust
CPU
GPU
specific solver
specific renderer
specific window system
specific video encoder
```

The author describes meaning.

The runtime chooses an execution strategy.

The presentation system chooses a renderer.

The output system chooses an encoder.

Conceptually:

```text
                 DSL
                  │
                  ↓
              SEMANTICS
             /    |     \
            /     |      \
       RUNTIME  PRESENTATION  OUTPUT
```

---

# 28. Requirement Group Z: Error Awareness

The language must make meaningful distinctions between:

```text
semantic invalidity
computational failure
runtime failure
presentation failure
```

For example:

```text
probability = -2
```

may be a semantic error.

Whereas:

```text
solver failed to converge
```

is a computational failure.

And:

```text
renderer cannot represent requested feature
```

is a presentation limitation/failure.

These should not all collapse into generic "error".

---

# 29. Requirement Group AA: Determinism and Provenance

The language/runtime must be capable of preserving enough information to reproduce an experiment where required.

Potential provenance:

```text
model version
initial state
parameters
random seed
execution configuration
numerical configuration
external inputs
interaction history
```

This is particularly important for educational experiments and scientific simulations.

---

# 30. Requirement Group AB: Output Independence

The same authored system should be usable for different outputs.

Conceptually:

```text
                 MODEL
                   │
              ┌────┴────┐
              ↓         ↓
         INTERACTIVE   OFFLINE
              │         │
        ┌─────┼─────┐   ├── image
        ↓     ↓     ↓   ├── video
       UI   WASM   APP  ├── frames
                         └── data
```

The DSL should therefore not fundamentally be:

> a language for making interactive windows.

It should describe the underlying authored system.

# 32. The most important conclusion

We now have a very useful boundary.

### The DSL must express **meaning**, not implementation.

For example, the author should be able to express:

> "A particle has position and velocity, gravity accelerates it, its position is displayed as a circle, its velocity is displayed as an arrow, the particle can be dragged, and its trajectory is recorded."

The author should **not** have to express:

> allocate this ECS component, invoke RK4, update this Vello path, perform inverse matrix multiplication, run hit testing, enqueue an event, invalidate this cache, upload this buffer...

Those belong beneath the language.

So our next step is **not yet syntax**.

# 09.2 Construct Inventory

Now that we know **what the language must be capable of saying**, the next question is:

> **What actual language constructs do we need to give the author?**

And this is where we need to be particularly careful.

We will take the requirements above and classify each possible construct as:

```text
FUNDAMENTAL LANGUAGE CONSTRUCT
        vs
LIBRARY CONSTRUCT
        vs
INFERRED CONSTRUCT
        vs
RUNTIME/IMPLEMENTATION DETAIL
```

For example, we need to determine whether things like:

```text
system
object
property
let
state
process
event
rule
equation
view
projection
bind
interaction
experiment
animate
```

should actually exist in the language, or whether some of them should emerge from more fundamental constructs.

**That is the next artifact: 09.2 Construct Inventory.**

So our tracking point is now unambiguous:
