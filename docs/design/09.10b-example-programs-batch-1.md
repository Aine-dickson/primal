# 09.10 Example Programs: Validation Batch 1

## Validation rule

For every case:

```text
DSL
  ↓
Semantic meaning
  ↓
Generalized model
  ↓
Runtime / projection / interaction
```

Then classify any problem as:

```text
SYN, syntax problem
SEM, semantic ambiguity
TYP, type-system problem
BND, binding/scoping problem
CMP, composition problem
RUN, runtime-semantics problem
PRJ, projection problem
INT, interaction problem
EXT, extension-model problem
CORE, genuinely missing core capability
```

# 01 Pure function: `f(x) = x²`

This is our simplest test.

### DSL

```text
system Quadratic {

    function f(x : Real) : Real =
        x²

    domain x = [-5, 5]

    view graph {
        plot f(x)
    }
}
```

### Semantic lowering

```text
System
├── Function
│   └── f : Real → Real
├── Domain
│   └── x ∈ [-5,5]
├── Projection
│   └── f(x) → graph curve
└── View
    └── graph
```

No simulation exists.

That's important:

```text
Function → Projection → View
```

is sufficient.

### Verdict

**PASS**

The generalized model handles static mathematics without inventing simulation semantics.

### Observation

We have one syntax issue worth recording:

```text
domain x = [-5,5]
```

Is `x` itself a domain variable, or is the domain a separate declaration?

We'll revisit this when several examples expose the same issue.

# 04 Static triangle

Now something with identity.

### DSL

```text
system Triangle {

    object A {
        position = (0, 0)
    }

    object B {
        position = (4, 0)
    }

    object C {
        position = (2, 3)
    }

    relation AB = segment(A.position, B.position)
    relation BC = segment(B.position, C.position)
    relation CA = segment(C.position, A.position)

    view geometry {
        show A
        show B
        show C
        show AB
        show BC
        show CA
    }
}
```

### Semantic model

```text
Objects
    A
    B
    C

Properties
    A.position : Point<2>
    B.position : Point<2>
    C.position : Point<2>

Relations
    AB
    BC
    CA

Projection
    objects → points
    relations → segments
```

### Interesting question

Why not:

```text
A = (0,0)
```

instead of:

```text
object A {
    position = (0,0)
}
```

Because identity matters.

Later we may want:

```text
select A
drag A
measure distance(A,B)
attach label to A
```

So an object is justified here.

### But another issue appears

`segment(A.position, B.position)` creates geometry from model values.

Is `AB`:

1. a semantic relation?
2. derived geometry?
3. both?

We shouldn't decide yet.

This is a **semantic-model question**, not merely syntax.

### Verdict

**PASS, with semantic question recorded**

```text
SEM-01:
Distinguish semantic relations from derived geometric representations.
```

# 05 Projectile motion

Now the first serious test.

### DSL

```text
system Projectile {

    parameter g : Acceleration = 9.81 m/s²

    object ball {

        position : Point<2> =
            (0 m, 0 m)

        velocity : Vector<2> =
            (10 m/s, 15 m/s)

        mass : Mass =
            1 kg
    }

    process motion {

        equation:
            d(ball.position) / dt =
                ball.velocity

        equation:
            d(ball.velocity) / dt =
                (0, -g)
    }

    view scene {

        show ball
        show trajectory(ball.position)
    }
}
```

Now we have a much richer lowering.

### Semantic model

```text
System
│
├── Parameter
│   └── g
│
├── Object
│   └── ball
│       ├── position
│       ├── velocity
│       └── mass
│
├── Process
│   └── motion
│       ├── equation 1
│       └── equation 2
│
└── Presentation
    └── scene
```

### Type checking

We need:

```text
d(position)/dt : Velocity
```

and:

```text
d(velocity)/dt : Acceleration
```

The units therefore provide useful constraints.

For example:

```text
position : m
velocity : m/s
acceleration : m/s²
```

A dimensionally incorrect equation should be rejected.

### But we hit a runtime problem

The model says:

\[
\frac{d\mathbf p}{dt}=\mathbf v
\]

and:

\[
\frac{d\mathbf v}{dt}=\mathbf a
\]

It does **not** specify whether execution uses:

```text
Euler
RK4
adaptive RK
Verlet
...
```

That's correct.

But runtime semantics must answer:

> How does an abstract continuous process become executable?

This is exactly why runtime semantics was a separate artifact.

### New issue

Suppose another process says:

```text
process wind {
    equation:
        d(ball.velocity) / dt =
            wind_acceleration
}
```

Now two processes affect the same derivative.

Do we:

```text
replace
```

or:

```text
combine contributions?
```

This is a major issue.

### Result

**PASS for model representation.**

**RUN-01 discovered:**

> Runtime needs explicit semantics for multiple behavioral contributions to the same state/evolution variable.

This should not become a physics-specific rule.

It needs to be generalized.

# 06 Pendulum

### DSL

```text
system Pendulum {

    parameter g : Acceleration =
        9.81 m/s²

    parameter L : Length =
        1 m

    state {

        θ : Angle =
            30°

        ω : AngularVelocity =
            0 rad/s
    }

    process motion {

        equation:
            d(θ) / dt = ω

        equation:
            d(ω) / dt =
                -(g / L) * sin(θ)
    }

    view scene {

        show pendulum(θ, L)
    }

    view graph {

        plot θ over time
        plot ω over time
    }
}
```

Here we intentionally used:

```text
state
```

rather than putting everything into an `object`.

This gives us our first potential syntax redundancy.

We currently have both:

```text
object ball {
    position = ...
}
```

and:

```text
state {
    θ = ...
}
```

Semantically, both create state bindings.

That suggests our earlier hypothesis about **bindings and roles** may be important.

Perhaps the deeper semantic structure is:

```text
binding
├── name
├── type
├── value
├── role
├── ownership
└── metadata
```

Then:

```text
object
state variable
parameter
constant
property
derived value
```

are different semantic roles/contextual constructs rather than completely unrelated mechanisms.

### But we should not collapse them prematurely.

`ball.position` has:

```text
object identity
+
property ownership
```

while `θ` is a state variable.

So there is still a meaningful distinction.

### Verdict

**PASS**

But:

```text
SEM-02:
Clarify relationship between object properties and standalone state variables.
```

# 07 Bouncing ball

This is where the model becomes hybrid.

### DSL

```text
system BouncingBall {

    parameter g : Acceleration =
        9.81 m/s²

    parameter restitution : Real =
        0.8

    object ball {

        position : Point<2> =
            (0 m, 5 m)

        velocity : Vector<2> =
            (0 m/s, 0 m/s)
    }

    process motion {

        equation:
            d(ball.position) / dt =
                ball.velocity

        equation:
            d(ball.velocity) / dt =
                (0, -g)
    }

    event ground_collision {

        when ball.position.y <= 0

        operation {

            set ball.position.y = 0

            set ball.velocity.y =
                -restitution * ball.velocity.y
        }
    }

    view scene {
        show ball
        show ground
    }
}
```

### Semantic structure

```text
Continuous Process
        │
        ↓
    state evolves
        │
        ↓
 condition becomes true
        │
        ↓
      Event
        │
        ↓
    Operations
        │
        ↓
    new state
```

Excellent.

This validates our distinction:

```text
Process ≠ Event
```

### But now a critical runtime question

Suppose numerical integration advances from:

```text
y = 0.03
```

to:

```text
y = -0.07
```

The event condition was not exactly sampled at `y = 0`.

The runtime must determine the event boundary.

That's a **continuous-event detection** problem.

The DSL shouldn't need to know whether the solver uses:

- interpolation,
- root finding,
- substepping,
- collision detection.

But runtime semantics must.

### Verdict

**PASS**

> **Correction note (2026-09-29; D-004; audit F-02):** This example is defective as written. After the reset sets `y = 0`, the guard `y <= 0` is still true, so under level-triggered semantics the event retriggers immediately. It also has no Zeno policy: with restitution 0.8 the ball bounces infinitely often in finite time. Current position: D-004 (directional crossing guards, resets, superdense time, declared Zeno policy). The ball is now the first reference program (D-012).

New runtime requirement:

```text
RUN-02:
Continuous processes need a defined relationship between numerical
integration and condition-triggered events.
```

# 08 Radioactive decay

Now we remove geometry entirely.

### DSL

```text
system RadioactiveSample {

    parameter λ : Rate =
        0.1 / s

    collection nuclei : Nucleus =
        create 1000

    process decay {

        for nucleus in nuclei {

            event decay {

                probability =
                    λ * dt

                operation {
                    destroy nucleus
                }
            }
        }
    }

    observation remaining =
        count(nuclei)

    view graph {
        plot remaining over time
    }
}
```

This is a powerful test because the model contains:

```text
collection
dynamic identity
probability
randomness
destruction
observation
dataset
graph
```

### First problem

What does:

```text
probability = λ * dt
```

mean?

For sufficiently small `dt`, it can be interpreted as the first-order decay probability, but the language itself should not silently pretend that all stochastic processes work this way.

The model should distinguish:

```text
distribution
random source
stochastic transition
```

The actual sampling mechanism belongs to the execution semantics.

### Better conceptual form

```text
event decay {

    hazard = λ

    operation {
        destroy nucleus
    }
}
```

This is arguably semantically cleaner.

But now we've introduced **hazard**, which is domain language.

It should probably live in a probability/stochastic-process library rather than the core.

So:

```text
stochastic.exponential_decay(λ)
```

could provide this behavior.

### Important extension test

The core only needs enough machinery to express:

```text
random transition
```

It doesn't need to understand radioactive decay.

### Verdict

**PASS conceptually.**

But:

```text
EXT-01:
Stochastic-process abstractions should be library-level.

RUN-03:
Runtime needs precise semantics for stochastic events and random-source state.
```

# 09 Chemical reaction

Let's make the system microscopic.

\[
A+B\rightarrow C
\]

### DSL

```text
system Reaction {

    collection molecules : Molecule

    event reaction(a : Molecule, b : Molecule) {

        when
            near(a, b)
            and a.species == A
            and b.species == B

        operation {

            destroy a
            destroy b

            create Molecule {
                species = C
            }
        }
    }

    view scene {

        for molecule in molecules {
            show molecule
        }
    }
}
```

### Semantic lowering

```text
Collection<Molecule>

Event
├── parameters a,b
├── predicate
└── operations
    ├── destroy
    ├── destroy
    └── create
```

### Extension model test

`Molecule` is not core.

`species` is not core.

`near()` is not core.

`reaction` isn't core.

Yet the program is expressible.

That is exactly what we wanted.

### Dynamic topology

The collection changes:

```text
before:
A B

after:
C
```

No special chemistry machinery is needed in the runtime.

The runtime only needs:

```text
CREATE
DESTROY
```

and collection consistency.

### Potential problem

What if both `a` and `b` refer to the same molecule?

We need a constraint such as:

```text
a != b
```

So the program becomes:

```text
when
    a != b
    and near(a,b)
    and ...
```

This reinforces that predicates and constraints are fundamental.

### Verdict

**PASS**

Strong validation of:

```text
dynamic collections
identity
relations
events
operations
extension types
constraints
```

# 10 Macroscopic reaction kinetics

Same domain, completely different model.

\[
\frac{d[A]}{dt}=-k[A][B]
\]

### DSL

```text
system ReactionKinetics {

    parameter k : RatePerConcentration =
        0.2

    state {
        A : Concentration = 1 mol/L
        B : Concentration = 1 mol/L
        C : Concentration = 0 mol/L
    }

    process reaction {

        equation:
            d(A) / dt =
                -k * A * B

        equation:
            d(B) / dt =
                -k * A * B

        equation:
            d(C) / dt =
                k * A * B
    }

    view graph {

        plot A over time
        plot B over time
        plot C over time
    }
}
```

This is a particularly important result.

The word "reaction" appears in both models, but the underlying generalized model is completely different:

```text
Microscopic
    objects + collection + stochastic events

Macroscopic
    quantities + continuous equations
```

Therefore a domain concept doesn't dictate one representation or model.

This strongly validates the architecture:

```text
DOMAIN CONCEPT
       ↓
one or more MODELS
       ↓
one or more REPRESENTATIONS
```

# 12 BFS graph traversal

Now deliberately leave science.

### DSL

```text
system GraphSearch {

    type Node {
        value : Text
        visited : Boolean = false
    }

    relation Edge {
        from : Node
        to : Node
    }

    collection nodes : Node
    collection edges : Edge

    process bfs(start : Node) {

        collection frontier : Queue<Node> =
            [start]

        while not empty(frontier) {

            node = pop(frontier)

            set node.visited = true

            for edge in outgoing(node) {

                if not edge.to.visited {
                    push(frontier, edge.to)
                }
            }
        }
    }

    view graph {

        show nodes
        show edges
    }
}
```

### What does this test?

Almost everything outside physical simulation:

```text
user-defined types
relations
collections
generic collections
mutation
iteration
conditional logic
algorithms
graph projection
```

### Important discovery

Our DSL requirements said:

> expression / rule / process

but this example needs conventional computational control structures:

```text
while
for
if
```

We cannot assume that all behavior can be represented purely as equations/events.

This does **not** necessarily mean `while`, `for`, and `if` should all be fundamental semantic constructs.

But the language needs some general mechanism for **algorithmic computation**.

### This is a genuine language requirement

We previously had:

```text
PROCESS
```

but we need to distinguish at least:

```text
process {
    equations...
}
```

from:

```text
process {
    algorithm...
}
```

Both are processes, but their execution semantics differ.

### Verdict

**PASS conceptually, but important DSL requirement discovered.**

```text
SEM-03:
Process must support algorithmic behavior as well as mathematical evolution.

RUN-04:
Runtime must support general ordered/iterative computation.
```

# 13 Sorting

Now test a pure algorithm without graph relations.

```text
system Sorting {

    collection values : Sequence<Integer> =
        [7, 2, 9, 1, 5, 3]

    process insertion_sort {

        for i in 1 .. length(values) {

            key = values[i]
            j = i - 1

            while j >= 0
                and values[j] > key {

                values[j + 1] = values[j]
                j = j - 1
            }

            values[j + 1] = key
        }
    }

    view bars {

        for value in values {
            show value as bar
        }
    }
}
```

This raises another distinction:

```text
Sequence
Collection
```

A sequence has ordering.

A generic collection may not.

Therefore our earlier type system should probably retain:

```text
Sequence<T>
Collection<T>
Set<T>
Map<K,V>
```

rather than collapsing them all.

### Verdict

**PASS**

# 14 Predator/prey

Now a continuous nonphysical model.

```text
system PredatorPrey {

    parameter a : Real = 1.0
    parameter b : Real = 0.01
    parameter c : Real = 0.5
    parameter d : Real = 0.005

    state {
        prey : Real = 100
        predators : Real = 10
    }

    process ecology {

        equation:
            d(prey)/dt =
                a * prey
                - b * prey * predators

        equation:
            d(predators)/dt =
                -c * predators
                + d * prey * predators
    }

    view graph {

        plot prey over time
        plot predators over time
    }

    view phase {

        plot(
            x = prey,
            y = predators
        )
    }
}
```

This is useful because the model has:

```text
no physical space
```

but the representation contains:

```text
2D graph space
```

Therefore:

> **Model space and render space are genuinely different concepts.**

The phase portrait's `(x,y)` is representational coordinate space, not physical space.

### Verdict

**PASS**

Strong confirmation of the projection model.

# 15 Multi-view projectile

Now combine several representation families.

```text
system ProjectileStudy {

    parameter g : Acceleration =
        9.81 m/s²

    object ball {

        position : Point<2> = (0 m, 0 m)
        velocity : Vector<2> = (10 m/s, 15 m/s)
    }

    process motion {

        equation:
            d(ball.position)/dt =
                ball.velocity

        equation:
            d(ball.velocity)/dt =
                (0, -g)
    }

    observation speed =
        magnitude(ball.velocity)

    observation height =
        ball.position.y

    view scene {
        show ball
        show trajectory(ball.position)
    }

    view velocity {
        plot speed over time
    }

    view height {
        plot height over time
    }

    view equation {
        show motion
    }
}
```

The model remains one model.

```text
                 Projectile
                     │
        ┌────────────┼─────────────┐
        ↓            ↓             ↓
      Scene        Graph         Equation
        ↓            ↓             ↓
       View         View           View
```

### Important observation

The graphs use **observations**, not necessarily direct presentation of state.

That means:

```text
State → Observation → Data → Projection → View
```

while the scene can use:

```text
State → Projection → View
```

This validates why `Observation` and `Projection` should remain separate.

### Verdict

**PASS**

# 16 Interactive projectile

Now we test the interaction model.

```text
system InteractiveProjectile {

    parameter g : Acceleration =
        9.81 m/s²

    object ball {

        position : Point<2> = (0 m, 0 m)

        initial_velocity : Vector<2> =
            (10 m/s, 15 m/s)

        velocity : Vector<2> =
            initial_velocity
    }

    process motion {

        equation:
            d(ball.position)/dt =
                ball.velocity

        equation:
            d(ball.velocity)/dt =
                (0, -g)
    }

    view scene {

        show ball
        show velocity_handle(ball.initial_velocity)
    }

    interaction adjust_velocity {

        on drag(
            velocity_handle(ball.initial_velocity)
        ) {

            preview {
                set ball.initial_velocity =
                    inverse_position(mouse.position)
            }
        }

        on release {
            commit
        }
    }
}
```

The important part isn't whether this exact syntax survives.

It's the semantic chain:

```text
drag
 ↓
interpretation
 ↓
velocity_handle
 ↓
semantic target: ball.initial_velocity
 ↓
proposed SET operation
 ↓
validation
 ↓
commit
 ↓
simulation state changes
```

### One important correction

The initial velocity and current velocity are not the same thing.

If the simulation is halfway through:

```text
initial_velocity = (10,15)
velocity = (4,7)
```

Dragging the handle should probably modify the **initial condition**, not current state.

This is exactly why explicit semantic targets matter.

### Verdict

**PASS**

The interaction architecture survives.

# 19 User-defined extension

Now the decisive test.

Imagine the user wants to add:

```text
Projectile
```

without changing the language implementation.

### Extension

```text
type Projectile {

    position : Point<2>

    velocity : Vector<2>

    mass : Mass
}

capability Positioned {

    position : Point<2>
}

Projectile provides Positioned
```

Generic geometry:

```text
function distance<A : Positioned, B : Positioned>(
    a : A,
    b : B
) : Length =

    magnitude(a.position - b.position)
```

Then:

```text
object ball : Projectile {

    position = (0 m, 0 m)

    velocity = (10 m/s, 15 m/s)

    mass = 1 kg
}

object atom : Atom {

    position = (2 nm, 4 nm)
}

distance(ball, atom)
```

Ignoring dimensional incompatibility for the moment, the *semantic* idea works:

```text
Projectile ──┐
             ├── Positioned
Atom ────────┘
```

and:

```text
distance()
```

depends on the capability rather than concrete type.

### This is exactly the extension behavior we wanted.

The compiler does not need:

```text
if type == Projectile ...
if type == Atom ...
if type == Vehicle ...
```

# 21. Issues discovered

## RUN-01 Multiple processes affecting the same evolution variable

Example:

```text
process gravity {
    d(v)/dt = gravity
}

process wind {
    d(v)/dt = wind
}
```

Does that mean:

```text
error?
```

or:

```text
d(v)/dt = gravity + wind
```

or:

```text
last writer wins?
```

The runtime needs a generalized **contribution/composition semantics for behavior**.

---

## RUN-02 Continuous/event boundary

Bouncing ball exposes:

```text
continuous evolution
        ↓
condition crossing
        ↓
discrete event
```

The runtime needs event-detection semantics.

The DSL should not encode the numerical root-finding algorithm.

---

## RUN-03 Stochastic execution

We need a precise distinction between:

```text
Distribution
RandomSource
StochasticProcess
RandomEvent
```

The core shouldn't become a probability-engine implementation.

---

## SEM-01 Relation vs derived geometry

```text
relation AB = segment(A.position,B.position)
```

Is `AB`:

- semantic relation,
- derived geometry,
- or a relation whose representation is a segment?

We need to clarify this before final DSL semantics.

---

## SEM-02 Object properties vs state variables

These both look like state:

```text
ball.position
```

and:

```text
θ
```

But they aren't semantically identical.

We need a clean binding/property/state relationship.

---

## SEM-03 Process vs algorithm

A process can represent:

```text
d(x)/dt = ...
```

but also:

```text
while ...
    ...
```

So `Process` must be broad enough to encompass both without conflating their execution semantics.

# 22. One particularly important discovery

The examples reveal that our language really has **three different styles of computation**:

```text
              COMPUTATION
                   │
       ┌───────────┼────────────┐
       ↓           ↓            ↓
 Mathematical   Reactive      Algorithmic
 Evolution      Behavior      Computation
       │           │            │
    equations    events       loops
    processes    rules        functions
    fields       triggers     iteration
```

For example:

### Mathematical

```text
d(x)/dt = v
```

### Reactive

```text
when x > 10 → destroy object
```

### Algorithmic

```text
while queue not empty {
    ...
}
```

Our generalized model can represent all three.

But the DSL should make their distinction obvious.

That is more important than forcing them into one syntax.

---

# 23. Another important discovery: the DSL isn't only a simulation language

The test set contains:

```text
f(x) = x²
```

which has:

- no evolving state,
- no simulation,
- no interaction.

It also contains:

```text
BFS
```

which has:

- state,
- algorithmic evolution,
- but no physical simulation.

And:

```text
projectile
```

which has:

- mathematical evolution,
- physical interpretation,
- visualization,
- interaction.

And:

```text
triangle construction
```

which has:

- interaction,
- state mutation,
- geometry,
- but potentially no simulation.

So the broader identity of the language is looking more like:

> **A language for defining computationally meaningful models, their evolution, observations, representations, and interactions.**

Rather than merely:

> "A simulation language."

That distinction is becoming increasingly important.

# 25. What we should **not** change yet

Several tempting reactions should be resisted.

We should **not** yet add:

```text
Projectile
Particle
Atom
Molecule
Reaction
Graph
Pendulum
Field
Solver
Collision
```

to the core.

The examples have actually demonstrated that the extension architecture is doing its job.

Likewise, we shouldn't yet add dozens of keywords for:

```text
probability
hazard
trajectory
velocity
force
energy
```

Many of these belong naturally in libraries.

# 26. What Batch 2 should attack

The first batch mostly proves that the **happy path works**.

The next batch should deliberately attack the things most likely to break the model:

```text
19. Collision of many objects
20. 2D/3D coordinate transformation
21. Heat diffusion field
22. Wave propagation
23. Cellular automaton
24. Dynamic graph topology
25. Particle spawning/destruction
26. Coupled microscopic + macroscopic models
27. Stochastic particle simulation
28. External sensor input
29. Missing/unavailable input
30. Invalid state + constraint rejection
31. Numerical instability/failure
32. Non-invertible projection
33. Many-to-one projection
34. One-to-many projection
35. Direct manipulation with constraints
36. Multiple interacting subsystems
37. Replay and deterministic branching
38. Pure explanatory animation with no simulation
39. Educational guided experiment
40. User-defined domain-specific representation
```

Those are more likely to expose **actual holes in the semantic model**.

And I think there's one particularly valuable thing to do before Batch 2: **take the issues discovered here and resolve them against the existing artifacts without touching syntax yet**, especially `RUN-01` (multiple behavioral contributions), `SEM-02` (state/property/binding), and `SEM-03` (mathematical vs reactive vs algorithmic processes). Otherwise we'd risk building Batch 2 on ambiguous semantics.
