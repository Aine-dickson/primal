# 09.5b Type-System Revalidation Against the Extension Model

The goal isn't to redesign the type system from scratch.

The question is:

> **Does our current type system provide enough structure for arbitrary domain extensions to define new concepts, compose them, and write reusable behavior without requiring new core primitives?**

---

## 1. Start With the Extension Stress Test

Let's take concepts from completely different domains:

```text
Mathematics
    Vector
    Matrix
    Function

Physics
    Projectile
    Charge
    Field
    Pendulum

Chemistry
    Atom
    Molecule
    Reaction

Biology
    Cell
    Population

Computer Science
    Graph
    Node
    Packet
    Algorithm
```

We want all of these to coexist in one language.

More importantly, generic things should be able to operate across domains.

For example:

```text
distance(A, B)
```

shouldn't care whether `A` and `B` are:

```text
particles
atoms
cities
graph nodes
points
vehicles
```

provided they satisfy the required semantic capability.

That immediately tells us:

> **Type identity alone isn't enough.**

We need **capability/contract typing**.

---

# 2. Type vs Capability

Consider:

```text
Projectile
```

and:

```text
Positioned
```

They aren't the same kind of concept.

`Projectile` describes a particular semantic concept.

`Positioned` describes a capability:

```text
position : Point<2>
```

So:

```text
Projectile
    HAS capability
Positioned
```

But so might:

```text
Particle
Vehicle
Atom
Molecule
GraphNode
```

Therefore:

```text
TYPE
    What kind of semantic thing is this?

CAPABILITY / INTERFACE
    What can this thing provide?
```

This is the first modification to our earlier model.

---

# 3. Candidate Type Architecture

We can now tentatively separate:

```text
TYPE
├── Primitive Type
├── Structured Type
├── Domain Type
├── Collection Type
├── Function Type
├── Interface / Capability
└── Generic / Parameterized Type
```

But we shouldn't assume all seven need independent machinery.

We'll test each.

---

# 4. Primitive Types

These remain straightforward:

```text
Boolean
Integer
Real
Complex
Text
```

Potentially:

```text
Symbol
```

for symbolic mathematics, although that may simply be part of expressions rather than a runtime value type.

---

# 5. Quantities

Scientific computing requires more than ordinary numbers.

```text
5 m
20 kg
9.81 m/s²
3 C
300 K
```

So:

```text
Quantity
```

remains important.

Conceptually:

```text
Quantity
├── magnitude
├── unit
└── dimension
```

The type system can therefore reject:

```text
5 m + 3 s
```

while accepting:

```text
5 m + 3 m
```

---

# 6. Quantity Type vs Unit

We previously distinguished:

```text
Unit ≠ Dimension
```

That remains correct.

For example:

```text
m
cm
km
```

are different units of the same dimension:

```text
Length
```

while:

```text
m/s
m/s²
kg
```

have different dimensions.

This means a type could conceptually be parameterized by dimension:

```text
Quantity<Length>
Quantity<Mass>
Quantity<Velocity>
```

But there's a subtle question:

Should `Velocity` itself be a distinct nominal type?

Probably not at the core level.

The underlying semantic fact is:

```text
Velocity = Quantity<Length / Time>
```

A physics extension can give that expression a domain-level name.

---

# 7. Domain Types

Now consider:

```text
Atom
Projectile
Molecule
Graph
Cell
```

These are **user/library-defined structured types**.

For example:

```text
type Projectile {
    position : Point<2>
    velocity : Vector<2>
    mass : Quantity<Mass>
}
```

The core doesn't need to know what a projectile is.

It only needs to understand:

```text
type
fields/properties
identity
constraints
behavior
composition
```

This passes the extension test.

---

# 8. Nominal vs Structural Identity

Now we hit a major issue.

Suppose two libraries define:

```text
type Point2D {
    x : Real
    y : Real
}
```

and:

```text
type Coordinate {
    x : Real
    y : Real
}
```

Are they the same type?

There are two possibilities.

### Structural

They are compatible because they have the same structure.

### Nominal

They are different because they were explicitly declared as different types.

For a scientific language, **pure structural typing is dangerous**.

Imagine:

```text
Mass
Energy
Temperature
```

all ultimately containing a number.

We absolutely don't want:

```text
Mass ↔ Energy
```

just because their representation happens to be similar.

So domain semantics require **nominal identity in important cases**.

---

# 9. But Pure Nominal Typing Is Too Restrictive

Now consider:

```text
Projectile
Particle
Atom
Vehicle
```

All might expose:

```text
position
```

A function like:

```text
distance(a, b)
```

shouldn't need a separate implementation for every type.

Therefore we need:

```text
nominal type identity
+
structural/capability compatibility
```

This gives us a hybrid.

---

# 10. Proposed Model: Nominal Types + Explicit Capabilities

A type has its own identity:

```text
Projectile ≠ Particle
```

even if their structures overlap.

But it can explicitly provide a capability:

```text
Projectile : Positioned
Particle   : Positioned
Atom       : Positioned
```

Then:

```text
distance(Positioned, Positioned)
```

works for all of them.

This is significantly safer than saying:

> "Anything with a `position` field is automatically a `Positioned`."

---

# 11. Why Explicit Capability Matters

Imagine:

```text
type TemperatureReading {
    value : Quantity<Temperature>
}
```

and:

```text
type Particle {
    value : Quantity<Energy>
}
```

They may both have a field called `value`.

That doesn't mean they satisfy the same semantic interface.

So:

```text
same structure ≠ same meaning
```

This is consistent with our general philosophy:

> **Semantic meaning must not be inferred merely from representation.**

---

# 12. Interfaces / Capabilities

A capability can therefore be defined as:

```text
interface Positioned {
    position : Point<2>
}
```

A type explicitly satisfies it:

```text
type Projectile ... provides Positioned
```

Or:

```text
type Particle ... provides Positioned
```

Now generic functions can depend on the capability rather than the concrete type.

---

# 13. Capability Is Not Inheritance

This is important.

We're not saying:

```text
Projectile
    inherits
Positioned
```

We're saying:

```text
Projectile
    provides
Positioned
```

That means:

```text
Positioned
```

is a contract, not necessarily a parent class.

This preserves our composition-first architecture.

---

# 14. Multiple Capabilities

A type can provide many capabilities:

```text
Projectile
├── Positioned
├── Massive
├── Observable
├── Collidable
└── Drawable
```

Another:

```text
Atom
├── Positioned
├── Charged
├── Observable
└── Drawable
```

They need not share a class hierarchy.

---

# 15. Capability Composition

Capabilities themselves can depend on other capabilities.

For example:

```text
interface Moving {
    velocity : Vector<2>
}
```

could require:

```text
Positioned
```

Conceptually:

```text
Moving
    requires Positioned
```

This allows more expressive contracts.

---

# 16. Generic Functions

Now test generic behavior.

We want:

```text
function distance(a, b)
```

to work for anything that can provide position.

Conceptually:

```text
function distance<A : Positioned, B : Positioned>(
    a : A,
    b : B
)
```

The exact syntax is not important yet.

The semantic requirement is:

> **Generic behavior can constrain its inputs by capabilities rather than concrete domain types.**

---

# 17. Generic Collections

Our existing model requires collections:

```text
Collection<T>
```

This should continue to work.

Examples:

```text
Collection<Particle>
Collection<Atom>
Collection<Node>
Collection<Real>
Collection<Projectile>
```

And generic operations:

```text
count
filter
map
reduce
sort
group
sample
```

must operate on them.

---

# 18. Capability-Constrained Collections

Now something more interesting:

```text
Collection<T where T : Positioned>
```

This could support generic spatial operations.

For example:

```text
nearest(particles, location)
```

without knowing what the concrete particle type is.

This is a strong argument for capability-constrained generics.

---

# 19. Fields

Our field model was:

```text
Field<Domain, Value>
```

For example:

```text
electric_field : Field<Space2D, Vector<2>>
```

or:

```text
temperature : Field<Space3D, Quantity<Temperature>>
```

Now extensions can build fields naturally.

A field doesn't need to be a special domain primitive.

---

# 20. Generic Functions Need Domain Constraints

Consider:

```text
gradient(T)
```

It shouldn't accept arbitrary values.

Conceptually:

```text
gradient :
    Field<D, V>
    →
    Field<D, Gradient<V>>
```

Similarly:

```text
integrate
differentiate
interpolate
sample
```

can operate generically where their mathematical requirements are satisfied.

This means the type system needs to express **relationships between types**, not merely a flat list of types.

---

# 21. Parameterized Types

This strengthens the case for parameterized types.

Examples:

```text
Vector<2, Real>
Vector<3, Real>

Matrix<3, 3, Real>

Collection<Particle>

Field<Space2D, Quantity<Temperature>>

Function<Real, Real>
```

But we need to distinguish **type parameters** from **runtime values**.

For example:

```text
Vector<3>
```

can use `3` as a type-level dimension.

While:

```text
Vector(n)
```

could represent runtime-sized vectors.

That distinction will matter later.

---

# 22. Point vs Vector

Our previous type system distinguished:

```text
Point
Vector
```

This remains important.

We want:

```text
Point + Vector → Point
Point - Point → Vector
Vector + Vector → Vector
```

but generally not:

```text
Point + Point
```

This is a semantic type distinction that prevents many scientific errors.

---

# 23. Domain Types Can Wrap Core Types

Now test:

```text
Velocity
```

Should it be:

```text
type Velocity = Quantity<Length / Time>
```

or:

```text
type Velocity {
    magnitude...
}
```

The first is preferable when no additional semantic structure is required.

A domain library can therefore define aliases/new semantic names while retaining dimensional semantics.

But a **nominal wrapper** may be appropriate when two mathematically identical representations have different meanings.

That suggests we need both:

```text
TYPE ALIAS
```

and:

```text
NEW / NOMINAL TYPE
```

conceptually.

---

# 24. Alias vs New Type

For example:

```text
Velocity = Quantity<Length / Time>
```

means:

> Velocity is another name for this type.

Whereas:

```text
type Temperature = Quantity<TemperatureDimension>
```

could potentially establish domain-level identity.

But this needs careful design because units already provide strong semantic distinctions.

We shouldn't create nominal wrappers unnecessarily.

---

# 25. Types With Behavior

A type can have associated definitions:

```text
type Projectile {
    position
    velocity
    mass

    function kinetic_energy(...)
}
```

But semantically, this doesn't mean the type owns a method table like a conventional OO class.

It could simply establish names associated with the type.

That keeps us compatible with our composition model.

---

# 26. Behavior Should Still Be Independent

We should therefore allow:

```text
function kinetic_energy(p : Projectile)
```

rather than requiring:

```text
p.kinetic_energy()
```

The latter can potentially be syntactic sugar.

This means behavior can be attached without changing the type's definition.

That is useful for extensions.

A third-party library could define:

```text
drag_force(p : Projectile)
```

without modifying `Projectile`.

---

# 27. Extension Specialization

Now revisit our earlier problem.

We want:

```text
Projectile
GuidedProjectile
Rocket
```

without inheritance.

A better model is:

```text
Projectile
├── Positioned
├── Massive
└── Moving

Guidance
├── target
└── steering behavior

Rocket
├── Projectile
├── Propulsion
└── Guidance
```

So specialization can happen through **composition of definitions and capabilities**.

---

# 28. But Sometimes We Need Type Refinement

There are cases where one type really is a constrained form of another.

For example:

```text
PositiveReal
```

could mean:

```text
Real
constraint x > 0
```

This isn't inheritance.

It's a **refinement**.

Similarly:

```text
NormalizedVector
```

could be:

```text
Vector
constraint |v| = 1
```

This suggests another concept:

```text
REFINEMENT TYPE
```

But should it be fundamental?

Maybe not as a separate type category.

It could be:

```text
Type + Constraint
```

which we already have.

This is a nice example of avoiding unnecessary primitives.

---

# 29. Type + Constraint

We could therefore express:

```text
type PositiveMass =
    Quantity<Mass>
    where value > 0
```

Conceptually:

```text
Base Type
    +
Constraint
```

This fits our existing model beautifully.

It also means the type system doesn't need a separate `PositiveNumber`, `NonZeroNumber`, etc.

---

# 30. Stateful Types

Now consider:

```text
Projectile
```

Its properties change over time.

Does that make `Projectile` a special type?

No.

Its type describes the structure and semantic contract.

Its **state** contains the current values.

So:

```text
TYPE
    Projectile

STATE
    position = ...
    velocity = ...
```

This preserves:

```text
TYPE ≠ STATE
```

---

# 31. Type vs Role

This also validates an earlier conclusion.

Consider:

```text
parameter g = 9.81 m/s²
```

and:

```text
variable x = 0 m
```

`parameter` and `variable` probably shouldn't be independent value types.

They are **roles of bindings/state**.

Likewise:

```text
constant
derived
user-controlled
computed
```

are better represented as metadata/semantic roles.

So:

```text
TYPE
    what is the value?

ROLE
    how does the binding behave?
```

---

# 32. Type vs Identity

An entity has:

```text
identity
```

and:

```text
type
```

For example:

```text
ball1 : Projectile
ball2 : Projectile
```

Both have the same type.

But:

```text
ball1 ≠ ball2
```

because they are different runtime entities.

Therefore:

```text
TYPE ≠ IDENTITY
```

---

# 33. References

This validates our `Reference<T>` concept.

For example:

```text
Reference<Projectile>
```

can identify a particular projectile.

This is especially important for:

- relations,
- collections,
- dynamic creation/destruction,
- interaction,
- observation,
- composition.

---

# 34. Dynamic Collections

Consider radioactive decay.

Initially:

```text
Collection<Nucleus>
```

During execution:

```text
nucleus → daughter nucleus
```

The collection may change.

Therefore:

```text
Collection<T>
```

must support dynamic membership without making collection identity equivalent to a static array.

This is a semantic/runtime concern, but the type system must permit it.

---

# 35. Sum/Variant Types

Now consider events.

An event might be:

```text
Decay
Collision
Birth
Death
UserInput
SensorUpdate
```

A generic event stream may contain one of several event types.

That suggests a variant/sum type:

```text
Event =
    Decay
  | Collision
  | Birth
  | Death
```

Do we need sum types?

Probably yes at the general language level.

Not because of physics specifically, but because arbitrary domain extensions naturally produce alternatives.

---

# 36. Optional Values

External data introduces another need.

```text
temperature
```

might not exist yet.

We need to distinguish:

```text
Temperature
```

from:

```text
Temperature or absent
```

So conceptually:

```text
Optional<T>
```

or equivalent nullable/absence semantics.

But remember our error model:

```text
unknown
unavailable
pending
```

are not all necessarily the same as absence.

Therefore the value system needs to avoid collapsing these states into a single null.

---

# 37. Result Types

Similarly, computation may produce:

```text
success
failure
```

We don't necessarily want every semantic value to carry an error union.

Instead, at operation boundaries we can have a result abstraction conceptually like:

```text
Result<T, Failure>
```

This fits our 09.8 conclusions.

But this should primarily be an **operation/computation mechanism**, not something every DSL variable automatically becomes.

---

# 38. Function Types

Extensions depend heavily on functions.

We already have:

```text
Function<Domain, Codomain>
```

But we now need functions that can be constrained.

For example:

```text
distance :
    (Positioned, Positioned) → Quantity<Length>
```

or:

```text
integrate :
    Function<Time, Quantity<Length>>
    → ...
```

This suggests the type system must support:

- parameter types,
- return type,
- domain,
- generic parameters,
- capability constraints,
- possibly effects.

---

# 39. Function Effects

Here's a new question exposed by the extension model.

Consider:

```text
function speed(p)
```

which merely computes a value.

Versus:

```text
process move(p)
```

which changes state.

The type system may need to distinguish:

```text
PURE
```

from:

```text
STATEFUL
```

But we already distinguish function from process semantically.

So perhaps an effect system can remain a later refinement rather than a new fundamental type.

For now:

```text
Function ≠ Process
```

is sufficient.

---

# 40. Interfaces Should Be Semantic

A capability shouldn't merely expose a field.

For example:

```text
interface Collidable
```

might require more than:

```text
shape
```

It may establish semantic guarantees:

```text
can participate in collision detection
has a collision geometry
supports collision response
```

Therefore an interface can contain:

```text
values
functions
constraints
semantic guarantees
```

This makes it much more powerful than a simple structural record.

---

# 41. Contract Example

Conceptually:

```text
interface Positioned {
    position : Point<2>
}
```

Another:

```text
interface Massive {
    mass : Quantity<Mass>
    constraint mass > 0
}
```

Then:

```text
Projectile
    provides Positioned, Massive
```

A generic law could require:

```text
Massive
```

rather than:

```text
Projectile
```

That is exactly the extensibility we want.

---

# 42. Capability Composition

We can now express domain laws generically.

For example, Newtonian acceleration requires:

```text
Massive
```

and some notion of force/contribution.

Rather than:

```text
if type == Projectile ...
if type == Vehicle ...
if type == Particle ...
```

the behavior depends on contracts.

This is the difference between:

```text
DOMAIN ENUMERATION
```

and:

```text
CAPABILITY COMPOSITION
```

The latter scales much better.

---

# 43. Structural Compatibility Still Has a Place

I wouldn't completely eliminate structural typing.

It is useful for anonymous mathematical structures.

For example:

```text
(x, y)
```

may naturally be usable wherever:

```text
Point<2>
```

is expected, depending on syntax/context.

Likewise an inline record:

```text
{x: 1, y: 2}
```

may satisfy a structural record requirement.

So the likely model is:

```text
NOMINAL TYPES
    semantic identity

STRUCTURAL TYPES
    anonymous structural compatibility

CAPABILITIES
    explicit semantic compatibility
```

---

# 44. Three Different Questions

This is worth making explicit:

When asking whether two things are compatible, we might mean three different things.

### 1. Are they the same type?

```text
Projectile == Projectile
```

### 2. Do they have compatible structure?

```text
{x, y} ≈ {x, y}
```

### 3. Do they satisfy the same semantic contract?

```text
Projectile : Positioned
Particle   : Positioned
```

These should not be conflated.

---

# 45. Generic Domain Libraries

Now test whether an extension can define reusable generic libraries.

Imagine:

```text
library spatial
```

It provides:

```text
distance
nearest
within
intersects
translate
rotate
```

These should operate on:

```text
Point
Positioned
Geometry
Region
```

without knowing anything about:

```text
Projectile
Atom
Vehicle
Cell
```

This is exactly what we want.

---

# 46. Domain Libraries Can Add Their Own Capabilities

Chemistry could define:

```text
interface Reactant
interface Product
interface Charged
interface Bondable
```

Physics could define:

```text
interface Massive
interface Charged
interface Collidable
```

Notice that:

```text
Charged
```

could potentially be shared between chemistry and physics.

This raises an important architectural point:

> **Capabilities themselves can be reusable cross-domain vocabulary.**

The extension ecosystem therefore isn't necessarily a strict tree.

It can be a graph:

```text
                mathematics
                /         \
           physics       statistics
             /  \           /
        chemistry        biology
              \            /
               common capabilities
```

---

# 47. Avoid Capability Name Collisions

Suppose two libraries define:

```text
Charged
```

with different meanings.

Namespaces solve the naming issue:

```text
physics.Charged
chemistry.Charged
```

But if they actually mean the same semantic capability, there should be a shared definition rather than duplicate incompatible versions.

This connects extension identity and type identity.

---

# 48. Versioned Type Identity

Suppose:

```text
physics.Projectile@1
```

changes structure in version 2.

A stored experiment referring to the old type must remain interpretable.

So type identity needs some relationship to extension/version provenance.

Not necessarily:

```text
type = string
```

but semantically:

```text
definition identity
+
version/compatibility information
```

---

# 49. Type Evolution

This becomes important for saved models.

Imagine:

```text
Projectile v1
    position
    velocity
```

then:

```text
Projectile v2
    position
    velocity
    mass
```

Can old models be loaded?

Potentially through migration:

```text
v1
 ↓
migration
 ↓
v2
```

This belongs partly to serialization/versioning rather than the core type system, but the extension model must account for it.

---

# 50. Higher-Kinded Abstractions?

We should be careful here.

Once we have:

```text
Collection<T>
Field<D,V>
Function<A,B>
Vector<D,T>
```

it's tempting to build an extremely sophisticated generic type system.

We should resist that until cases demand it.

Our design principle is still:

> **Don't add a type-system feature because it is theoretically elegant. Add it because the case space requires it.**

At this point we clearly need:

- parameterized types,
- generic functions,
- constraints.

But we haven't yet demonstrated that we need a full higher-kinded type system.

So don't add it yet.

---

# 51. Type-Level Dimensions

One area that probably *does* deserve careful support is dimensional structure.

For example:

```text
Vector<2>
Vector<3>
```

and:

```text
Matrix<3,3>
```

need dimensions.

Likewise:

```text
Quantity<Length>
Quantity<Velocity>
```

needs dimension information.

The type system therefore benefits from some form of compile-time/static metadata for dimensions.

But again, we shouldn't commit to the exact implementation yet.

---

# 52. Types and Runtime Values

The system needs a clear boundary:

```text
TYPE
    describes allowable structure/meaning

VALUE
    actual data

INSTANCE
    identified runtime semantic object
```

For example:

```text
type Projectile
```

then:

```text
ball : Projectile
```

then runtime:

```text
ball.position = (5m, 10m)
```

This gives us:

```text
Projectile
    ↓
ball
    ↓
state
```

---

# 53. Types and State Validity

A type alone may not guarantee every semantic invariant.

For example:

```text
type Projectile {
    mass : Quantity<Mass>
}
```

doesn't necessarily mean:

```text
mass > 0
```

unless constrained.

So:

```text
TYPE
+
CONSTRAINT
```

defines richer validity.

This reinforces our earlier decision that constraints shouldn't be swallowed by the type system.

---

# 54. Type Checking vs State Checking

This distinction becomes:

```text
TYPE CHECK
    "Can this operation make sense for these kinds of values?"

STATE VALIDATION
    "Does the current value satisfy the model's constraints?"
```

Example:

```text
mass * acceleration
```

may type-check.

But:

```text
mass = -5 kg
```

may violate a model constraint.

So:

```text
type-valid ≠ state-valid
```

Very important.

---

# 55. Extension Test: Radioactive Decay

Let's push the system.

Chemistry/physics defines:

```text
type Nucleus {
    isotope
    state
}
```

with:

```text
interface Decaying
```

and:

```text
process decay(...)
```

A collection:

```text
Collection<Nucleus>
```

can evolve.

The random source provides:

```text
Random
```

not a special "radioactivity" primitive.

The observation system records:

```text
time
remaining_count
decay_events
```

And representations can show:

```text
particles
count graph
histogram
half-life equation
```

No new core type is needed.

**Pass.**

---

# 56. Extension Test: Chemical Reaction

```text
A + B → C
```

Could be represented with:

```text
type Species
type Reaction
Collection<Molecule>
Relation<Bond>
Process<...>
Constraint<...>
```

The reaction extension defines the semantics.

Dynamic creation/destruction is already supported by composition/state.

**Pass.**

---

# 57. Extension Test: Graph Algorithms

Define:

```text
type Node
type Edge
type Graph
```

Graph can contain:

```text
Collection<Node>
Collection<Edge>
```

Edge relates two nodes.

An algorithm can operate on:

```text
Graph
```

or on a capability such as:


The type system is no longer simply:


It becomes:

```text

   │
   ▼

   │

   ├── structure
```

```text
 ↓

 ↓
```

This is the mechanism that allows extensions to remain independent.

# 66. Final 09.5b Verdict

**The extension model does not require us to fundamentally redesign the type system.**

But it **does require us to strengthen and clarify it around four things:**

### 1. Nominal semantic identity

Different domain concepts remain genuinely different types.

### 2. Explicit capabilities/interfaces

Different types can expose common semantic contracts.

### 3. Generic constrained behavior

Functions and behaviors can operate on capabilities rather than enumerating domain types.

### 4. Composition-based specialization

New concepts can be built from existing concepts and capabilities without requiring inheritance.

So the resulting philosophy is:

```text
                 SEMANTIC TYPE
                       │
          ┌────────────┼────────────┐
          │            │            │
       identity     structure   constraints
          │
          ▼
     CAPABILITIES
          │
          ▼
   GENERIC BEHAVIOR
          │
          ▼
      COMPOSITION
          │
          ▼
     DOMAIN TYPES
```

This gives us a very credible route from:

```text
core
```

to:

```text
physics
chemistry
biology
computer science
```

to:

```text
completely new user-defined domains
```

without continuously expanding the compiler's list of special cases.
