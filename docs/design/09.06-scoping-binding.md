# 09.6 Scoping / Binding

The central question is:

> **When the author writes a name, what does that name refer to?**

This sounds like an ordinary programming-language problem, but our DSL makes it substantially more interesting because a name may refer to a mathematical value, model object, property, parameter, function, collection element, field, process, view, or representation.

---

# 1. First distinction: name, binding, value

These three things must remain separate.

Consider:

```text
g = 9.81 m/s²
```

There are three concepts:

```text
NAME
    g

BINDING
    g → some semantic declaration

VALUE
    9.81 m/s²
```

So:

```text
Name ≠ Binding ≠ Value
```

This is foundational.

A name is merely a symbol used by the author.

A binding says what that symbol refers to.

The value is what that binding currently denotes.

---

# 2. Why binding matters so much here

Consider:

```text
ball.velocity
```

We need to resolve:

```text
ball
  ↓
which object?

velocity
  ↓
which property?

property
  ↓
what type?

value
  ↓
current state or derived value?
```

Or:

```text
speed = magnitude(velocity)
```

We need:

```text
speed
  ↓
new binding

magnitude
  ↓
function binding

velocity
  ↓
property binding
```

So binding is the mechanism connecting the author's source code to the semantic model.

---

# 3. What can have a name?

From everything we've designed so far, candidate named things include:

```text
system
type
object
property
variable
parameter
collection
relation
function
expression
equation
constraint
process
event
field
observation
dataset
projection
representation
view
interaction
operation
```

But this does **not** mean each needs a separate namespace.

We should minimize that complexity.

---

# 4. Candidate namespace model

A straightforward design would be:

```text
GLOBAL / MODULE
│
├── Types
├── Functions
├── Constants
└── Systems

SYSTEM
│
├── Objects
├── Collections
├── Relations
├── Parameters
├── Functions
├── Processes
├── Events
├── Observations
├── Views
└── ...
```

Then inside an object:

```text
OBJECT
│
├── Properties
└── Behaviors
```

But this may still be too many namespaces.

Let's derive it more carefully.

---

# 5. A useful distinction: declarations vs values

Some names identify **things**:

```text
Particle
ball
particles
gravity
velocity
```

Others produce **values**:

```text
magnitude
speed
position.x
```

So conceptually:

```text
NAME
├── TYPE-LEVEL NAME
│   └── Particle
│
└── VALUE-LEVEL NAME
    ├── ball
    ├── gravity
    ├── velocity
    └── speed
```

This gives us a conventional type/value namespace distinction.

---

# 6. Type names

For example:

```text
type Particle {
    position : Point<2>
    velocity : Vector<2>
}
```

`Particle` is a type-level binding.

Then:

```text
ball : Particle
```

`ball` is a value/object-level binding.

Therefore:

```text
Particle
```

and:

```text
ball
```

can coexist naturally.

---

# 7. System scope

A system creates a major lexical/environment boundary.

Conceptually:

```text
system Projectile {

    parameter g = 9.81 m/s²

    object ball {
        ...
    }

    process motion {
        ...
    }
}
```

Inside the system:

```text
g
ball
motion
```

are visible.

Outside:

```text
Projectile.g
Projectile.ball
```

might be accessible only if explicitly exposed.

This gives us encapsulation.

---

# 8. Object scope

Inside:

```text
object ball {
    position = ...
    velocity = ...
}
```

the properties can be referenced directly:

```text
position
velocity
```

or from outside:

```text
ball.position
ball.velocity
```

This creates a natural hierarchical binding structure:

```text
ball
└── position
└── velocity
└── mass
```

---

# 9. Property lookup

Suppose:

```text
object ball {
    position = (0, 0)
}
```

and:

```text
process motion {
    velocity = ...
}
```

If we write:

```text
position
```

inside `motion`, should that mean:

```text
motion.position
```

or:

```text
ball.position
```

or some global `position`?

We cannot allow arbitrary guessing.

This is where lexical and contextual scope matter.

---

# 10. Lexical scope first

A good base rule is:

> **Look in the nearest lexical scope first, then outward.**

For example:

```text
system S {
    g = 9.81

    process P {
        x = ...
    }
}
```

Inside `P`:

```text
x
```

resolves locally.

If `g` isn't local:

```text
g
```

resolves in the enclosing system.

Conceptually:

```text
P scope
   ↓
S scope
   ↓
module scope
   ↓
imports
```

This is predictable.

---

# 11. But model property lookup is different

There is an important complication.

Suppose:

```text
object ball {
    position = ...
}
```

and a process operates on `ball`.

Inside:

```text
process motion(ball) {
    ...
}
```

then:

```text
ball.position
```

is unambiguous.

This is preferable to magically injecting every property into process scope.

So our initial rule should be:

> **Object properties are normally accessed through an object binding unless explicitly introduced into local scope.**

That avoids mysterious resolution.

---

# 12. Explicit bindings

We can allow controlled shorthand.

Conceptually:

```text
with ball {
    position
    velocity
}
```

or perhaps process parameters:

```text
process motion(ball) {
    ...
}
```

Now `ball` is explicitly bound in the process scope.

This is much safer than implicit object selection.

---

# 13. Function scope

Consider:

```text
function square(x) {
    return x * x
}
```

`x` exists only within the function.

So:

```text
function scope
└── x
```

The function's parameters are local bindings.

---

# 14. Local variables

Inside behavior:

```text
process motion(ball) {

    acceleration = (0, -g)

    ...
}
```

`acceleration` could be a local binding.

We must distinguish it from:

```text
ball.acceleration
```

The latter belongs to model state.

The former may exist only during computation.

This gives us:

```text
LOCAL VALUE
≠
MODEL STATE
```

That's extremely important.

---

# 15. State binding vs local binding

For example:

```text
process motion(ball) {

    old_velocity = ball.velocity

    ball.velocity = ...
}
```

Here:

```text
old_velocity
```

is local computational state.

Whereas:

```text
ball.velocity
```

is semantic model state.

The binding system must preserve that distinction.

---

# 16. Parameters

Parameters introduce another category.

```text
parameter g = 9.81 m/s²
```

`g` is a named value but has special semantics.

It may be:

- externally controlled,
- exposed to UI,
- changed between experiments,
- recorded as experimental metadata,
- constrained,
- swept across ranges.

Therefore:

```text
g → Parameter binding → Quantity<Acceleration>
```

rather than simply treating it as an ordinary local variable.

---

# 17. Constants

We may also have:

```text
constant pi = 3.14159...
```

or perhaps `π` is built in.

A constant is:

```text
binding
+
immutable semantics
```

Again:

```text
constant ≠ parameter ≠ variable
```

even though all can produce values.

---

# 18. Derived bindings

Consider:

```text
speed := magnitude(ball.velocity)
```

This creates:

```text
speed
    ↓
derived binding
    ↓
expression
    ↓
ball.velocity
```

It does not create independent stored state.

Therefore:

```text
speed
```

can be recomputed when:

```text
ball.velocity
```

changes.

This is dependency tracking.

---

# 19. Binding graph

This leads to a useful internal representation:

```text
g
 ↓
acceleration
 ↓
velocity
 ↓
position
 ↓
trajectory
 ↓
plot
```

More generally:

```text
Binding A
    ↓ depends on
Binding B
    ↓ depends on
Binding C
```

The runtime can use this for:

- invalidation,
- recomputation,
- projection updates,
- optimization,
- scheduling.

---

# 20. Binding modes

We should classify bindings by how their value is obtained.

```text
Binding
├── Constant
├── Parameter
├── Stored
├── Derived
├── Computed
├── External
└── Local
```

For example:

```text
g                 → Parameter
ball.position     → Stored
speed              → Derived
temperature_sensor → External
old_velocity       → Local
π                  → Constant
```

This is probably more useful than creating separate language namespaces for all of them.

---

# 21. Read/write capability

Binding also needs access semantics.

Conceptually:

```text
Binding
├── readable?
├── writable?
└── observable?
```

Examples:

```text
speed
    read ✓
    write ✗

ball.position
    read ✓
    write ✓

g
    read ✓
    write ✓ through parameter controls
```

This connects directly to our interactive model.

---

# 22. Lexical scope vs semantic ownership

These should not be confused.

Consider:

```text
ball.position
```

The name `position` is lexically nested beneath `ball`.

But semantically it belongs to the model object.

Similarly:

```text
system.temperature
```

might be semantically owned by the system state.

So:

```text
LEXICAL SCOPE
```

answers:

> Where can I write this name?

while:

```text
SEMANTIC OWNERSHIP
```

answers:

> What model element does this binding belong to?

---

# 23. Collections

Now consider:

```text
particles : Collection<Particle>
```

A collection itself has a binding:

```text
particles
```

But its elements may be dynamically created.

So:

```text
particles[0]
```

is not necessarily a lexical binding.

It is an **indexed access expression**.

Likewise:

```text
particle.position
```

is a property lookup on a runtime object.

This distinction matters for the compiler.

---

# 24. Iteration scope

Suppose:

```text
for particle in particles {
    ...
}
```

Then:

```text
particle
```

is a local binding.

Its lifetime is the iteration body.

Conceptually:

```text
for scope
└── particle : Particle
```

This is ordinary lexical scoping.

But its value changes for each iteration.

---

# 25. Collection comprehensions

If the DSL supports something like:

```text
velocities = particles.map(p => p.velocity)
```

then:

```text
p
```

is a local binding within the lambda.

So:

```text
lambda scope
└── p : Particle
```

Again, ordinary lexical scope handles this nicely.

---

# 26. Fields and bound variables

Consider:

```text
E(x, y) = ...
```

Here `x` and `y` are bound variables.

They are not global model objects.

They're parameters of a mathematical function.

Therefore:

```text
E
└── function scope
    ├── x
    └── y
```

This is exactly why functions need their own lexical scopes.

---

# 27. Time variable

We also have:

```text
x(t)
```

Here `t` is a bound variable.

But there may also be a system simulation clock.

These should not be confused.

For example:

```text
function trajectory(t) ...
```

`t` is a function parameter.

Whereas:

```text
time
```

might refer to the current simulation time.

So:

```text
t
```

and:

```text
simulation_time
```

may have different bindings.

---

# 28. Process scope

Processes need special treatment because they interact with model state.

For example:

```text
process motion(ball) {
    ...
}
```

The process scope contains:

```text
ball
```

as a binding.

It may also contain:

```text
dt
t
local variables
temporary values
```

But model state remains accessed through semantic bindings.

---

# 29. Event scope

Events may introduce bindings too.

For example:

```text
on collision(a, b) {
    ...
}
```

Then:

```text
a
b
```

are event-local bindings.

Their existence is tied to the event occurrence.

This is especially useful for dynamic systems:

```text
on decay(atom) {
    ...
}
```

where `atom` identifies the entity involved in that event.

---

# 30. Interaction scope

An interaction can similarly bind targets.

Conceptually:

```text
on drag(target) {
    ...
}
```

`target` is an interaction-local binding.

But importantly:

```text
target
```

could resolve to a representation object first, then through semantic binding to a model object.

That gives us:

```text
input
 ↓
interaction scope
 ↓
representation target
 ↓
semantic target
```

---

# 31. View scope

Views introduce another interesting namespace.

For example:

```text
view scene {
    show ball
    show trajectory
}
```

Inside the view:

```text
ball
trajectory
```

refer to semantic sources.

But the view can also create presentation-local names:

```text
ball_visual
trajectory_plot
```

These should not accidentally become model objects.

So:

```text
MODEL SCOPE
≠
VIEW SCOPE
```

---

# 32. Projection bindings

A projection may establish a mapping:

```text
ball.position
    →
ball_visual.position
```

Internally this is a binding:

```text
source binding
        ↓
projection
        ↓
representation binding
```

The representation name doesn't become the model object's name.

This protects our:

> Model ≠ Representation

invariant.

---

# 33. Name shadowing

Should this be allowed?

```text
system S {
    x = 10

    process P {
        x = 20
    }
}
```

Probably yes for ordinary local bindings, but it can be dangerous in scientific code.

An author might accidentally shadow a model variable.

So we could allow shadowing lexically but issue a diagnostic:

```text
warning: local `x` shadows system binding `x`
```

For model properties, explicit qualification should make the distinction obvious.

---

# 34. Qualified names

We need a way to escape ambiguity.

Conceptually:

```text
system.gravity
ball.position
world.time
module.function
```

Qualified names provide deterministic access.

Potentially:

```text
self.position
```

inside an object/process.

For example:

```text
object ball {
    position = ...

    process {
        self.position
    }
}
```

This is likely useful.

---

# 35. `self`

A `self` binding can represent the current semantic object.

For example:

```text
object Particle {
    process {
        self.velocity
    }
}
```

This is useful for reusable object behavior.

But it should be introduced only where there is an actual semantic owner.

---

# 36. Binding object members

We can therefore define member lookup roughly as:

```text
a.b
```

means:

1. Resolve `a`.
2. Determine its semantic type.
3. Find member `b` in that type/schema.
4. Produce a member binding/reference.

For:

```text
ball.position
```

we get:

```text
ball : Particle
position : Property<Point<2>>
```

---

# 37. Dynamic members

Could objects gain properties dynamically?

Our generalized model allows dynamic structures, but allowing arbitrary runtime member creation makes static analysis harder.

For the DSL core, I recommend:

> **Object schemas are statically known, while object instances may dynamically appear/disappear.**

So:

```text
Particle
├── position
├── velocity
└── mass
```

is known.

But:

```text
particles
```

can dynamically contain 10, 100, or 1,000,000 particles.

This gives us dynamic simulation without sacrificing structural typing.

---

# 38. Relations

Relations introduce another lookup mechanism.

Suppose:

```text
bond(a, b)
```

or:

```text
a.connected_to
```

A relation may have:

```text
source
target
properties
identity
```

The binding system must distinguish relation instances from ordinary properties.

For example:

```text
bond.length
```

could be a property of the relation itself.

---

# 39. Namespace collision

Suppose we have:

```text
object ball
function ball(...)
type ball
```

Should all coexist?

I would avoid this.

A good rule is:

> **At a given scope, value-level names should not ambiguously refer to different semantic declarations.**

Type names can occupy a separate namespace.

Thus:

```text
type Particle
object particle
```

is fine.

But:

```text
object ball
function ball
```

should require overloading rules or be rejected.

For our first DSL version, rejection is simpler.

---

# 40. Imports and modules

Eventually we need:

```text
import physics
import geometry
import statistics
```

A module creates another binding environment.

Conceptually:

```text
Module
├── public bindings
└── private bindings
```

Imports introduce selected bindings into the current environment.

This is critical for our domain-library strategy.

The core language doesn't know:

```text
Projectile
Electron
Pendulum
```

until a library provides those definitions.

---

# 41. Extension and binding

For example:

```text
import physics.mechanics
```

could expose:

```text
Vector
Force
Projectile
integrate
...
```

But these are library definitions mapped onto the core semantic model.

So:

```text
CORE
 ↑
LIBRARY
 ↑
AUTHOR PROGRAM
```

Binding connects all three.

---

# 42. Closures

If functions can capture external values:

```text
g = 9.81 m/s²

function acceleration(v) {
    return ...
}
```

the function may reference `g`.

Then the function carries an environment:

```text
function
├── parameters
└── captured bindings
```

This is a closure.

We'll likely need it.

---

# 43. But model references create a special issue

Suppose:

```text
function energy(ball) {
    return ...
}
```

This function explicitly takes `ball`.

Good.

But if:

```text
function energy() {
    return ball.mass * ...
}
```

then it captures `ball`.

If `ball` is model state, the function is now dependent on dynamic state.

That may be useful, but the compiler should know the difference between:

```text
pure function
```

and:

```text
state-dependent function
```

This will matter later for computation and runtime scheduling.

---

# 44. Binding dependencies

We can model:

```text
speed := magnitude(ball.velocity)
```

as:

```text
speed
 ↓
magnitude
 ↓
ball.velocity
```

And:

```text
trajectory := observe ball.position over time
```

as:

```text
trajectory
 ↓
observation
 ↓
ball.position
```

This dependency graph is more fundamental than merely lexical scope.

---

# 45. Binding lifetime

Different bindings have different lifetimes.

```text
MODULE
    exists while module loaded

SYSTEM
    exists while system exists

OBJECT
    exists while object exists

PROCESS LOCAL
    exists during execution

EVENT LOCAL
    exists during event handling

ITERATION LOCAL
    exists during iteration

TEMPORARY INTERACTION
    exists during interaction transaction
```

This distinction will become useful when we implement dynamic entities and transactions.

---

# 46. Dynamic entity binding

Suppose:

```text
on collision {
    create Particle
}
```

A new object gets identity at runtime.

The **type** is known statically:

```text
Particle
```

but the instance binding is created dynamically.

So:

```text
type binding
    ↓ static

instance binding
    ↓ dynamic
```

This is exactly what we need for particle creation, chemical reactions, graph nodes, etc.

---

# 47. Destruction

Likewise:

```text
destroy particle
```

removes its active instance binding.

References to it then need defined semantics.

We need to distinguish:

```text
reference exists
```

from:

```text
referenced object currently exists
```

This connects to the invalid/pending/unavailable distinctions from the core model.

---

# 48. References and binding

A reference should therefore conceptually be:

```text
Reference<T>
```

with runtime state such as:

```text
valid
dangling
unavailable
```

For example, an event may retain a reference to an object that has since been destroyed.

The runtime needs defined behavior rather than silently dereferencing garbage.

---

# 49. Binding and interaction

This is where the earlier interactive model comes back.

Suppose the user drags a visual particle.

The interaction system might resolve:

```text
visual_particle
      ↓
representation binding
      ↓
projection
      ↓
model reference
      ↓
Particle.position
```

The name resolver itself doesn't perform this.

Instead:

```text
NAME RESOLUTION
```

handles source-level names.

Then:

```text
TARGET RESOLUTION
```

handles runtime interaction targets.

Keeping these separate is important.

---

# 50. Binding and observation

Similarly:

```text
observe ball.velocity
```

resolves:

```text
ball
 ↓
velocity
 ↓
model property
```

Then observation semantics take over.

Again:

```text
binding
≠
observation
```

Binding answers what is being referred to.

Observation answers how that value is sampled/read.

---

# 51. Binding and projections

Likewise:

```text
show ball.position
```

first resolves:

```text
ball.position
```

Then projection semantics determine how that value becomes a representation.

So:

```text
NAME
 ↓
BINDING
 ↓
MODEL SOURCE
 ↓
PROJECTION
 ↓
REPRESENTATION
```

This is a clean architecture.

---

# 52. Proposed environment model

Internally, we can think of every lexical scope as an environment:

```text
Environment
├── bindings
├── parent
└── metadata
```

For example:

```text
ModuleEnv
    ↓
SystemEnv
    ↓
ProcessEnv
    ↓
BlockEnv
```

Name lookup:

```text
lookup(name, current_env)
```

searches the appropriate environment chain.

---

# 53. But don't make semantic scopes purely lexical

The model has another structure:

```text
System
├── Object
│   └── Property
├── Collection
├── Relation
└── ...
```

This is a **semantic ownership graph**, not simply a lexical scope chain.

We therefore need both:

```text
LEXICAL ENVIRONMENT
```

and:

```text
SEMANTIC MODEL GRAPH
```

The compiler links the former to the latter.

---

# 54. Binding representation

A conceptual internal binding might contain:

```text
Binding
├── name
├── semantic identity
├── type
├── role
├── mutability
├── visibility
├── lifetime
├── owner
└── dependency information
```

For example:

```text
g
├── type: Quantity<Acceleration>
├── role: Parameter
├── writable: yes
├── owner: Projectile
└── identity: parameter#...
```

This is likely much closer to what the Rust compiler implementation will need than simply:

```rust
HashMap<String, Value>
```

---

# 55. Identity vs name

This deserves emphasis.

Two names can refer to the same thing:

```text
ball
b
```

if aliases are allowed.

Conversely, the same name may refer to different things in different scopes.

Therefore:

```text
NAME ≠ IDENTITY
```

The runtime semantic object should have stable identity independent of its source-level name.

This is especially important for:

- dynamic objects,
- references,
- relations,
- undo/redo,
- branching,
- serialization,
- interaction,
- replay.

---

# 56. Aliases

We may eventually support:

```text
alias b = ball
```

Then:

```text
b.position
ball.position
```

refer to the same semantic object.

But aliases should not create another object.

This is another case where identity matters.

---

# 57. Destructuring

Mathematical code benefits from destructuring.

For example:

```text
(x, y) = point
```

This introduces local bindings:

```text
x
y
```

Likewise:

```text
(a, b, c) = vector
```

Could be supported as syntactic sugar over pattern binding.

This is useful, but probably doesn't need to be a fundamental semantic construct.

---

# 58. Pattern binding

We may eventually have:

```text
for (node, edge) in graph.edges {
    ...
}
```

or:

```text
on collision(a, b)
```

Patterns simply introduce bindings.

So the semantic kernel can have:

```text
Pattern → bindings
```

without making destructuring itself a major semantic subsystem.

---

# 59. Scoping rules we can now propose

### Rule 1 Lexical lookup

Names resolve through lexical environments.

### Rule 2 Explicit model access

Model properties are normally accessed through their owning object/system.

### Rule 3 Local bindings win

Local bindings shadow enclosing bindings where allowed.

### Rule 4 Types have a distinct namespace

Type names don't collide with value names.

### Rule 5 Runtime entities have semantic identity

Their identity is independent of source-level names.

### Rule 6 Dynamic instances don't create dynamic types

A new `Particle` instance has the already-known `Particle` type.

### Rule 7 Derived values are bindings

They participate in dependency graphs.

### Rule 8 Model state and locals are distinct

A local variable doesn't automatically become model state.

### Rule 9 View names don't become model names

Presentation objects remain separate.

### Rule 10 Ambiguity must be rejected or explicitly resolved

No "guess what the author meant."

---

# 60. A complete example

Consider:

```text
system Projectile {

    parameter g = 9.81 m/s²

    object ball {
        position = (0 m, 0 m)
        velocity = (10 m/s, 15 m/s)
        mass = 1 kg
    }

    function speed(v) {
        return magnitude(v)
    }

    process motion(ball) {

        acceleration = (0 m/s², -g)

        ball.velocity = ball.velocity + acceleration * dt
        ball.position = ball.position + ball.velocity * dt
    }

    view scene {
        show ball
        show ball.position
    }
}
```

Let's resolve the bindings.

### System scope

```text
Projectile
├── g
├── ball
├── speed
├── motion
└── scene
```

### Object scope

```text
ball
├── position
├── velocity
└── mass
```

### Function scope

```text
speed
└── v
```

### Process scope

```text
motion
├── ball
├── acceleration
├── dt
└── inherited system bindings such as g
```

Then:

```text
ball.velocity
```

resolves:

```text
ball
 ↓
Particle/object instance
 ↓
velocity property
 ↓
stored model state
```

while:

```text
acceleration
```

is local computational state.

And:

```text
g
```

resolves outward to the system parameter.

---

# 61. What if `acceleration` were a model property?

Suppose instead:

```text
object ball {
    position
    velocity
    acceleration
}
```

Then:

```text
ball.acceleration
```

is model state.

Whereas:

```text
acceleration
```

inside a process remains a local binding unless explicitly qualified.

This gives us predictable behavior.

# 62. Binding and equations

Consider:

```text
F = m * a
```

This could involve:

```text
F → model property
m → model property
a → model property
```

or:

```text
F
m
a
```

could be local mathematical variables.

The surrounding semantic context determines their bindings.

But the type checker then checks:

```text
m * a
```

against:

```text
F
```

for dimensional compatibility.

Thus:

```text
binding → type → semantic validation
```

works as a pipeline.

# 63. Binding and function parameters

Consider:

```text
function kinetic_energy(m, v) {
    return 0.5 * m * magnitude(v)^2
}
```

The bindings are:

```text
m : Quantity<Mass>
v : Vector<..., Velocity>
```

The compiler can infer or verify the output:

```text
Quantity<Energy>
```

So scoping and typing cooperate:

```text
resolve names
      ↓
determine bindings
      ↓
obtain types
      ↓
type-check expressions
```

# 64. Binding and state evolution

Consider:

```text
ball.position = ...
```

Name resolution finds:

```text
ball.position
```

Type checking verifies:

```text
RHS : Point<2, Length>
```

Semantic analysis then sees:

```text
assignment to stored model property
```

Runtime semantics eventually turns it into:

```text
SET(ball.position, value)
```

This demonstrates why the previous artifacts fit together:

```text
SCOPING
   ↓
TYPE SYSTEM
   ↓
SEMANTIC MAPPING
   ↓
RUNTIME
```

# 65. Binding and dependency graphs

A derived binding:

```text
energy := 0.5 * mass * speed²
```

creates dependencies:

```text
energy
├── mass
└── speed
    └── velocity
```

If:

```text
velocity
```

changes, the runtime can invalidate:

```text
speed
energy
```

without recomputing unrelated values.

So binding isn't merely about resolving names during compilation.

It contributes to the runtime dependency graph.

# 69. Important invariant

We can now add:

> **A source-level name identifies a binding; a binding resolves to semantic identity/value; semantic identity is independent of the source name.**

This will be critical for:

- serialization,
- dynamic entities,
- undo/redo,
- branching,
- replay,
- collaborative editing,
- generated code,
- optimization.

---

# 70. Another important invariant

> **Lexical scope determines name visibility; semantic ownership determines what the name refers to in the model.**

Those are separate mechanisms.

This prevents the language from becoming a confusing mixture of ordinary programming scope and model structure.
