# 09.8 Error Model

## 1. The Core Question

Our DSL can fail at very different layers.

For example:

```text
x = 5 + "hello"
```

is fundamentally different from:

```text
dN/dt = -λN
```

where the equation is valid but the numerical solver fails to converge.

And both are different from:

```text
temperature → color
```

where the model is valid but a renderer cannot produce the requested visualization.

And all three are different from:

```text
user drags particle into forbidden region
```

where nothing has actually "gone wrong" with the runtime: the requested operation was simply rejected by the model's constraints.

So the first principle is:

> **An error is not one kind of thing.**

The system needs to distinguish **invalid descriptions, invalid states, failed computations, unavailable resources, rejected operations, and presentation failures.**

---

# 2. Deriving Error Categories From the System

Our existing architecture gives us several layers:

```text
SOURCE
  ↓
SEMANTIC MODEL
  ↓
STATE
  ↓
EVOLUTION / COMPUTATION
  ↓
OBSERVATION
  ↓
PROJECTION
  ↓
REPRESENTATION / VIEW
```

Interaction can enter at multiple points:

```text
USER
 ↓
INTERACTION
 ↓
OPERATION
 ↓
MODEL / STATE / RUNTIME / VIEW
```

Therefore failures can occur at each boundary.

A useful initial classification is:

```text
ERROR MODEL
│
├── AUTHORING
│   ├── Syntax
│   ├── Name / binding
│   ├── Type
│   └── Semantic
│
├── MODEL
│   ├── Invalid model
│   ├── Invalid state
│   └── Constraint violation
│
├── COMPUTATION
│   ├── Evaluation failure
│   ├── Numerical failure
│   ├── Solver failure
│   └── Resource limitation
│
├── EXTERNAL
│   ├── Missing input
│   ├── Invalid input
│   └── External failure
│
├── INTERACTION
│   ├── Invalid operation
│   ├── Rejected operation
│   └── Interaction failure
│
└── PRESENTATION
    ├── Projection failure
    ├── Representation failure
    └── Output failure
```

But this classification alone is not enough.

The important question is:

> **Which of these should actually be called an error?**

---

# 3. Error vs Invalid State vs Normal Condition

This distinction is fundamental.

Consider a radioactive simulation.

A nucleus decays.

That is **not an error**.

A stochastic process happens according to its model.

Likewise:

```text
particle reaches boundary
```

might be completely normal.

But:

```text
particle position = NaN
```

may indicate computational failure.

And:

```text
particle enters forbidden region
```

could be either:

- an invalid state,
- a constraint violation,
- or a valid state that triggers a collision event,

depending on the model.

Therefore:

> **The meaning of a condition comes from semantics, not from its appearance.**

---

# 4. Four Fundamental Kinds of "Something Went Wrong"

I think the model becomes much cleaner if we distinguish four broad categories.

## A. Diagnostic

Something is wrong with the **author's description**.

Example:

```text
circle radius = "large"
```

when radius requires a number.

Or:

```text
show ball.posotion
```

when `posotion` doesn't exist.

This happens before or during model construction.

---

## B. Invalid Semantic State

The model exists, but its state violates its own semantics.

Example:

```text
mass = -5 kg
```

if the model declares mass must be non-negative.

Or:

```text
triangle
    sides = 1, 2, 10
```

which cannot form a valid triangle.

The runtime has not necessarily crashed.

The state is simply invalid.

---

## C. Failed Operation / Computation

The requested operation was meaningful, but execution could not complete it.

Example:

```text
solve equation
```

but the numerical method fails to converge.

Or:

```text
read sensor
```

but the sensor communication times out.

---

## D. Presentation Failure

The underlying model remains valid, but something prevents it from being displayed or exported.

Example:

```text
3D model
    ↓
2D projection
    ↓
renderer
```

and the renderer cannot handle some geometry.

The scientific model should not become invalid merely because rendering failed.

---

# 5. Authoring Errors

These are encountered while turning source code into a semantic model.

### 5.1 Syntax error

The source cannot be parsed.

```text
object ball {
    position = (0, 0
}
```

The structure is incomplete.

---

### 5.2 Binding/name error

A referenced name cannot be resolved.

```text
show projectile.position
```

when `projectile` doesn't exist.

Or:

```text
x = y + 1
```

when `y` isn't available in the relevant scope.

---

### 5.3 Type error

The operation isn't valid for the involved types.

```text
position = 10 + "hello"
```

---

### 5.4 Unit/dimension error

This deserves its own diagnostic category because scientific DSLs depend heavily on dimensional correctness.

```text
velocity = 5 m + 3 s
```

or:

```text
distance = velocity + acceleration
```

The values might all individually be valid, but the operation is dimensionally meaningless.

---

### 5.5 Domain error

The operation is mathematically defined only over a particular domain.

For example:

```text
sqrt(-4)
```

when working in real numbers.

Or:

```text
log(-2)
```

in a real-valued context.

This is different from an ordinary type error.

---

### 5.6 Ambiguity

Suppose multiple bindings match:

```text
x
```

and the language cannot determine which one is intended.

That should be a diagnostic rather than silently choosing one.

---

# 6. Semantic Model Errors

Now suppose the program parses and type-checks.

It can still describe something that doesn't make semantic sense.

Example:

```text
system Triangle {
    constraint:
        a + b > c
        a + c > b
        b + c > a
}
```

is fine.

But a model could define mutually contradictory constraints:

```text
x > 10
x < 5
```

There may be no valid state.

So:

```text
SOURCE
  ↓
PARSE ✓
TYPE ✓
BIND ✓
SEMANTICS ✗
```

This is a **model diagnostic**, not a runtime crash.

---

# 7. Invalid State

This is one of the most important distinctions in the whole error model.

A simulation can exist while its current state is invalid.

For example:

```text
mass >= 0
```

but an operation produces:

```text
mass = -1 kg
```

The runtime may then have:

```text
STATE
status = INVALID
```

rather than:

```text
RUNTIME = CRASHED
```

This allows the system to do useful things with invalid states:

- show the violation,
- explain why it is invalid,
- prevent commitment,
- allow correction,
- roll back,
- continue in an explicitly permissive mode,
- use it as an educational demonstration.

Therefore:

> **Invalid state is a semantic condition, not necessarily an execution failure.**

---

# 8. Constraint Violation

Constraint violation deserves special treatment because it frequently happens during interaction.

Suppose:

```text
particle.position ∈ region
```

is required.

The user drags the particle outside.

The interaction pipeline becomes:

```text
INPUT
 ↓
DRAG
 ↓
TARGET = particle.position
 ↓
PROPOSED VALUE
 ↓
CONSTRAINT CHECK
 ↓
REJECT
```

This is not necessarily an error.

It can simply produce:

```text
OperationResult = Rejected
Reason = ConstraintViolation
```

The UI could then:

- snap the object back,
- prevent movement,
- show an explanation,
- highlight the constraint.

This is much cleaner than throwing an exception.

---

# 9. Computational Errors

Now consider:

```text
equation
    dN/dt = -λN
```

The equation itself is valid.

But the execution strategy could fail.

For example:

```text
MODEL
dN/dt = -λN

EXECUTION
RK method
dt = ...
```

could encounter:

- divergence,
- overflow,
- underflow,
- NaN,
- insufficient precision,
- excessive timestep,
- non-convergence,
- iteration limit,
- memory exhaustion.

These belong to the **computation layer**.

Crucially:

> **A solver failure does not mean the equation is invalid.**

That preserves one of our existing invariants:

```text
EQUATION ≠ SOLVER
```

---

# 10. Numerical Warning vs Numerical Failure

Not every numerical problem should be fatal.

For example:

```text
relative_error ≈ 0.001
```

might be perfectly acceptable.

The runtime may report:

```text
warning:
    numerical error exceeds preferred tolerance
```

while continuing.

Other situations may prevent a result:

```text
solver did not converge
```

Then:

```text
result = unavailable
reason = non_convergence
```

rather than inventing a value.

This leads to an important distinction:

```text
APPROXIMATE
    ↓
valid result with error estimate

UNSTABLE
    ↓
result may be unreliable

FAILED
    ↓
no valid result produced
```

---

# 11. Undefined vs Invalid vs Unknown vs Unavailable

Our refined model already proposed:

```text
valid
invalid
unknown
unavailable
pending
```

The error model should preserve these.

They mean different things.

### Undefined

The mathematical operation has no defined result in the current domain.

Example:

```text
1 / 0
```

in ordinary real arithmetic.

### Invalid

The model/state violates its semantic constraints.

### Unknown

The system does not currently know the value.

For example:

```text
temperature
```

before a sensor has supplied a reading.

### Pending

The computation has been requested but hasn't completed.

### Unavailable

The requested result cannot currently be obtained.

For example, a disconnected sensor.

### Failed

The system attempted the operation and execution failed.

These should **not** all collapse into `null`.

---

# 12. External Inputs

Our model allows:

```text
sensor
network
file
camera
microcontroller
live dataset
user
```

These introduce a new class of conditions.

For example:

```text
temperature = sensor.read()
```

The sensor may:

- be unavailable,
- return malformed data,
- timeout,
- return a value outside expected range,
- disconnect,
- provide stale data.

These are not necessarily model errors.

We should therefore preserve:

```text
MODEL
    valid

EXTERNAL INPUT
    unavailable
```

The model can then define what happens.

For example:

```text
if temperature unavailable:
    use last_value
```

or:

```text
if temperature unavailable:
    pause simulation
```

or:

```text
if temperature unavailable:
    mark observation incomplete
```

---

# 13. Interaction Errors

Consider:

```text
drag(ball.position)
```

Several things can happen.

### Valid operation

```text
drag → new position → commit
```

### Rejected operation

```text
drag → violates constraint → reject
```

### Invalid target

```text
drag → target isn't writable
```

### Interaction subsystem failure

For example, a device event could not be processed.

These should be distinct.

A particularly useful result model is conceptually:

```text
Operation
    ↓
Result
├── Committed
├── Rejected
├── Cancelled
└── Failed
```

Where:

```text
Rejected
```

means the model intentionally refused the operation.

While:

```text
Failed
```

means the system could not successfully perform an otherwise meaningful operation.

---

# 14. Transactional Failure

This connects directly to our interaction model.

Suppose:

```text
begin
    move particle
    change temperature
    create bond
    commit
```

If the final state violates a constraint:

```text
commit → validation failure
```

we don't want:

```text
particle moved ✓
temperature changed ✓
bond creation failed ✗
```

unless partial commits are explicitly supported.

The default should therefore be:

```text
BEGIN
 ↓
PROPOSED STATE
 ↓
VALIDATE
 ↓
COMMIT
```

or:

```text
BEGIN
 ↓
PROPOSED STATE
 ↓
INVALID
 ↓
ROLLBACK
```

Thus:

> **Failed transactional operations do not partially modify semantic state by default.**

This gives us a very strong invariant.

---

# 15. Projection and Presentation Errors

Suppose:

```text
model
  ↓
projection
  ↓
representation
  ↓
view
```

The model could be perfectly valid while projection fails.

Examples:

- projection requires a coordinate transformation that cannot be evaluated,
- representation cannot handle the generated geometry,
- renderer runs out of memory,
- font is unavailable,
- video encoder fails,
- export format doesn't support the representation.

These should remain outside model validity.

For example:

```text
MODEL = VALID
PROJECTION = FAILED
VIEW = UNAVAILABLE
```

not:

```text
MODEL = INVALID
```

---

# 16. Non-Invertible Projection Is Not an Error

This is another important consequence of 07 and 08.

Suppose:

```text
temperature → color
```

The projection is:

```text
300 K → blue
500 K → red
```

There is no unique inverse:

```text
red → ??? K
```

That does **not** mean the projection is erroneous.

It simply means:

```text
projection = read-only
```

If the author wants interaction:

```text
slider → temperature
```

they define an explicit interaction mapping.

Therefore:

> **Non-invertibility is a property of a projection, not a failure.**

---

# 17. Composition Errors

Our composition model introduces another important question.

Suppose:

```text
Motor
Battery
Wheel
Controller
```

are composed.

The motor requires:

```text
Voltage : Quantity<Voltage>
```

but the connection provides:

```text
Temperature
```

That's an interface/type mismatch.

But suppose everything is semantically compatible and a runtime subsystem fails.

Then only that subsystem may fail.

We therefore want **localized failure**:

```text
Vehicle
├── Battery       VALID
├── Motor         FAILED
├── Controller    VALID
└── Wheels        VALID
```

rather than automatically declaring the whole system meaningless.

The parent system can then decide whether:

```text
motor failure → stop entire simulation
```

or:

```text
motor failure → degrade vehicle behavior
```

or:

```text
motor failure → display diagnostic
```

This is another place where the DSL shouldn't hard-code one policy.

---

# 18. Error Propagation

Errors/statuses therefore need propagation semantics.

For example:

```text
sensor
 ↓
temperature
 ↓
heat equation
 ↓
field
 ↓
color projection
```

If the sensor is unavailable:

```text
temperature = unavailable
```

Then the equation may produce:

```text
heat field = pending/unavailable
```

Then:

```text
color projection = unavailable
```

But the system itself isn't necessarily invalid.

So we get a dependency chain:

```text
SOURCE CONDITION
       ↓
DEPENDENT RESULT
       ↓
DEPENDENT REPRESENTATION
```

The runtime should preserve the **cause**.

Otherwise users see:

> "Renderer failed"

when the actual cause was:

> "Temperature sensor disconnected."

---

# 19. Dependency-Aware Diagnostics

This fits our composition/dependency model.

Suppose:

```text
A → B → C → D
```

and `A` fails.

We should distinguish:

```text
A = FAILED
B = UNAVAILABLE because A failed
C = UNAVAILABLE because B failed
D = UNAVAILABLE because C failed
```

rather than producing four unrelated errors.

This suggests that statuses should carry provenance:

```text
status
reason
cause
dependency
```

---

# 20. Cycles Are Not Automatically Errors

Our composition model explicitly allows cycles.

For example:

```text
x depends on y
y depends on x
```

This might represent a valid coupled system.

Similarly:

```text
A → B → C → A
```

could be feedback.

Therefore:

```text
cycle detected
```

is not automatically an error.

It becomes an error only if the particular semantic construct requires an acyclic dependency graph.

For example:

```text
a := b + 1
b := a + 1
```

may be unsolvable as a simple derived-value dependency.

Whereas:

```text
feedback process
```

can legitimately contain a cycle.

So:

> **Cycles are semantic-context dependent, not universally invalid.**

---

# 21. Static Diagnostics vs Runtime Status

We can now make an important separation.

## During authoring

We have:

```text
Diagnostics
```

Examples:

```text
syntax error
type mismatch
unit mismatch
unresolved name
invalid equation
ambiguous binding
```

These prevent or warn about constructing a valid model.

---

## During execution

We have:

```text
Runtime / computation status
```

Examples:

```text
pending
converging
non-convergent
overflow
external input unavailable
resource exhausted
```

---

## During model evolution

We have:

```text
State status
```

Examples:

```text
valid
invalid
constraint violated
undefined
unknown
```

---

## During interaction

We have:

```text
Operation result
```

Examples:

```text
committed
rejected
cancelled
failed
```

---

## During presentation

We have:

```text
Presentation status
```

Examples:

```text
projected
unavailable
render failed
export failed
```

This gives us a much cleaner architecture than one universal `Error`.

---

# 23. The Deeper Model

After separating them, I think we should avoid making:

```text
Error
```

a giant universal semantic type.

Instead, we have three related concepts:

```text
DIAGNOSTIC
STATUS
RESULT
```

### Diagnostic

Describes a problem discovered by the system.

```text
where
what
why
severity
```

### Status

Describes the current condition of something.

```text
state.status = invalid
computation.status = pending
external.status = unavailable
```

### Result

Describes what happened when an operation was attempted.

```text
operation → committed
operation → rejected
operation → failed
```

This is considerably cleaner.

---

# 24. Diagnostic Structure

A diagnostic should conceptually contain:

```text
Diagnostic
├── severity
├── category
├── message
├── location
├── target
├── cause
├── expected
├── actual
└── related information
```

Severity can be:

```text
ERROR
WARNING
INFO
```

Potentially:

```text
HINT
```

but that doesn't need to be fundamental.

---

# 25. Error Messages Should Explain Semantics

Compare:

```text
Error: invalid value
```

with:

```text
Cannot assign 5 seconds to velocity.

Expected:
    Quantity<Length / Time>

Received:
    Quantity<Time>
```

The second is much more useful.

For scientific education, this becomes even more important.

The system could explain:

```text
Acceleration has units m/s².

You attempted to add:
    4 m/s
    2 m/s²

These quantities have different dimensions.
```

Thus the error model isn't merely for developers.

It can become part of the **Education layer**.

---

# 26. Errors as Educational Events

This is a particularly interesting consequence of the DSL.

Suppose a student constructs:

```text
F = m + a
```

The system can treat the resulting diagnostic as educational information:

```text
Conceptual mistake:
    mass and acceleration cannot be added directly.

Try:
    F = m × a
```

The core system doesn't need to know pedagogy.

Instead:

```text
Diagnostic
    ↓
Education layer
    ↓
Feedback
```

This preserves our architecture.

---

# 27. Warnings Are Not Errors

Consider:

```text
simulation timestep = 0.5 s
```

The system may know that:

```text
recommended timestep < 0.01 s
```

That doesn't necessarily make the model invalid.

So:

```text
WARNING
```

can communicate:

> "This is allowed, but the result may be inaccurate."

This is especially important for scientific computation.

---

# 28. Fatality Should Not Be a Semantic Category

We might be tempted to define:

```text
fatal error
recoverable error
```

But that is actually a **runtime policy**.

For example:

```text
solver failed
```

could mean:

- stop the simulation,
- fall back to another solver,
- reduce timestep,
- display partial result,
- let the user intervene.

Therefore the semantic error model should describe:

```text
what happened
```

while runtime policy determines:

```text
what to do about it
```

This mirrors our existing separation:

```text
MODEL ≠ EXECUTION STRATEGY
```

---

# 29. Error Recovery

Recovery should therefore be handled by the layer capable of making the decision.

Examples:

```text
Numerical instability
    ↓
reduce timestep
    ↓
retry
```

or:

```text
Sensor unavailable
    ↓
use last known value
```

or:

```text
Constraint violation
    ↓
rollback
```

or:

```text
Renderer failure
    ↓
switch representation
```

Potentially:

```text
3D renderer unavailable
    ↓
2D projection
```

This becomes powerful because failure doesn't necessarily terminate the system.

---

# 30. Failure and Fallback

Our model therefore supports:

```text
PRIMARY
   ↓
FAIL
   ↓
FALLBACK
   ↓
RESULT
```

For example:

```text
GPU computation
    ↓ failure
CPU computation
```

or:

```text
high-resolution representation
    ↓ unavailable
simplified representation
```

or:

```text
live data
    ↓ unavailable
recorded dataset
```

But again, these are runtime/library policies, not necessarily core DSL semantics.

---

# 31. Partial Results

Scientific computation sometimes produces useful partial results.

For example:

```text
simulation:
    0 → 9.4 seconds ✓
    9.4 → 10 seconds ✗
```

We shouldn't necessarily throw away the first 9.4 seconds.

The computation can expose:

```text
result
├── data
├── completion = partial
└── failure = ...
```

This is especially useful for:

- long simulations,
- experiments,
- data analysis,
- batch computation,
- rendering,
- video generation.

---

# 32. Deterministic Failures

Our provenance model also applies to errors.

If:

```text
seed
initial state
parameters
execution configuration
```

are identical, a deterministic simulation should produce equivalent failure conditions too.

That helps with:

```text
replay
debugging
education
testing
scientific reproducibility
```

An error should therefore be capable of carrying enough provenance to reproduce its cause when appropriate.

---

# 33. What Should the DSL Author Actually See?

We don't want authors writing:

```text
try {
    ...
} catch NumericalInstability {
    ...
}
```

everywhere unless such behavior is genuinely needed.

Most errors should be handled by the compiler/runtime automatically.

The author should normally express **semantic recovery policies only when they matter to the model**.

For example:

```text
when sensor unavailable:
    use last_temperature
```

is meaningful model behavior.

But:

```text
when renderer allocation fails:
    retry malloc
```

belongs in the implementation/runtime.

This maintains the distinction:

```text
MODEL SEMANTICS
        vs
RUNTIME ENGINEERING
```

---

# 35. Error Propagation Principle

One of the strongest rules we can establish is:

> **A failure should propagate only as far as its semantics require.**

Examples:

```text
renderer failure
    ≠ model failure
```

```text
sensor unavailable
    ≠ equation invalid
```

```text
solver failure
    ≠ equation invalid
```

```text
constraint rejection
    ≠ runtime failure
```

```text
invalid state
    ≠ runtime crash
```

```text
non-invertible projection
    ≠ projection failure
```

```text
warning
    ≠ error
```

This is probably one of the most important invariants in the entire runtime.

---

# 36. Error Model and Composition

For composed systems:

```text
SYSTEM
├── A
├── B
├── C
└── D
```

failure should be represented locally:

```text
A = valid
B = failed
C = unavailable because B
D = valid
```

The parent system then determines whether the overall system can continue.

Possible parent status:

```text
healthy
degraded
blocked
failed
```

I would **not** make these core semantic statuses yet. They look more like runtime aggregation policies.

---

# 37. Candidate Core Error Model

After minimizing everything we've discussed:

```text
ERROR MODEL
```

Some of these can probably be further generalized.

```text

overflow
underflow
```

Likewise:

```text

```

can be a reason for:

```text

```

or:

```text

```

depending on whether we're describing a state or an attempted operation.

# 38. Revised Semantic Layer

I think the cleanest architecture is now:

```text
SEMANTIC SYSTEM
│
├── VALUES
├── DOMAINS
├── OBJECTS
├── STATE
├── RELATIONS
├── BEHAVIOR
├── CONTEXT
├── OBSERVATION
├── PROJECTION
├── COMPOSITION
└── VALIDITY
```

Where **Validity** is part of the semantic system, while diagnostics/results surround it.

Then:

```text
VALIDITY
    │
    ├── state validity
    ├── constraint validity
    └── semantic validity
```

And outside the semantic model:

```text
EXECUTION
    ├── computation status
    ├── operation results
    ├── external resource status
    └── runtime failures

PRESENTATION
    ├── projection status
    ├── rendering status
    └── output status
```

# 40. Final 09.8 Conclusions

### Fundamental distinctions

```text
DIAGNOSTIC ≠ STATUS ≠ RESULT
```

```text
INVALID STATE ≠ RUNTIME FAILURE
```

```text
CONSTRAINT REJECTION ≠ ENGINE FAILURE
```

```text
SOLVER FAILURE ≠ EQUATION INVALIDITY
```

```text
EXTERNAL INPUT FAILURE ≠ MODEL FAILURE
```

```text
PROJECTION FAILURE ≠ MODEL FAILURE
```

```text
RENDER FAILURE ≠ PROJECTION FAILURE
```

```text
WARNING ≠ ERROR
```

```text
UNAVAILABLE ≠ INVALID
```

```text
PENDING ≠ FAILED
```

```text
UNDEFINED ≠ UNKNOWN
```

### Core principles

1. **Errors belong to layers.**
2. **Invalidity is not the same as execution failure.**
3. **A rejected operation is not necessarily an error.**
4. **Computation failure must not invalidate the scientific model automatically.**
5. **Presentation failure must not invalidate the model.**
6. **Failures should retain causal provenance.**
7. **Failure propagation should follow dependencies.**
8. **Composition should localize failures where possible.**
9. **Recovery policy belongs to the appropriate runtime/model layer.**
10. **Transactions should prevent partial semantic mutation by default.**
11. **Warnings should allow execution when semantics remain valid.**
12. **Educational layers can consume diagnostics as meaningful feedback.**
13. **Domain-specific failure reasons should be extensible rather than hard-coded into the core.**
14. **The core should describe what happened; runtime policy determines what to do about it.**
