# 09.9 Extension Model

## 1. The Fundamental Principle

We have deliberately established:

```text
Projectile ≠ Core Primitive
Atom       ≠ Core Primitive
Molecule   ≠ Core Primitive
Pendulum   ≠ Core Primitive
Graph      ≠ Core Primitive
Reaction   ≠ Core Primitive
Particle   ≠ Core Primitive
```

But that does **not** mean they should be awkward to use.

Ideally, an author should be able to write:

```text
projectile ball
```

almost as naturally as:

```text
object ball
```

The difference is that `projectile` should be **defined using the core language**.

Therefore:

> **Extensions should add vocabulary and reusable semantics, not secretly add new fundamental execution mechanisms.**

---

# 2. Three Layers of the Language

This suggests a very important architecture:

```text
                    DSL
                     │
        ┌────────────┴────────────┐
        │                         │
     CORE DSL                EXTENSION DSL
        │                         │
        │              ┌──────────┼──────────┐
        │              │          │          │
        │           Physics    Chemistry     CS
        │
        └──────────────┬─────────────────────┘
                       │
                     RUNTIME
```

For example:

```text
core
├── mathematics
├── geometry
├── collections
├── time
├── dynamics
├── observation
└── presentation

physics
├── mechanics
├── electromagnetism
├── thermodynamics
├── waves
└── relativity

chemistry
├── atoms
├── molecules
├── reactions
├── kinetics
└── equilibrium

computer_science
├── graphs
├── algorithms
├── networks
└── automata
```

But there is an important constraint:

> **An extension must ultimately lower to concepts the core understands.**

---

# 3. What Exactly Is an Extension?

An extension could introduce several things.

```text
EXTENSION
├── TYPE
├── FUNCTION
├── VALUE
├── PROPERTY
├── RELATION
├── CONSTRAINT
├── BEHAVIOR
├── PROCESS
├── EVENT
├── OBSERVATION
├── PROJECTION
├── REPRESENTATION
├── INTERACTION
└── COMPOSITE SYSTEM
```

So "extension" isn't just a new type.

It is a mechanism for defining **new semantic vocabulary**.

---

# 4. Example: Projectile

Suppose the core provides:

```text
object
property
vector
quantity
process
equation
constraint
```

Then a physics extension could define:

```text
type Projectile {
    position : Point<2>
    velocity : Vector<2>
    mass     : Quantity<Mass>
}
```

Then define its behavior:

```text
process projectile_motion(p : Projectile) {
    ...
}
```

And perhaps:

```text
function kinetic_energy(p : Projectile)
    = 1/2 * p.mass * |p.velocity|²
```

The important thing is that `Projectile` is not magically understood by the runtime.

It expands into core semantics.

---

# 5. Extension = Definition + Composition

This gives us a powerful principle:

```text
EXTENSION
=
CORE DEFINITIONS
+
COMPOSITION
+
SEMANTIC CONTRACTS
```

For example:

```text
Projectile
    ↓
Entity
    ├── position
    ├── velocity
    └── mass

Behavior
    └── acceleration

Constraint
    └── mass > 0

Observation
    └── trajectory

Projection
    └── position → visual point
```

Nothing fundamental has been added.

We've simply packaged a useful concept.

---

# 6. But This Isn't Enough

There is a deeper problem.

Suppose we define:

```text
type Projectile { ... }
```

Can another author extend it?

For example:

```text
type GuidedProjectile extends Projectile {
    target : Point<2>
}
```

We could introduce traditional inheritance.

But that would potentially pull the language toward an object-oriented class hierarchy.

And our composition model deliberately avoided inheritance as the primary reuse mechanism.

So we need to distinguish:

```text
TYPE EXTENSION
```

from:

```text
INHERITANCE
```

---

# 7. Composition Should Remain Primary

Instead of:

```text
GuidedProjectile
    extends Projectile
```

we could conceptually have:

```text
Guidance
├── target
├── steering behavior
└── guidance process

Projectile
├── position
├── velocity
└── motion process

GuidedProjectile
├── Projectile
└── Guidance
```

This is composition.

The resulting object can satisfy multiple interfaces:

```text
Projectile
Positioned
Guided
Collidable
Observable
```

This is much more compatible with our previous composition model.

---

# 8. Interfaces Become Critical

Our composition artifact already introduced interfaces.

They become even more important here.

An extension can define:

```text
interface Positioned {
    position : Point<2>
}
```

Then:

```text
Projectile implements Positioned
Particle implements Positioned
Molecule implements Positioned
Vehicle implements Positioned
```

A generic behavior can then operate on the interface:

```text
function distance_between(a : Positioned, b : Positioned)
```

Now we get reuse without inheritance.

---

# 9. Semantic Interfaces

These aren't necessarily programming interfaces.

They describe **semantic capabilities**.

Examples:

```text
Positioned
Massive
Charged
Rotatable
Observable
Renderable
Collidable
TimeDependent
Stochastic
Container
Connectable
```

But even these names shouldn't necessarily become core keywords.

They can be extension-defined interfaces.

For example, `Charged` could mean:

```text
interface Charged {
    charge : Quantity<ElectricCharge>
}
```

Then an electrostatic force library can operate on anything satisfying that interface.

---

# 10. Capability-Based Extensions

This gives us a much more scalable structure:

```text
Concept
   ↓
Capabilities
   ↓
Behaviors
```

For example:

```text
Particle
 ├── Positioned
 ├── Massive
 └── Charged
```

A physics law can then say conceptually:

```text
if A and B are Charged:
    ...
```

It doesn't need to know whether they are:

- electrons,
- ions,
- dust particles,
- charged spheres,
- fictional objects.

That is powerful.

---

# 11. Extension-Defined Laws

Now consider physics.

We don't want:

```text
core:
    NewtonSecondLaw
    CoulombLaw
    HookeLaw
    OhmLaw
```

Those are domain concepts.

Instead, an extension can define them.

For example:

```text
law NewtonSecondLaw {
    equation:
        F = m * a
}
```

But remember our semantic mapping:

```text
EQUATION ≠ SOLVER
```

So defining the law doesn't automatically prescribe how the equation is solved.

The runtime can use whatever compatible computation strategy exists.

---

# 12. A Domain Extension Can Be Mostly Ordinary DSL

This is the really important part.

Imagine a `physics.mechanics` library.

It could define:

```text
type Mass
type Momentum
type Force
type Acceleration
type Position
type Velocity
```

along with:

```text
function momentum(...)
function kinetic_energy(...)
function potential_energy(...)
```

and:

```text
process NewtonianMotion(...)
```

and:

```text
constraint mass > 0
```

and:

```text
projection position → trajectory
```

The physics library therefore looks like **DSL code**, not compiler source code.

That makes the system self-hosting to a significant degree.

---

# 13. But Some Extensions Need More Than DSL

Now we hit the boundary.

Suppose somebody wants:

```text
GPU particle simulation
```

The mathematical model can be defined in the DSL.

But executing 100 million particles efficiently may require:

- GPU kernels,
- SIMD,
- specialized memory layouts,
- parallel scheduling,
- custom numerical methods.

Likewise, a symbolic algebra system may need sophisticated algorithms.

A chemistry package might need a specialized molecular mechanics engine.

Therefore:

> **Not every extension must be implemented entirely in the DSL.**

We need two extension classes.

---

# 14. Declarative Extensions

These are expressible using existing language capabilities.

```text
DSL EXTENSION
    ↓
CORE SEMANTICS
```

Examples:

- projectile,
- pendulum,
- triangle,
- graph,
- population model,
- simple chemical reaction,
- standard mathematical functions,
- educational widgets.

---

# 15. Native/Runtime Extensions

These provide implementations for capabilities that cannot practically be expressed efficiently in DSL alone.

```text
DSL SEMANTICS
      ↓
EXTENSION INTERFACE
      ↓
NATIVE IMPLEMENTATION
```

Examples:

- GPU backend,
- specialized ODE solver,
- symbolic algebra engine,
- molecular dynamics engine,
- video encoder,
- hardware sensor interface,
- optimized graph algorithm,
- WebGPU renderer.

The key constraint:

> **Native extensions implement an already-understood semantic contract; they should not redefine the meaning of the core language.**

---

# 16. Semantic Contracts

This becomes essential.

Suppose we provide an optimized solver.

The extension shouldn't just say:

```text
run my_magic_solver()
```

Instead it should satisfy a contract like:

```text
Input:
    differential system
    initial state
    parameters
    numerical configuration

Output:
    state evolution
    error information
    convergence information
```

The runtime knows what that means.

The solver can be swapped without changing the model.

```text
MODEL
 │
 ├── Solver A
 ├── Solver B
 └── Solver C
```

Same semantics.

Different execution strategies.

---

# 17. Extension Points

We can now identify explicit extension points:

```text
EXTENSION POINTS
│
├── TYPE SYSTEM
├── VALUES / OPERATORS
├── FUNCTIONS
├── BEHAVIORS
├── PROCESSES
├── EVENTS
├── CONSTRAINTS
├── COMPUTATION
├── OBSERVATION
├── PROJECTION
├── REPRESENTATION
├── INTERACTION
├── INPUT SOURCES
└── OUTPUT TARGETS
```

This is much broader than "plugins."

---

# 18. Type Extensions

A domain can define types.

For example:

```text
type Charge = Quantity<ElectricCharge>
```

or a structured semantic type:

```text
type Atom {
    atomic_number : Integer
    ...
}
```

The type system still knows the underlying structure.

This lets generic language mechanisms work on it.

---

# 19. Operator Extensions

A domain may need meaningful operators.

For example, vectors already have:

```text
+
-
*
/
dot
cross
```

A complex-number extension may define appropriate operations.

A matrix extension can define:

```text
A * B
A⁻¹
det(A)
```

The extension provides semantics for those operations.

But the compiler/runtime still checks their types.

---

# 20. Function Extensions

A library can introduce:

```text
sin
cos
exp
log
```

or domain functions:

```text
kinetic_energy
electric_field
reaction_rate
```

These should behave like ordinary functions from the language's perspective.

That is important because it prevents the core from accumulating:

```text
if function == sin ...
if function == kinetic_energy ...
if function == ...
```

---

# 21. Behavior Extensions

A domain can package reusable behavior.

For example:

```text
behavior ProjectileMotion {
    ...
}
```

Another model can simply attach it.

This gives us a distinction:

```text
TYPE
    describes what something is

BEHAVIOR
    describes what it does

INTERFACE
    describes what it provides/requires
```

That is a useful separation.

---

# 22. Representation Extensions

This is especially important for your Manim-like goal.

A domain concept shouldn't need the core renderer to know what an atom is.

Instead:

```text
Atom
 ↓
AtomProjection
 ↓
AtomRepresentation
```

The chemistry library can define how an atom is normally represented.

For example:

```text
atom
├── nucleus representation
├── electron representation
└── labels
```

The core only sees:

```text
Projection → Representation
```

---

# 23. Multiple Representations Per Extension

A domain extension can provide several representations.

For a function:

```text
f(x)
```

we might have:

```text
Graph
Equation
Table
Derivative
Animation
```

For a chemical reaction:

```text
A + B → C
```

we could have:

```text
Symbolic equation
Particle animation
Molecular view
Concentration graph
Energy diagram
```

All can consume the same model.

This is exactly why we separated:

```text
MODEL
    ↓
PROJECTION
    ↓
REPRESENTATION
```

---

# 24. Interaction Extensions

The same applies to interaction.

A chemistry extension might provide:

```text
drag atom
```

or:

```text
add reactant
```

A graph extension might provide:

```text
click node
connect nodes
delete edge
```

But these ultimately lower to generic operations:

```text
CREATE
DESTROY
CONNECT
DISCONNECT
SET
MODIFY
SELECT
OBSERVE
```

The domain library gives them meaningful names and behavior.

---

# 25. Extension Packages

Now we can think about packaging.

Conceptually:

```text
package physics.mechanics
```

could contain:

```text
types/
functions/
behaviors/
laws/
observations/
projections/
representations/
interactions/
documentation/
examples/
```

Similarly:

```text
package chemistry
package biology
package computer_science
package statistics
```

The core remains small.

---

# 26. Imports

A user could then write something conceptually like:

```text
use physics.mechanics
```

and gain access to:

```text
Projectile
Pendulum
RigidBody
Force
Momentum
NewtonianMotion
...
```

The language itself hasn't changed.

The **available vocabulary** has changed.

That's a crucial distinction.

---

# 27. Namespaces

Extensions need namespace isolation.

Without it:

```text
Graph
```

could mean:

- mathematical graph,
- bar graph,
- dependency graph,
- circuit graph,
- molecular graph.

So:

```text
math.Graph
cs.Graph
statistics.Graph
chemistry.Graph
```

could coexist.

Imports can provide aliases.

This connects directly to 09.6 Scoping/Binding.

---

# 28. Versioning

Extensions need versioning.

Suppose:

```text
physics.mechanics 1.0
```

defines `Projectile`.

Later:

```text
physics.mechanics 2.0
```

changes its semantics.

Old simulations need to remain reproducible.

Therefore experiments should record:

```text
model version
extension versions
parameters
initial state
execution configuration
random seed
external inputs
```

This follows directly from our provenance model.

---

# 29. Semantic Versioning Is Not Enough

There's a deeper issue.

An extension could change:

```text
Projectiles now use air resistance by default.
```

That's not merely an API change.

It changes scientific behavior.

Therefore extension metadata should distinguish:

```text
API compatibility
```

from:

```text
semantic/model compatibility
```

A simulation needs to know whether its **meaning** changed.

---

# 30. Extension Dependencies

Extensions can depend on other extensions.

For example:

```text
physics.mechanics
       ↓
geometry
       ↓
mathematics
```

Chemistry might depend on:

```text
chemistry
├── mathematics
├── statistics
└── physics
```

But dependency direction should remain explicit.

```text
extension A
    requires
extension B
```

not implicit compiler magic.

---

# 31. Circular Extension Dependencies

Again, cycles shouldn't automatically be forbidden.

For example:

```text
physics
 ↕
chemistry
```

could theoretically share concepts.

But the package/module system may require an acyclic **definition dependency graph** for compilation.

That's different from semantic model cycles.

We therefore distinguish:

```text
MODEL CYCLE
≠
MODULE DEPENDENCY CYCLE
```

The former may be valid.

The latter may or may not be supported by the module system.

---

# 32. Extension Authority

Here's another important question:

> Can extensions modify existing core semantics?

I think the answer should be **no** in the normal model.

An extension can:

```text
add types
add functions
add behaviors
add projections
add representations
add interactions
add computation implementations
```

But shouldn't redefine:

```text
what assignment means
what a quantity means
what state means
what a function means
what a transaction means
```

Otherwise two extensions could change the language underneath each other.

So:

> **Extensions add semantics; they do not redefine core semantics.**

---

# 33. Controlled Operator Extension

There is one exception worth investigating.

Suppose an extension wants:

```text
A ⊗ B
```

for a domain-specific operation.

That's probably fine if it declares:

```text
⊗ : A × B → C
```

and the type system can verify it.

The extension is adding an operator **meaning**, not changing existing `+`.

Even then, operator overloading needs strict rules to avoid ambiguity.

---

# 34. Domain Libraries Should Be Composable

Now we can build something interesting.

A "vehicle" doesn't have to belong exclusively to physics.

It can combine:

```text
mechanics
electronics
control_systems
energy
geometry
networking
```

Conceptually:

```text
Vehicle
├── mechanics
├── motor
├── battery
├── controller
├── sensors
└── network
```

Each comes from different extensions.

This is exactly what our composition model was designed for.

---

# 35. Extension vs DSL Syntax

We should also be careful not to make every extension introduce new syntax.

Bad direction:

```text
projectile ...
pendulum ...
molecule ...
reaction ...
graph ...
algorithm ...
```

each with special syntax rules.

That creates a language that grows indefinitely.

Better:

```text
CORE SYNTAX
       ↓
EXTENSION DEFINITIONS
       ↓
DOMAIN VOCABULARY
```

An extension can provide convenient syntax only if the mechanism is generic.

---

# 36. Macros / Derived Syntax

This raises the possibility of a generic **derived syntax mechanism**.

For example, a high-level construct:

```text
experiment decay {
    ...
}
```

could lower to:

```text
system
snapshot
parameters
execution
observations
results
```

But we need to decide whether this should be:

- a macro system,
- syntactic sugar,
- a compiler transform,
- a library construct,
- or simply ordinary DSL composition.

My current inclination is:

> **Prefer ordinary semantic composition first; introduce macros only where the repeated syntax genuinely justifies them.**

We don't want a macro language accidentally becoming a second programming language.

---

# 37. Extension-Level Abstraction

There should be several levels.

```text
CORE
  ↓
FOUNDATIONAL LIBRARY
  ↓
DOMAIN LIBRARY
  ↓
SPECIALIZED LIBRARY
  ↓
USER PROJECT
```

For example:

```text
CORE
 ↓
mathematics
 ↓
physics
 ↓
mechanics
 ↓
vehicle_dynamics
 ↓
my_vehicle_model
```

Or:

```text
CORE
 ↓
mathematics
 ↓
statistics
 ↓
epidemiology
 ↓
my_population_model
```

This is how the system can become enormous without making the core enormous.

---

# 38. User Extensions Must Be First-Class

This is important for your educational vision.

A teacher should be able to define:

```text
type Planet { ... }
```

without modifying the language.

A student could potentially define:

```text
type MyMachine { ... }
```

and experiment with it.

A researcher could build:

```text
package my_research_model
```

without needing to submit a compiler patch.

So:

> **If a concept can be expressed with existing semantics, defining it should not require changing the compiler.**

That is a major test for the architecture.

---

# 39. What Cannot Be User-Defined?

There must still be a boundary.

A user shouldn't be able to redefine:

```text
assignment semantics
type checking itself
memory safety
transaction semantics
core state identity
fundamental evaluation rules
```

through ordinary DSL definitions.

Otherwise the language stops having a stable semantic foundation.

Those belong to:

```text
CORE LANGUAGE
RUNTIME
EXTENSION ABI/API
```

depending on the feature.

---

# 40. Native Extension Boundary

For native extensions, we need a stable interface.

Conceptually:

```text
CORE SEMANTIC IR
        ↓
EXTENSION INTERFACE
        ↓
NATIVE IMPLEMENTATION
        ↓
RESULT + STATUS + PROVENANCE
```

This is particularly relevant for your Rust implementation.

A Rust extension could implement:

```text
Solver
Renderer
DataSource
Sensor
Optimizer
NumericalKernel
```

while the DSL sees a semantic capability.

---

# 41. Rust Should Not Leak Into the DSL

This is important.

We don't want:

```text
rust_type<T>
unsafe fn(...)
trait Solver...
```

becoming DSL concepts.

The DSL should express:

```text
solver
data source
computation
behavior
```

The Rust runtime handles implementation.

That keeps the language domain-oriented rather than implementation-oriented.

---

# 42. Extension Discovery

Eventually, users need to know what extensions exist.

Conceptually:

```text
registry
├── mathematics
├── physics
├── chemistry
├── biology
├── computer_science
...
```

But this is tooling/package-management territory rather than core semantics.

The core only needs to understand:

```text
import definition
resolve dependency
verify compatibility
```

---

# 43. Security Boundary

This becomes especially important once native extensions exist.

A DSL file shouldn't automatically gain:

- filesystem access,
- network access,
- hardware access,
- arbitrary native execution.

An extension should declare capabilities.

For example:

```text
requires:
    sensor.read
    network.connect
```

The runtime/user can decide whether those capabilities are allowed.

This is particularly relevant for educational content distributed to students.

---

# 44. Extension Permissions

Potential capability categories:

```text
filesystem
network
camera
microphone
sensor
microcontroller
GPU
native-code
external-process
```

Again, these are runtime/security concepts rather than model semantics.

But the extension model needs a boundary between:

```text
WHAT THE EXTENSION MEANS
```

and:

```text
WHAT THE EXTENSION IS ALLOWED TO ACCESS
```

---

# 45. Extension Metadata

An extension package may therefore conceptually contain:

```text
Extension
├── identity
├── version
├── dependencies
├── semantic definitions
├── implementations
├── capabilities
├── compatibility
├── documentation
└── examples
```

Not all of this belongs in the language itself.

Some belongs in the package ecosystem.

# 47. What About Completely New Domains?

This is the real stress test.

Suppose someone wants to model:

> traffic flow through a city.

We don't have a `Traffic` primitive.

They can combine:

```text
vehicles
roads
graphs
queues
agents
probability
spatial relationships
events
optimization
```

from existing extensions.

Or suppose someone wants:

> an ecosystem with predator-prey dynamics.

They combine:

```text
entities
collections
population variables
stochastic processes
spatial domains
interactions
observations
```

No compiler change.

That is exactly what we want.

---

# 48. Extension Self-Hosting Test

A strong architectural test is:

> **Can we implement the first-party domain libraries using the same extension mechanism that users receive?**

For example:

```text
core
 ↓
math library
 ↓
physics library
 ↓
chemistry library
```

If physics requires special compiler code such as:

```text
if (type == Projectile) ...
```

then `Projectile` isn't really an extension.

It's a hidden core primitive.

This gives us a powerful validation criterion:

> **First-party domains should use the same extension mechanism as third-party/user domains wherever practical.**

---

# 49. Extension Escalation

There will inevitably be cases where a DSL-only extension isn't enough.

So the architecture can escalate:

```text
LEVEL 1
Pure DSL definition

        ↓ insufficient

LEVEL 2
DSL + generic runtime capability

        ↓ insufficient

LEVEL 3
Native implementation through extension interface

        ↓ insufficient

LEVEL 4
Core/runtime enhancement
```

And **Level 4 should be rare**.

This gives us a disciplined way of deciding when something deserves to enter the core.

---

# 50. Core Promotion Rule

This is perhaps the most important governance rule for the language.

A feature should become core only when:

1. Many unrelated domains require it.
2. It cannot reasonably be composed from existing primitives.
3. Its semantics are fundamental rather than domain-specific.
4. It affects multiple runtime subsystems.
5. Having it outside the core creates unnecessary semantic ambiguity or inefficiency.
6. Its semantics are stable enough to become foundational.

For example:

```text
Quantity
Function
Collection
Field
Event
Constraint
```

have strong arguments for being fundamental.

Whereas:

```text
Projectile
Atom
Pendulum
Molecule
Graph
```

do not.

# 52. The Three Most Important Boundaries

After this artifact, I think we have three extremely important boundaries.

### Boundary 1 Core vs Domain

```text
CORE
    fundamental semantics

DOMAIN
    reusable meaning built from core
```

### Boundary 2 Semantics vs Implementation

```text
SEMANTICS
    what something means

IMPLEMENTATION
    how it executes
```

### Boundary 3 Library vs Language

```text
LANGUAGE
    stable fundamental constructs

LIBRARY
    vocabulary and reusable models
```

If these boundaries hold, the system can grow enormously without the DSL becoming a giant collection of special cases.

---

# 53. Extension Invariants

Let's make these explicit.

```text
1. Extensions add vocabulary; they do not redefine core semantics.

2. Domain concepts should be library constructs unless they are genuinely
   fundamental.

3. Extensions compose through the existing composition model.

4. Extensions use the existing type system.

5. Extensions use explicit interfaces/contracts.

6. DSL-defined and native-defined extensions expose the same semantic boundary.

7. Native implementations must not silently alter model meaning.

8. Representation extensions do not redefine the model.

9. Interaction extensions ultimately lower to generic operations.

10. Extension dependencies are explicit.

11. Extension versions participate in reproducibility/provenance.

12. User-defined extensions are first-class.

13. First-party domain libraries should use the same extension mechanism
    wherever practical.

14. New core primitives require justification against the general case space.

15. Extension failure should remain localized according to the error model.

16. Extension capabilities requiring external resources must be explicitly
    declared.
```

# 55. But There Is One Remaining Question

The extension model exposes a deeper issue that we should **not skip**:

Suppose I define:

```text
type Projectile {
    position
    velocity
    mass
}
```

and another person defines:

```text
type Projectile {
    position
    velocity
    mass
    drag_coefficient
}
```

And another defines:

```text
type Projectile {
    position
    velocity
    mass
    angular_velocity
    spin
}
```

What does it actually mean for these definitions to be **the same kind of thing**?

And how do we make this work:

```text
physics.Projectile
        ↓
GuidedProjectile
        ↓
MyRocket
```

without falling into an inheritance mess?

This brings us to a deeper layer of the type system:

```text
TYPE
  ↓
INTERFACE
  ↓
CAPABILITY
  ↓
COMPOSITION
  ↓
SPECIALIZATION
```

We touched this in 09.5, but **09.9 shows that it needs to be validated much more deeply**.

That is probably the first thing I'd investigate before moving to 09.10 Example Programs, because the examples will otherwise be built on assumptions about **type extension, specialization, interfaces, generic behavior, and domain vocabulary** that we haven't fully stress-tested yet.
