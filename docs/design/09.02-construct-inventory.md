---

# 1. First: What is a "construct"?

A construct is something the author can deliberately express in the language.

But not everything in our architecture deserves to become a language construct.

We have four categories:

```text
┌─────────────────────────────────────┐
│ 1. CORE LANGUAGE CONSTRUCT          │
│    Author needs it directly.        │
├─────────────────────────────────────┤
│ 2. LIBRARY CONSTRUCT                │
│    Built using the core language.   │
├─────────────────────────────────────┤
│ 3. INFERRED CONSTRUCT               │
│    System can derive it safely.     │
├─────────────────────────────────────┤
│ 4. RUNTIME DETAIL                   │
│    Author shouldn't need to express │
│    it directly.                     │
└─────────────────────────────────────┘
```

This distinction will prevent the DSL from becoming a giant collection of specialized commands.

# 3. SYSTEM

### Candidate: CORE

A system gives us a semantic boundary.

It can contain:

```text
state
behavior
context
observations
projections
interactions
```

This is useful for:

- a complete simulation
- a mathematical visualization
- an educational activity
- a subsystem
- a reusable component

### Verdict

**CORE CONSTRUCT**

```text
System
```

---

# 4. VALUE

### Candidate: CORE

Values are fundamental.

Examples:

```text
42
3.14
true
"hello"
[1, 2, 3]
(2, 4)
```

But physical quantities, vectors, matrices, distributions, etc. can be types built around the value system.

### Verdict

**CORE**

---

# 5. TYPE

### Candidate: CORE

The language needs a way to distinguish:

```text
Real
Integer
Vector
Point
Quantity
Function
...
```

This becomes especially important once we reach the type-system step.

### Verdict

**CORE**

---

# 6. OBJECT

### Candidate: CORE

We need identity.

Consider two particles:

```text
particle A
particle B
```

They may currently have identical properties, but they are still different entities.

Therefore:

```text
identity + state
```

needs representation.

### Verdict

**CORE**

---

# 7. PROPERTY

### Candidate: CORE

Objects need associated values:

```text
particle.mass
particle.position
particle.velocity
```

Properties may be:

- constant
- variable
- derived
- computed
- stochastic
- user-controlled

### Verdict

**CORE**

---

# 8. COLLECTION

### Candidate: CORE

This one is extremely important.

Without collections, we'd struggle with:

- particle systems
- populations
- graph nodes
- datasets
- molecules
- arrays
- repeated structures
- dynamic entities

### Verdict

**CORE**

Although particular collection operations can be library functionality.

---

# 9. RELATION

### Candidate: CORE

We established that relationships are not merely metadata.

They can have:

- identity
- properties
- state
- lifecycle

For example:

```text
A connected_to B
```

may later become:

```text
A not_connected_to B
```

Or a chemical bond may break.

### Verdict

**CORE**

---

# 10. FUNCTION

### Candidate: CORE

Functions are fundamental mathematical/computational mappings.

```text
f(x) → y
```

They are needed everywhere.

### Verdict

**CORE**

---

# 11. EXPRESSION

### Candidate: CORE

Expressions describe computation:

```text
x² + 2x + 1
```

or:

```text
mass * acceleration
```

### Verdict

**CORE**

---

# 12. PREDICATE

### Candidate: CORE

A predicate produces a Boolean condition.

```text
x > 5
inside(circle, point)
temperature >= boiling_point
```

Predicates underpin:

- rules
- events
- constraints
- interactions
- filtering
- branching

### Verdict

**CORE**

Potentially this doesn't need a distinct syntactic construct: it could simply be a type of expression.

That's an important distinction:

> **Semantic construct ≠ necessarily dedicated syntax.**

We'll revisit this during syntax design.

### Verdict

**CORE SEMANTIC CONCEPT**

Possibly **no dedicated keyword**.

---

# 13. EQUATION

### Candidate: CORE SEMANTIC CONSTRUCT

Equations are important because:

```text
equation ≠ expression
```

An expression produces a value.

An equation establishes a relationship.

For example:

```text
F = m*a
```

and:

```text
dN/dt = -λN
```

have semantic meaning beyond simply evaluating an expression.

### Verdict

**CORE SEMANTIC CONSTRUCT**

Whether it gets special syntax is deferred.

---

# 14. RULE

### Candidate: CORE

Rules represent conditional behavior.

Conceptually:

```text
condition → operation
```

For example:

```text
if x < 0:
    bounce()
```

### Verdict

**CORE**

---

# 15. PROCESS

### Candidate: CORE

A process describes ongoing evolution.

Examples:

- continuous motion
- diffusion
- population growth
- iterative algorithm

It is different from an event.

### Verdict

**CORE**

---

# 16. EVENT

### Candidate: CORE

Events represent discrete occurrences.

Examples:

```text
collision
decay
reaction
timer expiration
user intervention
particle creation
```

Events can be:

- scheduled
- conditional
- random
- external
- user-generated

### Verdict

**CORE**

---

# 17. CONSTRAINT

### Candidate: CORE

Constraints define permitted states.

Examples:

```text
x >= 0
distance(a,b) <= r
sum(probabilities) == 1
```

They are important independently of simulation.

### Verdict

**CORE**

---

# 18. DOMAIN

### Candidate: CORE

A domain describes the space over which values/functions operate.

For example:

```text
x ∈ [0, 10]
```

or:

```text
time ∈ [0, 100s]
```

or:

```text
nodes ∈ Graph
```

### Verdict

**CORE**

---

# 19. SPACE

### Candidate: CORE, but specialized

Space is essentially a specialized domain with spatial semantics.

It needs:

- coordinates
- geometry
- distance
- direction
- transformations

### Verdict

**CORE SEMANTIC CONSTRUCT**

Potentially represented as a specialized `domain` rather than a completely independent primitive.

---

# 20. TIME

Same question.

Time is a domain/context with temporal semantics.

We need:

```text
t
duration
instant
clock
timestep
```

But the DSL doesn't necessarily need separate fundamental machinery for every one.

### Verdict

**CORE SEMANTIC CONSTRUCT**

Possibly represented through a generalized domain/context system.

---

# 21. PARAMETER

### Candidate: CORE

A parameter is externally controllable/configurable input to a model.

For example:

```text
gravity = 9.81 m/s²
mass = 2 kg
initial_velocity = 10 m/s
```

It differs from an ordinary variable because its role is **model configuration/control**.

### Verdict

**CORE SEMANTIC CONCEPT**

Dedicated syntax may be justified because parameter authoring is extremely common.

---

# 22. FIELD

### Candidate: CORE

We deliberately established fields as first-class:

```text
F(x,y,t) → value
```

They appear in:

- electromagnetism
- temperature
- pressure
- fluid dynamics
- probability density
- terrain
- vector fields

### Verdict

**CORE**

---

# 23. OBSERVATION

### Candidate: CORE

Observation is fundamental because:

```text
Model
  ↓
Observation
  ↓
Data
```

is different from simply reading a property.

An observation may include:

- sampling
- measurement
- instrument behavior
- uncertainty
- timestamp
- resolution

### Verdict

**CORE**

---

# 24. DATA

### Candidate: CORE

Observed information must have a first-class destination.

Data supports:

- graphs
- tables
- statistics
- analysis
- exports
- educational feedback

### Verdict

**CORE**

---

# 25. PROJECTION

### Candidate: CORE

This is one of the constructs I would **strongly retain**.

We don't want:

```text
model → magic renderer
```

We need:

```text
model
  ↓
projection
  ↓
representation
```

A projection expresses **what semantic information is being mapped into a representation**.

### Verdict

**CORE**

---

# 26. REPRESENTATION

### Candidate: CORE SEMANTIC CONCEPT

A representation is what something becomes in a presentation context.

Examples:

```text
circle
arrow
text
equation
graph
histogram
timeline
table
field visualization
```

However, individual representation types should be libraries.

So:

```text
Representation
```

is core.

But:

```text
Circle
Arrow
Histogram
Plot
```

are likely library constructs.

### Verdict

**CORE**

---

# 27. VIEW

### Candidate: CORE

A view gives a presentation context.

It may contain:

```text
camera
layout
visibility
scale
selection
representation instances
```

### Verdict

**CORE**

---

# 28. INTERACTION

### Candidate: CORE

We established interaction as a semantic subsystem rather than a renderer feature.

It needs to express:

```text
input
intent
target
operation
effect
```

### Verdict

**CORE**

---

# 29. OPERATION

### Candidate: CORE

An interaction ultimately produces an operation.

Operations include categories such as:

```text
SET
MODIFY
CREATE
DESTROY
CONNECT
DISCONNECT
MEASURE
SELECT
START
PAUSE
STEP
RESET
BRANCH
```

But here's an important distinction:

These **categories** don't necessarily need to become keywords.

The fundamental concept is:

> **An operation changes something or requests an execution/view/observation action.**

### Verdict

**CORE SEMANTIC CONCEPT**

---

# 30. EXPERIMENT

### Candidate: CORE OR LIBRARY?

This is an interesting boundary.

We can describe an experiment using existing constructs:

```text
initial state
parameters
interventions
execution
observations
results
```

So technically it could be composed.

However, experimentation is such a central use case that a first-class construct may dramatically improve authoring.

### Verdict

**CORE LANGUAGE CONCEPT**

But we should test this against actual examples before giving it dedicated syntax.

---

# 31. ANIMATION

### Candidate: NOT FUNDAMENTAL

We need animation semantics.

But animation can potentially be constructed from:

```text
time
property changes
transitions
sequences
representation state
```

For example:

```text
position(t)
opacity(t)
scale(t)
```

could describe animation.

Therefore animation itself may be a **higher-level construct**.

### Verdict

**LIBRARY / HIGH-LEVEL CONSTRUCT**

This does **not** mean the DSL won't have convenient animation syntax later.

It means animation shouldn't contaminate the deepest semantic core.

---

# 32. CAMERA

### Candidate: NOT CORE

Camera belongs to presentation state.

We need camera semantics, but:

```text
camera
zoom
pan
rotation
```

don't need to be fundamental model constructs.

### Verdict

**VIEW/PRESENTATION LIBRARY**

---

# 33. SHAPES

Things such as:

```text
circle
rectangle
line
polygon
arrow
text
```

are clearly necessary for the initial 2D system.

But they are not universal semantic primitives.

A chemistry model doesn't fundamentally contain a circle.

### Verdict

**REPRESENTATION LIBRARY**

---

# 34. GRAPH

This is an important test.

Should `Graph` be core?

We need graph algorithms, networks, trees, etc.

But a graph can be constructed from:

```text
objects
collections
relations
```

Therefore the underlying semantics already support graphs.

### Verdict

**DOMAIN LIBRARY**

Not core.

A graph library can give us:

```text
Graph
Node
Edge
Traversal
ShortestPath
```

without changing the language core.

---

# 35. PARTICLE

A particle is essentially:

```text

mass
```

### Verdict

**PHYSICS LIBRARY**

# 36. PROJECTILE

Clearly composed from:


### Verdict

**PHYSICS LIBRARY**

# 37. MOLECULE / ATOM / BOND / REACTION

# 38. ODE SOLVER

Should the DSL contain:

```text

verlet
...
```

as fundamental constructs?

No.

The model says:

```text

```


**RUNTIME / COMPUTATION LIBRARY**

# 45. But there's an important problem

We have arrived at something we should **not rush past**.

Our Tier 1 list contains about 30 concepts.

That doesn't mean the final DSL needs 30 keywords.

For example:

```text
PROPERTY
VARIABLE
PARAMETER
VALUE
EXPRESSION
FUNCTION
EQUATION
PREDICATE
```

may be represented by a smaller set of deeper language mechanisms.

Likewise:

```text
PROCESS
EVENT
RULE
OPERATION
```

may share underlying machinery.

And:

```text
DOMAIN
SPACE
TIME
```

may have a common abstraction.

So the next step should **not** simply be:

> "Let's turn these 30 things into keywords."

Instead we need to determine the **semantic dependency structure**.

# 47. A potentially deeper discovery

We may eventually discover that many of these constructs reduce to a smaller semantic kernel:

```text
VALUE
OBJECT
RELATION
DOMAIN
EXPRESSION
BEHAVIOR
STATE
OBSERVATION
PROJECTION
OPERATION
```

with things like:

```text
Property
Collection
Function
Equation
Predicate
Rule
Process
Event
Constraint
Field
Experiment
View
Interaction
```

being structured forms of those primitives.

**But we should not decide that yet.**

That would be imposing an abstraction before testing it.

Instead, our next stage should examine the candidate constructs against the full case catalogue and ask:

> Can every required case be expressed if we remove this construct?

That will tell us whether something is truly fundamental.
