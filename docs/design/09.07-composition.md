# 09.7 Composition

The central question is:

> **How do independently defined pieces become a larger model without losing their meaning, encapsulation, or ability to evolve independently?**

This is essential because our target isn't merely:

```text
one file → one animation
```

We want things like:

```text
particle model
    +
gravity model
    +
collision model
    +
measurement system
    +
2D projection
    +
interactive controls
```

to form one coherent system.

And eventually:

```text
physics library
    ↓
projectile component
    ↓
projectile experiment
    ↓
interactive lesson
    ↓
video/web/desktop output
```

---

# 1. Composition is not inheritance

The first decision should be clear:

> **Composition is the primary reuse mechanism.**

We don't want the DSL to become an object-oriented class hierarchy.

For example, we shouldn't need:

```text
Projectile
  extends MovingObject
      extends PhysicalObject
          extends Object
```

Instead:

```text
Projectile System
├── particle
├── gravity
├── motion process
├── observation
└── view
```

Components cooperate through explicit interfaces.

---

# 2. What can be composed?

From the previous artifacts, we have many candidates:

```text
VALUES
EXPRESSIONS
FUNCTIONS
OBJECTS
COLLECTIONS
RELATIONS
FIELDS
PROCESSES
EVENTS
CONSTRAINTS
OBSERVATIONS
DATASETS
PROJECTIONS
REPRESENTATIONS
VIEWS
INTERACTIONS
SYSTEMS
```

But these don't all compose in the same way.

So we need several composition mechanisms rather than one universal `compose`.

---

# 3. The major composition forms

I see at least these:

```text
COMPOSITION
│
├── STRUCTURAL
│   └── system contains components
│
├── FUNCTIONAL
│   └── output → input
│
├── STATE
│   └── shared/accessed state
│
├── BEHAVIORAL
│   └── processes/events interact
│
├── RELATIONAL
│   └── objects connected through relations
│
├── TEMPORAL
│   └── events/processes coordinated in time
│
├── PRESENTATIONAL
│   └── multiple projections/views
│
└── EXPERIMENTAL
    └── model + controls + observations
```

---

# 4. Systems as composition boundaries

Our generalized model already has:

```text
System
├── state
├── behavior
├── context
├── observations
├── presentation
└── interaction
```

Therefore a system can itself contain subsystems.

For example:

```text
system SolarSystem {

    system Sun { ... }

    system Earth { ... }

    system Moon { ... }
}
```

But we need to be careful.

Does a nested system mean:

> merely a namespace?

Or:

> a genuinely independent semantic subsystem?

I think it should be the latter.

---

# 5. Subsystems

A subsystem should have its own:

```text
state
behavior
context
observations
interfaces
```

but participate in a containing system.

Conceptually:

```text
SYSTEM A
│
├── SUBSYSTEM B
│   ├── state
│   ├── behavior
│   └── interface
│
└── SUBSYSTEM C
    ├── state
    ├── behavior
    └── interface
```

This gives us hierarchy without requiring inheritance.

---

# 6. Why subsystems matter

Consider a vehicle simulation:

```text
Vehicle
├── battery
├── motor
├── inverter
├── wheels
├── controller
└── telemetry
```

Each can be independently modeled.

The battery shouldn't need to know the internals of the motor.

Instead:

```text
Battery
    → electrical power
    → Motor
```

This is much cleaner.

---

# 7. Interfaces

This suggests a first-class concept:

> **An interface defines what a component exposes to other components.**

For example:

```text
interface PowerSource {
    voltage : Voltage
    current : Current
}
```

A battery can provide that interface.

A motor can consume it.

The interface doesn't care how the battery computes its voltage.

---

# 8. Interfaces should describe semantics, not implementation

For example:

```text
interface PositionSource {
    position : Point<2>
}
```

could be satisfied by:

- a particle,
- a vehicle,
- a robot,
- a graph node,
- a tracked person,
- a mathematical point.

This is powerful because composition becomes semantic.

---

# 9. Three ways components communicate

Components can interact through:

```text
A
│
├── shared values
├── functions
├── events
├── relations
└── interfaces
```

We should not make everything shared mutable state.

---

# 10. Shared values

Simple composition:

```text
gravity
```

Both systems may read it.

For example:

```text
Environment
    └── gravity

Projectile
    └── reads gravity
```

But the projectile doesn't own gravity.

---

# 11. Data-flow composition

Another approach:

```text
Battery.voltage
       ↓
Inverter.input_voltage
       ↓
Motor.voltage
```

This is essentially function/data-flow composition.

This should be strongly supported because scientific models often naturally form pipelines.

---

# 12. Functional composition

Suppose:

```text
velocity = derivative(position)
acceleration = derivative(velocity)
```

This gives:

```text
position
   ↓
derivative
   ↓
velocity
   ↓
derivative
   ↓
acceleration
```

No shared mutable state is necessary.

This is a very useful form of composition.

---

# 13. Process composition

Now consider:

```text
process gravity
process drag
process collision
```

All affect the same physical system.

We need to define how they compose.

For example:

```text
gravity → force
drag    → force
collision → force
```

Then one integration mechanism combines the resulting effects.

This is better than having each process blindly write:

```text
velocity = ...
```

and fight over ownership.

---

# 14. Multiple processes modifying state

This is one of the most important composition problems.

Suppose:

```text
process gravity {
    velocity += gravity * dt
}

process drag {
    velocity += drag * dt
}
```

Both modify:

```text
ball.velocity
```

What happens?

If execution order matters, we could accidentally get:

```text
gravity
→ drag
→ result
```

versus:

```text
drag
→ gravity
→ result
```

For some systems these are equivalent.

For others they aren't.

The runtime semantics already told us that execution ordering must be explicit.

Composition therefore needs a better abstraction.

---

# 15. Contribution vs ownership

A useful distinction:

```text
gravity
    contributes acceleration

drag
    contributes acceleration

collision
    contributes impulse
```

rather than:

```text
gravity
    owns velocity
```

Then a solver/evolution mechanism combines contributions.

This is particularly powerful for physics.

---

# 16. But don't make "force" a core primitive

We don't want:

```text
Force
Impulse
Acceleration
```

as fundamental DSL primitives.

Instead, the core can support:

```text
value
function
process
operation
composition
```

The physics library can define "force accumulation" using those.

---

# 17. Event composition

Events provide another mechanism.

For example:

```text
collision
    ↓
emit collision event
    ↓
damage subsystem
    ↓
sound subsystem
    ↓
statistics subsystem
```

One event can therefore be observed by multiple components.

This avoids direct coupling.

---

# 18. Event subscriptions

Conceptually:

```text
event collision
    → handler A
    → handler B
    → handler C
```

The handlers should not need to know about each other.

This is useful for:

- simulations,
- educational feedback,
- telemetry,
- logging,
- animation,
- audio,
- analytics.

---

# 19. Event data

An event can carry structured data.

For example:

```text
CollisionEvent {
    object_a
    object_b
    position
    time
}
```

Again, this can be library-defined.

The core only needs:

```text
Event<T>
```

where `T` is the event payload.

---

# 20. Relations as composition

Sometimes two systems are connected through a relation.

For example:

```text
particle A
    ↕
bond
    ↕
particle B
```

The relation itself can carry state:

```text
Bond
├── endpoints
├── length
├── energy
└── state
```

This supports chemistry, graphs, networks and many physical systems.

---

# 21. Dynamic composition

Composition cannot always be static.

Consider:

```text
chemical reaction
A + B → C
```

The system's structure changes.

Or:

```text
node connects to node
```

Or:

```text
cell divides
```

Therefore composition must support:

```text
create
destroy
connect
disconnect
merge
split
```

We already identified these as operations in the interaction model.

Here they become model/runtime composition operations.

---

# 22. Composition vs collection

A collection:

```text
particles : Collection<Particle>
```

does not necessarily mean the particles form one subsystem.

A subsystem:

```text
system particle_system { ... }
```

has its own behavior/context/interfaces.

So:

```text
Collection
≠
Subsystem
```

A subsystem may contain collections.

---

# 23. Composition and encapsulation

A subsystem should expose only what it needs to expose.

For example:

```text
Battery
├── internal chemistry
├── internal temperature
├── cells
└── controller state

PUBLIC
├── voltage
├── current
└── state_of_charge
```

Another subsystem shouldn't casually access:

```text
battery.internal.cell[27].ion_state
```

unless explicitly exposed.

This is essential as models become large.

---

# 24. Public vs private

Therefore components need visibility:

```text
private
public
```

Potentially:

```text
protected
```

but I don't think we need object-oriented `protected` semantics.

Public bindings form the interface.

Private bindings remain implementation details.

---

# 25. Interface connections

We can think of composition as:

```text
Component A
    │
    │ provides
    ↓
 Interface
    ↑
    │ consumes
Component B
```

For example:

```text
Battery
   │
   │ electrical output
   ↓
Inverter
```

The compiler can check:

```text
Battery.voltage : Voltage
```

matches:

```text
Inverter.input_voltage : Voltage
```

This uses our type system.

---

# 26. Interface adapters

Sometimes two components have compatible semantics but different representations.

For example:

```text
A outputs
    velocity : Vector<3>

B expects
    speed : Real
```

We can connect them through:

```text
magnitude
```

giving:

```text
Vector<3>
    ↓ magnitude
Real
```

So adapters are usually just functions/projections/conversions.

We don't need a giant adapter framework.

---

# 27. Composition of mathematical models

Consider:

```text
f(x) = x²
g(x) = sin(x)
```

Then:

```text
h = g ∘ f
```

This is composition at the mathematical level.

The DSL should support it naturally.

---

# 28. Composition of fields

Suppose:

```text
temperature(x,y)
velocity(x,y)
```

Then:

```text
heat_flux(x,y)
    = function(temperature...)
```

A field is just a function over a domain, so composition follows naturally.

This is another reason not to make fields a completely separate core mechanism.

---

# 29. Composition of observations

Suppose we have:

```text
position(t)
velocity(t)
```

We can derive:

```text
speed(t)
distance_travelled(t)
average_speed
```

Then:

```text
Dataset
   ↓
Projection
   ↓
Plot
```

Again, each stage composes through typed data flow.

---

# 30. Composition of views

This is extremely important for the project.

One model may have:

```text
                    MODEL
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
    2D scene        graph        equation
       │              │              │
       ↓              ↓              ↓
     View A         View B         View C
```

These views should remain synchronized because they observe the same underlying model/state.

This is not duplication of the model.

---

# 31. Composite views

A view can itself contain views.

For example:

```text
Lesson View
├── simulation panel
├── graph panel
├── equation panel
├── controls
└── measurement panel
```

Thus:

```text
```

is naturally compositional.

---

# 32. Composition of interactions

Likewise, an interaction can be composed.

For example:

```text
drag
+
constraint
+
measurement
+
feedback
```

A user drags a point:

```text
drag
 ↓
constraint
 ↓
model update
 ↓
observation
 ↓
graph update
 ↓
feedback
```

This is already supported by our previous interaction model.

---

# 33. Composition of experiments

An experiment is naturally:

```text
MODEL
+
INITIAL STATE
+
PARAMETERS
+
INTERVENTIONS
+
EXECUTION
+
OBSERVATIONS
+
RESULTS
```

So experiments can themselves be composed.

For example:

```text
experiment A
    ↓
results
    ↓
experiment B
```

or:

```text
same model
├── g = 9.0
├── g = 9.5
├── g = 9.81
└── g = 10.0
```

---

# 34. Model reuse

We should support something like:

```text
component ProjectileModel { ... }

system Lesson {
    use ProjectileModel
}
```

But what does `use` mean?

Potentially:

```text
reference existing instance
instantiate new component
inherit definition
import module
copy model
```

These are different.

We need explicit semantics.

---

# 35. Definition vs instance

A reusable component should be a definition:

```text
component Projectile { ... }
```

An actual model element is an instance:

```text
projectile1 : Projectile
projectile2 : Projectile
```

Then:

```text
Projectile definition
       ↓ instantiate
Projectile instance
```

This is much cleaner than copying source code.

---

# 36. Generic components

We may want parameterized components:

```text
component Projectile(gravity, initial_velocity) {
    ...
}
```

Then:

```text
p1 = Projectile(9.81 m/s²...)
p2 = Projectile(3.71 m/s²...)
```

This uses the type/binding machinery we've already designed.

---

# 37. Component parameters vs system parameters

These are different concepts.

A component parameter may be configured when instantiated:

```text
Projectile(gravity = 9.81 m/s²)
```

The containing experiment may then expose it:

```text
experiment {
    control projectile.gravity
}
```

So parameterization can propagate through interfaces.

---

# 38. Dependency injection, conceptually

We don't necessarily need the programming-language concept "dependency injection," but the semantic idea is useful.

For example:

```text
Projectile
    requires GravitySource
```

The containing system provides:

```text
EarthGravity
```

or:

```text
MoonGravity
```

Then the same projectile model can run under either environment.

This is powerful for reusable scientific models.

---

# 39. Composition and environments

Consider:

```text
Environment
├── gravity
├── temperature
├── pressure
└── magnetic_field
```

A model can depend on the environment without owning it.

Thus:

```text
Model
    requires
        gravity
        temperature
```

The containing system supplies them.

This is a very natural abstraction for simulation.

---

# 40. Shared state vs copied state

Another important question:

If we compose two components, does state become:

```text
A.x
   ↕
B.x
```

or:

```text
A.x
   ↓ copy
B.x
```

These are very different.

We should make sharing explicit.

Default should probably be:

> **Values are passed or referenced explicitly; composition does not silently merge state.**

That prevents spooky action at a distance.

---

# 41. State ownership

Every mutable model value should have a clear owner.

For example:

```text
Battery owns
    charge

Motor owns
    angular_velocity

Controller owns
    target_speed
```

A different subsystem may read these.

Writing should require an explicit operation/interface.

This gives us a strong invariant:

> **Every mutable semantic state element has an identifiable owner.**

---

# 42. Bidirectional coupling

Sometimes two components genuinely affect each other.

For example:

```text
Battery
  → voltage → Motor
Motor
  → current → Battery
```

This forms:

```text
Battery → Motor
   ↑       ↓
   └───────┘
```

Cycles must be allowed.

We already established that dependency cycles are not automatically errors.

The runtime must determine whether they represent:

- algebraic coupling,
- iterative computation,
- feedback,
- dynamic evolution.

---

# 43. Algebraic coupling

For example:

```text
x = f(y)
y = g(x)
```

This is a coupled equation system.

Composition creates the system:

```text
{x = f(y), y = g(x)}
```

Then a solver can handle it.

The model doesn't need to know which numerical method will solve it.

---

# 44. Feedback coupling

Alternatively:

```text
A output
   ↓
B
   ↓
A input
```

This may represent a dynamic feedback loop.

The distinction between algebraic and temporal coupling belongs to behavior/runtime semantics, not basic composition.

---

# 45. Hierarchical composition

A system can contain:

```text
System
├── subsystem
│   ├── subsystem
│   └── subsystem
└── subsystem
```

This supports very complex models.

But hierarchy should not imply physical containment.

For example:

```text
organism
    → organs
        → cells
```

can be semantic hierarchy.

Likewise:

```text
network
    → routers
        → interfaces
```

is structural hierarchy.

---

# 46. Composition and scale

This is particularly useful because the same system might have multiple levels:

```text
microscopic
    ↓
mesoscopic
    ↓
macroscopic
```

For example:

```text
molecules
    ↓
statistical model
    ↓
pressure / temperature
```

These need not be one giant simulation.

They can be separate models connected through interfaces/data.

This supports model transformation and multi-scale simulation.

---

# 47. Composition does not imply simultaneous execution

A composed system can contain:

```text
model A
model B
model C
```

without all three evolving continuously.

One might be:

- static,
- event-driven,
- continuously integrated,
- externally updated.

Composition therefore shouldn't force one execution model onto all components.

---

# 48. Execution contracts

A component could expose what it requires:

```text
requires:
    temperature

produces:
    pressure

updates:
    every simulation step
```

This gives the runtime enough information to schedule it.

But again, we don't need to make this a giant user-facing framework.

Much can be inferred from dependencies.

---

# 49. Dependency graph

Composition ultimately produces a graph:

```text
Component A
   ↓
Component B
   ↓
Component C
```

with potentially:

```text
A ───→ B
│      ↓
└────→ C
       ↑
       │
       B
```

The runtime can use this graph for:

- scheduling,
- invalidation,
- parallelization,
- incremental computation,
- synchronization.

---

# 50. Composition and parallelism

If:

```text
A → C
B → C
```

and A/B don't depend on each other, they can potentially execute concurrently.

Thus the semantic composition graph can inform runtime optimization.

But:

```text
composition semantics
≠
parallel execution strategy
```

The author doesn't need to say:

```text
run A on thread 3
```

unless they explicitly want low-level control.

---

# 51. Composition of domain libraries

This is one of the biggest benefits.

Imagine:

```text
core
├── mathematics
├── geometry
├── physics
├── chemistry
├── biology
└── computer_science
```

A program might use:

```text
physics
+
statistics
+
graph
+
geometry
```

without the core having built-in knowledge of all these domains.

For example:

```text
particle simulation
      ↓
observations
      ↓
statistics
      ↓
histogram
      ↓
2D representation
```

Each library composes with the others through the core abstractions.

---

# 52. Composition of educational layers

The education system can sit above the model:

```text
Scientific Model
      ↓
Experiment
      ↓
Interaction
      ↓
Observation
      ↓
Educational Activity
      ↓
Feedback / Assessment
```

The educational layer doesn't need to modify the physics model's fundamental semantics.

This maintains our architecture:

```text
DOMAIN
  ↓
CORE
  ↓
RUNTIME
  ↓
PRESENTATION
  ↓
EDUCATION
```

---

# 53. Composition of output

The same model can feed multiple outputs:

```text
                  MODEL
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
      Interactive  Video     Data
          ↓         ↓         ↓
       runtime    frames    dataset
```

This is another form of composition.

The model shouldn't know whether it is being rendered interactively or recorded.

---

# 54. Composition and serialization

A composed system must be representable as data.

For example:

```text
System
├── component instances
├── connections
├── parameters
├── state
└── configuration
```

This will eventually support:

- saving projects,
- undo/redo,
- snapshots,
- branching,
- sharing,
- reproducible experiments.

Composition therefore needs stable semantic identities, which we already established in 09.6.

---

# 55. The core composition abstraction

After all these cases, I don't think we need one giant `Composition` primitive.

Instead, the core needs a few fundamental mechanisms:

```text
COMPOSITION KERNEL
│
├── CONTAINMENT
│   └── system contains components
│
├── INTERFACE
│   └── explicit exposed capabilities
│
├── CONNECTION
│   └── one component connected to another
│
├── DEPENDENCY
│   └── A depends on B
│
├── INSTANTIATION
│   └── definition → instance
│
└── IDENTITY
    └── stable component identity
```

The rest can be built from these.

---

# 56. Composition vs module

We should make another distinction:

```text
MODULE
    organizes definitions

SYSTEM
    represents a composed semantic system
```

For example:

```text
module physics.mechanics
```

might contain definitions.

Then:

```text
system Experiment
```

instantiates and composes those definitions.

So:

```text
MODULE
  ↓ provides definitions
SYSTEM
  ↓ creates instances
RUNTIME
```

---

# 57. Composition vs inheritance: final stance

I think the DSL should have:

```text
✓ composition
✓ interfaces
✓ parameterized definitions
✓ functions
✓ delegation
✓ explicit connections

limited / carefully considered:
△ inheritance
```

We don't need inheritance to model scientific systems.

---

# 58. A complete example

Consider a vehicle.

```text
system VehicleSimulation {

    battery = Battery(...)
    motor   = Motor(...)
    wheel   = Wheel(...)
    road    = Road(...)

    connect battery.output → motor.input
    connect motor.output → wheel.input
    connect wheel.contact → road.surface

    view scene {
        show battery
        show motor
        show wheel
        show road
    }
}
```

Semantically:

```text
VehicleSimulation
│
├── Battery instance
├── Motor instance
├── Wheel instance
├── Road instance
│
├── connection:
│   Battery → Motor
│
├── connection:
│   Motor → Wheel
│
└── connection:
    Wheel → Road
```

No inheritance required.

---

```text
Environment

Projectile

Motion

Observation
└── records position

Controls
```

Notice how many subsystems cooperate without any one of them becoming "the projectile simulation."

One model, multiple composed observations and views.

# 62. Composition invariants

We can now add several strong invariants to the DSL.

### 1

> **Composition does not imply inheritance.**

### 2

> **Components communicate through explicit dependencies, interfaces, functions, relations, data or events.**

### 3

> **A component owns its mutable state unless explicitly shared/exposed.**

### 4

> **Composition does not silently merge namespaces or state.**

### 5

> **A reusable definition is distinct from its runtime instances.**

### 6

> **A subsystem may contain subsystems.**

### 7

> **Cycles are allowed; their execution semantics are determined separately.**

### 8

> **Dynamic creation/destruction can change system topology without changing the underlying type definitions.**

### 9

> **Composition does not determine execution order unless dependencies require one.**

### 10

> **Composition does not determine representation.**

# 63. Refined composition model

The resulting structure is:

```text
COMPOSITION
│
├── DEFINITIONS
│   ├── component/type
│   ├── function
│   └── subsystem
│
├── INSTANCES
│   ├── object
│   └── subsystem instance
│
├── INTERFACES
│   ├── provided
│   └── required
│
├── CONNECTIONS
│   ├── value/data
│   ├── function
```
