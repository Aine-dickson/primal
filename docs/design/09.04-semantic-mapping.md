# 1. What is Semantic Mapping?

The fundamental question is:

> When an author writes something in the DSL, what does it mean in the generalized model?

We want:

```text
DSL SOURCE
    ↓
PARSED STRUCTURE
    ↓
SEMANTIC MEANING
    ↓
GENERALIZED MODEL
    ↓
RUNTIME / PRESENTATION / INTERACTION
```

For example, imagine the eventual language has:

```text
mass = 2 kg
```

We cannot simply say:

> "That's an assignment."

It could mean several different things:

```text
declaration
initialization
assignment
definition
derived property
constraint
parameter
```

Semantic mapping forces us to distinguish these.

---

# 2. First Principle: Syntax Is Not Meaning

Suppose we eventually choose:

```text
x = 5
```

The `=` character itself should not determine the semantics.

Depending on context, it could mean:

```text
x := 5
```

or:

```text
x(t) = ...
```

or:

```text
x = y
```

or:

```text
x = 5
```

as initialization.

The parser identifies structure.

The semantic phase determines meaning.

So:

```text
SYNTAX
  ≠
SEMANTICS
```

This will become very important when we design the actual grammar.

---

# 3. Semantic Categories of Author Statements

We identified a major distinction earlier.

An authored statement can perform fundamentally different jobs:

```text
DECLARATION
DEFINITION
INITIALIZATION
ASSIGNMENT
DERIVATION
CONSTRAINT
EVOLUTION
OBSERVATION
PROJECTION
INTERACTION
CONTROL
```

Let's define these precisely.

---

# 4. Declaration

A declaration introduces something that exists.

Conceptually:

```text
object ball
```

means:

> There is an identifiable object named `ball`.

It doesn't necessarily say anything about its state yet.

Similarly:

```text
function f
```

introduces a function.

```text
view Scene
```

introduces a view.

### Semantic effect

```text
Declaration
    ↓
creates a named semantic entity
```

It does **not necessarily change simulation state**.

---

# 5. Definition

A definition says what something **means in terms of something else**.

For example:

```text
speed = sqrt(vx² + vy²)
```

could mean:

> `speed` is defined as a derived value of `vx` and `vy`.

The crucial property is dependency.

```text
vx ─┐
    ├──→ speed
vy ─┘
```

If `vx` changes, `speed` changes.

This is fundamentally different from:

```text
speed = 10
```

which may be an assignment/initialization.

---

# 6. Initialization

Initialization establishes the starting state.

For example:

```text
ball.position = (0, 0)
ball.velocity = (10, 15)
```

inside an initial-state context means:

```text
S₀(ball.position) = (0,0)
S₀(ball.velocity) = (10,15)
```

This is not an ongoing assignment.

It defines the initial condition.

---

# 7. Assignment

Assignment changes an existing mutable value.

Conceptually:

```text
x := x + 1
```

means:

```text
old state
    ↓
operation
    ↓
new state
```

Unlike a definition:

```text
x = f(y)
```

which establishes a dependency, assignment explicitly changes state.

This distinction is critical.

---

# 8. Derivation

A derived value is computed from other state.

For example:

```text
speed := magnitude(velocity)
```

Conceptually:

```text
velocity
    ↓
derived computation
    ↓
speed
```

The author doesn't independently control `speed`.

Therefore:

```text
speed = 10
```

should normally be invalid if `speed` is declared as derived.

This gives us a useful semantic property:

```text
DERIVED VALUE
    ↓
readable
    ↓
not directly writable
```

unless an explicit inverse relationship exists.

---

# 9. Constraint

A constraint does not necessarily calculate a value.

It restricts valid states.

For example:

```text
mass > 0
```

means:

```text
valid(state) only if mass > 0
```

This is fundamentally different from:

```text
mass = 0
```

which could be an assignment.

And different again from:

```text
mass := 2 kg
```

which establishes state.

---

# 10. Evolution

Evolution specifies how state changes over time.

For example:

```text
position' = velocity
velocity' = acceleration
```

means something like:

```text
dposition/dt = velocity
dvelocity/dt = acceleration
```

This isn't an ordinary assignment.

It defines the relationship governing successive states.

Conceptually:

```text
S(t)
 ↓
evolution law
 ↓
S(t + dt)
```

The runtime then chooses how to execute that law.

---

# 11. Observation

An observation reads information from the system.

For example:

```text
observe ball.position
```

means:

```text
State
 ↓
Observation
 ↓
Data
```

It does not mutate the state.

This gives us another invariant:

```text
OBSERVE ≠ MODIFY
```

---

# 12. Projection

Projection maps semantic information into representation.

For example:

```text
show ball.position as point
```

means conceptually:

```text
ball.position
      ↓
projection
      ↓
point representation
```

The point is not the ball.

It is a representation of the ball's position.

---

# 13. Interaction

Interaction maps external activity to operations.

For example:

```text
on drag(ball) {
    ...
}
```

means something conceptually like:

```text
Input
 ↓
intent: drag
 ↓
target: ball
 ↓
operation
 ↓
model/runtime/view effect
```

The interaction itself is not the state change.

---

# 14. Runtime Control

Some statements operate on the runtime rather than the model.

For example:

```text
play
pause
step
reset
```

These affect:

```text
RUNTIME STATE
```

not necessarily:

```text
MODEL STATE
```

So semantic mapping must distinguish:

```text
model operation
runtime operation
view operation
observation operation
```

---

# 16. Now the Critical Part: State Semantics

We need to define what counts as **state**.

Consider:

```text
ball.position
ball.velocity
gravity
speed
trajectory
```

Are all of these state?

Not necessarily.

We can classify them.

### Stored state

```text
position
velocity
```

These are explicitly stored and evolve.

### Parameter state

```text
gravity
```

Configured externally.

### Derived state

```text
speed
```

Computed from velocity.

### Observed data

```text
trajectory_record
```

Produced by observation.

### Presentation state

```text
circle.screen_position
camera.zoom
selected
```

These are not scientific model state.

This gives us:

```text
MODEL STATE
├── stored state
├── parameter state
└── derived state

OBSERVATION STATE
└── datasets

PRESENTATION STATE
├── representation state
├── view state
└── selection

RUNTIME STATE
├── clock
├── execution state
├── scheduler
└── computational state
```

---

# 17. Semantic Meaning of `=`

This deserves special attention.

We should probably **not** allow one syntactic symbol to silently represent every possible relationship.

Consider:

```text
x = 5
```

Possible meanings:

### Initialization

```text
initial:
    x = 5
```

### Definition

```text
x = f(t)
```

### Equation

```text
x = y + 1
```

### Assignment

```text
set x = 5
```

### Parameter

```text
parameter x = 5
```

These should have distinguishable semantic contexts.

A possible future principle:

```text
DECLARATIVE CONTEXT
→ equality-like syntax can define relationships

STATE-MUTATION CONTEXT
→ explicit mutation syntax

INITIALIZATION CONTEXT
→ initialization syntax/context

EQUATION CONTEXT
→ equation semantics
```

We don't yet choose the exact operators.

But we now know the semantic distinction must exist.

---

# 18. Definitions vs Equations

This is another subtle distinction.

Consider:

```text
speed = distance / time
```

This could be a **definition**:

```text
speed := distance / time
```

But:

```text
F = m * a
```

is normally a physical relationship/equation.

And:

```text
x² + y² = r²
```

is a geometric constraint.

So the language needs to distinguish:

```text
definition
equation
constraint
```

even if the surface syntax eventually looks similar.

---

# 19. Functions vs Processes

Consider:

```text
f(x) = x²
```

This is a function.

It doesn't evolve anything.

Whereas:

```text
dx/dt = f(x)
```

describes evolution.

So:

```text
FUNCTION
    ↓
input → output

PROCESS
    ↓
state(t) → state(t+dt)
```

This distinction must survive into the DSL.

---

# 20. Events vs Processes

A process can be continuous or repeatedly executed.

An event is an occurrence.

For example:

```text
particle moves
```

is a process.

```text
particle collides with wall
```

is an event.

The event may trigger:

```text
velocity := reflected_velocity
```

So:

```text
PROCESS
    │
    └── may cause EVENT
                 │
                 ↓
              OPERATION
```

---

# 21. Rules vs Events

A rule:

```text
if x < 0:
    bounce
```

describes a conditional relationship.

An event:

```text
when x crosses 0:
    bounce
```

describes an occurrence.

A rule can therefore be implemented through event machinery, but their semantic meanings differ.

This supports our earlier conclusion:

> `rule` can potentially be a surface convenience over predicate + event/operation semantics.

---

# 22. Projection Semantics

Now consider:

```text
particle.position → circle.position
```

We need to establish what this means.

It means:

```text
source = particle.position
target = representation.position
mapping = coordinate transformation
```

So semantically:

```text
Projection {
    source: particle.position
    target: representation.position
    mapping: ...
}
```

The mapping may involve:

```text
identity
scale
translation
coordinate transform
function
aggregation
filter
encoding
```

For example:

```text
temperature → color
```

is a projection.

```text
particles → histogram
```

is also a projection.

The second one is not one-to-one.

That is why we deliberately avoided defining projection as simply:

```text
object → shape
```

---

# 23. Representation Lifecycle

Suppose:

```text
particles = collection of 100 objects
```

and:

```text
particles → circles
```

What happens when a particle is created?

The projection semantics should define that the representation corresponding to the new member becomes available.

Likewise:

```text
particle destroyed
```

causes its representation to disappear or transition according to the projection policy.

This means representation lifecycle can be **derived from semantic membership** rather than manually managed.

That is exactly the kind of inference we want.

---

# 24. Interaction Mapping

Suppose:

```text
point.position
```

is represented as a draggable point.

The projection is:

```text
model → representation
```

The interaction mapping is:

```text
representation/input
       ↓
model operation
```

These are related but not identical.

Therefore we can have:

```text
Projection:
    point.position → visual_point.position

Interaction:
    drag visual_point
        → set point.position
```

This becomes especially important when the representation isn't mathematically invertible.

---

# 25. Example: Temperature → Color

Suppose:

```text
temperature → color
```

There is no meaningful inverse:

```text
color → exact temperature
```

because the mapping may be:

- quantized
- nonlinear
- perceptual
- ambiguous

Therefore the projection is read-only.

If we want a color-based control, we need an **explicit interaction mapping**.

This validates the architecture from Artifact 07.

---

# 26. Example: Dragging a Point

Here the mapping can be explicitly writable:

```text
visual position
      ↓
inverse coordinate mapping
      ↓
model position
```

But constraints may intervene:

```text
user drag
   ↓
proposed position
   ↓
constraint validation
   ↓
committed position
```

So the semantic pipeline becomes:

```text
INPUT
 ↓
TARGET
 ↓
PROPOSED OPERATION
 ↓
CONSTRAINTS
 ↓
COMMIT
 ↓
STATE
```

---

# 27. Semantic Mapping of Animation

Animation is interesting.

Suppose:

```text
animate point.position from A to B over 2s
```

This should **not automatically mean**:

```text
model.position changes from A to B
```

It may instead mean:

```text
presentation.position(t)
```

changes.

Therefore we must distinguish:

```text
MODEL ANIMATION
```

from:

```text
PRESENTATION ANIMATION
```

If the model itself is evolving, the representation follows it.

If an author explicitly animates the representation, it is presentation behavior.

---

# 28. Semantic Mapping of Experiment

An experiment:

```text
experiment {
    ...
}
```

would expand conceptually into:

```text
Experiment
├── model reference
├── initial state
├── parameter configuration
├── interventions
├── execution
├── observations
└── results
```

So `experiment` is likely a **high-level composition**, rather than an irreducible semantic primitive.

---

# 29. Semantic Expansion

This suggests a powerful implementation architecture.

The author may write:

```text
experiment {
    ...
}
```

but the compiler can lower it into:

```text
System
+
Snapshot
+
Parameter bindings
+
Operations
+
Execution
+
Observations
+
Data
```

Likewise:

```text
rule {
    condition
    action
}
```

could lower to:

```text
Predicate
+
Event
+
Operation
```

And:

```text
field
```

could lower to:

```text
Function
+
Domain
```

This gives us a **lowering hierarchy**:

```text
HIGH-LEVEL DSL
      ↓
DESUGARING
      ↓
CORE SEMANTIC IR
      ↓
RUNTIME / PRESENTATION
```

That is likely going to become extremely important when we implement this in Rust.

# 31. Semantic Mapping Rules

We can now establish some preliminary rules.

### Rule 1 Declaration introduces identity

```text
declare X
```

→ creates semantic entity `X`.

---

### Rule 2 Definition creates dependency

```text
X := expression
```

→ `X` depends on expression inputs.

---

### Rule 3 Initialization establishes initial state

```text
initial X = value
```

→ modifies `S₀`.

---

### Rule 4 Assignment produces a state operation

```text
set X = value
```

→ produces operation:

```text
SET(X, value)
```

---

### Rule 5 Evolution defines state transition semantics

```text
X' = f(...)
```

→ defines an evolution law.

---

### Rule 6 Constraint restricts valid states

```text
constraint C
```

→ `valid(S) ⇒ C(S)`.

---

### Rule 7 Observation reads state

```text
observe X
```

→ produces data without changing model state.

---

### Rule 8 Projection maps semantics to representation

```text
project X as R
```

→ creates a mapping:

```text
X → R
```

---

### Rule 9 Interaction maps input to operation

```text
on I target X → operation
```

→ establishes an interaction mapping.

---

### Rule 10 Runtime controls modify execution state

```text
pause
```

→ runtime operation, not model operation.

# 35. One major consequence

We should **not design the parser and AST first**.

Instead:

```text
SOURCE
 ↓
AST
 ↓
SEMANTIC ANALYSIS
 ↓
SEMANTIC IR
 ↓
RUNTIME
```

The AST represents what the author wrote.

The semantic IR represents **what the author meant**.

For example:

```text
rule {
    if x < 0 {
        bounce()
    }
}
```

might become semantically:

```text
Predicate(x < 0)
        ↓
Event(condition)
        ↓
Operation(bounce)
```

The runtime doesn't need to understand the author's surface syntax.

That separation will make the eventual Rust implementation much cleaner.
